# 算法公式、常量与参数槽位

输出等于某个中间量、分支恒不触发、不同 dtype 路径出现完全不同症状，或 SIMD VF 编译无告警但全域失配时，优先核对公式和参数槽位。类型相同的裸指针、重复缓冲和复制出的调用点会让位置错配逃过编译检查。

## 公式与槽位表

先画当前实现实际执行的逐步公式，不用“数学等价”跳过浮点顺序。再为每个调用点列出：形参位置、实参变量、逻辑角色、dtype、地址/槽位、生产者、最后写入点和消费者。CopyOut 的源槽位必须单独列，不能假设它随 VF 输出角色自动变化。

遇到 VF 时先按当前版本 API 文档确认 SIMD、SIMT 或混合调用模型与执行域，再跨调用文件和定义文件完成账本。寄存器、mask 和标量实参在调用点可能缺少类型语义提示；编译成功只能证明语法和静态约束通过，不能证明实参顺序、读写方向、有效 lane、UB 接力槽位或 helper 执行域兼容。

## 乘除重结合的有限精度分叉

遇到 `a*(b/c)` 与 `(a*b)/c` 的改写时，把两条链分别按目标 dtype 展开，不能只写实数域等式：

```text
q   = round_D(b / c)
y_A = round_D(a * q)

p   = round_D(a * b)
y_B = round_D(p / c)
```

两条链的中间舍入、overflow、underflow 和非法运算位置不同；最终数值接近也不能证明位级约定相同。有限值的舍入差也可能超过较紧容差，是否失败要按实际比较器计算，不能只在逐位约定时检查。先冻结目标舍入模式、FTZ/subnormal 行为、是否融合以及 NaN 比较规则，再构造能让中间数值类别分叉的 trigger。以下是 IEEE binary32、逐操作 round-to-nearest-even 且保留 subnormal 时的通用区分输入；`Fmax=0x1.fffffep+127`，`minSub=0x1p-149`：

| 目标 | `(a,b,c)` | `a*(b/c)` | `(a*b)/c` |
|---|---|---|---|
| 中间乘法 overflow | `(Fmax, 2, 2)` | `Fmax` | `+Inf` |
| 中间除法 underflow | `(2^24, minSub, 2)` | `+0` | `2^-126` |
| overflow 后非法除法 | `(Fmax, 2, +Inf)` | `+0` | `NaN` |

平台若启用 FTZ、采用其它舍入模式或把表达式融合，以上具体位模式可能改变；此时用目标 dtype 的 `nextafter`/位模式扫描生成满足同一分叉谓词的输入，而不是照搬常量。逐步保存 `q/p/y` 的数值类别和 bit pattern；signed zero 与 NaN payload 是否参与 bitwise 验收由当前约定的特殊值相等关系决定，不能从 `bitwise` 标签自行推导。由运算产生的 NaN payload 若无项目 oracle 或版本来源约束，保持 `UNKNOWN`，只把数值类别作为当前实验结论。

有限/Inf 分叉也可能来自中间值的微小差异。以相同的 binary32 乘法为例，`2*(Fmax/2)` 为 `Fmax`，而 `2*nextafter(Fmax/2,+Inf)` 溢出；因此两个 Exp 实现即使都返回有限值，也可能经后续乘法形成类别差异。这里是算术示例，不预设某个设备 Exp 的误差。区分 Exp、乘除顺序和阈值分支时，核对实际分支及对应中间值；只看最终类别或阈值相关性不能把这些解释分成互斥项。

### 先核对参考的实际行为

任务已规定的 dtype 与求值顺序直接沿用。项目 golden 若调用框架 API，确认实际版本和 dtype，再从对应实现或小规模调用核对求值方式；若与明确要求不一致，记录需求与参考实现的冲突，不把明确要求改成另一种待选约定。数学文档写成乘某个比例，不足以证明内部先算该比例；自建的“稳定版 golden”也不能替代项目 reference。

区分输入应让两个候选给出不同的类别或数值预测，再配普通量级对照；仅在两条链都有限且接近的样本上回归，无法排除重结合问题。某个溢出 trigger 超出合法域，只排除了该输入作为失败证据，不能据此宣称其余域内安全；仍按当前疑点检查合法域内的有限舍入差或其它分叉。若 reference 允许中间溢出，有限结果不自动更符合验收要求；任务确实只规定高精度 reference 与容差时，按该要求判断，不强制复刻未被要求的中间顺序。一个实际漏查例见[Softplus 浮点语义支路](../cases/softplus-v2-grad-family.md#支路-c浮点语义而不是实数恒等式)。

## 分段与稳定公式的跨实现一致性

同一分段或稳定公式若由 SIMT、SIMD、RegBase 等并列实现，它们都应满足同一公式的定义；一条路径修复或通过不足以外推其它路径。分别审计各实现的分段谓词、常量、逐操作顺序与 dtype/舍入点，再按当前约定覆盖普通域、分段边界、深尾及适用的特殊值。没有 visible case 的实现仍须判断其是否可达；不可达或无法确认时保留 `UNVERIFIED`，不把某个后端的结果写成跨实现结论。

修改影响多条公式实现时，选择能暴露同类差异的输入检查相关路径。普通输入通过不能说明深尾、分段边界或特殊值也正确；按实际影响补充代表性对照。

若某条路径的公式修复后来因编译器、资源或回归问题被撤销、换写或改成路由替代，撤销前的验证不再证明最终实现。重新核对最终谓词和操作链，并把同一分段/深尾 trigger 回放到最终仍可达的每条实现；路由替代只证明该配置走向了合规实现，不证明被绕开的实现本身正确。

### 跨实现的小量放大对照

门控、sigmoid 或其他指数链在一条后端修好后，用同一数值条件核对另一条可达实现，而不是只搜索相同常量是否出现。先从实际 Host 条件确定各自的 shape/dtype/可选输入，再填写一张小表：

| 实现 | 实际触发条件与分派证据 | 相关数值链 | 当前结果 |
| --- | --- | --- | --- |
| 路径 A，如 SIMT | 从当前 tiling/dispatch 读取，运行时核对 | Exp、缩放、恢复与输出消费 | 已确认的输入与误差，或未验证 |
| 路径 B，如 RegBase | 独立核对，不由路径 A 推断 | 对应公式及各步 dtype/舍入 | 单独记录，不能沿用 A 的通过结果 |

例如只考察 FP32 子表达式 `y=a*sigmoid(g)`，在合法域允许时选 `g=-100、a=2^100`，并配普通量级 `g=-4`。若某条实现先将极小 sigmoid 因子归零，大系数相乘也无法恢复；更高精度数学结果仍非零。保存 `g`、因子、放大前后值，区分“产生时归零”与后续搬运/消费。这里不预设 Exp/FTZ 行为，也不将此子表达式替代整个 SwiGLU 梯度 oracle。

两条路径可能需要不同的合法 shape，无法在同一 shape 强制切换时，保留同一局部数值分布并说明布局/归约等差异。最终各自回到原分派、正式输出和比较器；临时强制后端只是一项诊断对照。小量的分阶段检查见[特殊值与窄带放大](special-values.md#次正规数与窄带放大)。

## 小量级输入与稳定公式边界

遇到 `log(1+x)` 等结构，记录实现真正执行的 `s = round_dtype(1+x)`、`y = log(s)`，不要用实数域等价式替代逐操作链。保存 `x`、`s`、`y` 的值与位模式；若 `x` 或 `s` 已在窄 dtype 中丢失信息，后续扩大 dtype 不能恢复。先用量级扫描定位首次分叉，再判断问题属于输入量化、加法吞没还是后续函数近似。

`log1p` 风格的稳定公式只有在算子 oracle、输入域和特殊值约定允许时才是候选。对照至少覆盖接近零的正负值、`+0/-0` 和普通量级输入；只有当前约定明确覆盖 `x=-1` 邻域时才测试该边界及两侧，否则将域外点记为 out-of-scope/UNKNOWN，不能用未定义输入裁决实现。比较中间位模式而不只看最终容差。具体 Log/稳定变体是否存在、支持哪些 dtype 与模式属于版本 API 强事实；应查询对应版本的官方文档，缺少权威证据时标为 UNKNOWN，而不是从旧案例或函数名推断。

## GMM shape、offset 与 per-token 参数槽位

第二组开始整体错位、某组输出像取了相邻组 weight，或每行误差倍率能匹配另一 token 的 scale 时查询本节。对每组把 `M_g/N_g/K_g` 的生产者、字段单位和消费者写入同一表；再分别列出 A/B/C、bias、channel scale、token scale 的 base/prefix/span。一个 `groupList` 值究竟是组大小还是累计边界必须由当前算子约定或实际 host 生产代码证明，不能仅凭变量名决定。

若当前约定是把各组 token 行连续拼接，并为每个逻辑 token 提供一个 scale，则候选索引应显式写成：

```text
token_base[g] = sum(M_h, h<g)
token_global(g, i) = token_base[g] + i
scale_used(g, i, j) = per_token_scale[token_global(g,i)] * channel_scale(g,j)
```

这是待验证的数据流公式，不是所有 GMM 的通用约定。固定 9.0.0 QuantGroupMatmul 样例确实使用累计 M offset 取得 per-token scale，当前 Matmul/Mmad 接口使用 `ascendc-api-knowledge-query` 核对；其它 GMM 若采用累计 groupList、per-group scale、per-block scale 或不同布局，应按其有依据的约定重建，缺证据保持 UNKNOWN。

验证时为不同 group/token/column 赋予互不相同且可精确表示的 scale 哨兵，令单位基 Matmul 只激活一个 `(g,i,j)`，同时保存读取的 token index、scale 位模式、workspace 值和最终倍率。依次测试首行、组内末行、下一组首行、空组之后首行和尾组末行。若错值稳定等于相邻 token 的预测倍率，支持索引候选；若 Cube/workspace 已错，则该实验不能归因于 scale。把 channel scale 与 token scale 同时改成 1 只是一项组合观察，不能区分两条索引链。

group shape、offset、scale 角色与量化 dtype 必须由当前算法和布局约定确定；scale 哨兵与局部 oracle 只用于区分候选，不能决定广播 API 或实现常量。

## 支持与反证

- 错值反解能稳定匹配“用了另一个操作数/常量/中间槽位”的预测，强烈支持参数约定候选。
- 只修正注释或变量名不改变输出，不能证明问题已修复；必须确认数据流和生成物变化。
- 形参与实参逐位一致时，转查公式顺序、初始化常量、分支谓词或上游值。
- 只在某个 tile 后出现旧槽位值时，同时检查 buffer 生命周期和跨 tile 状态。

## 区分实验

使用可区分的哨兵填充每个逻辑槽位，选择能让分支输出不同结果的最小输入。一次只交换一个实参、常量或 CopyOut 槽位，并预先计算预测输出；枚举所有调用点，包括 cast 与非 cast 路径。对公式顺序，在 CPU 上逐操作复现目标 dtype 和特殊值规则，不用高精度化简式代替。

对每轮 VF 另核对有效 lane、tail mask、寄存器是否由本轮写全，以及分支判据读取的是原始语义量还是已被 clamp、cast 或覆盖的中间值。启发式静态审计只能排序嫌疑，最终仍以数据流和区分实验为准。

## Clamp 与分支判据的数据流分叉

当分支几乎恒定、只有阈值附近失败，或日志显示进入分支前同一槽位已经被 clamp/cast 覆盖时，查询本节。把一个变量名拆成至少三个语义角色：原始输入 `x_raw`、用于安全或近似计算的 `x_eval`，以及分支谓词实际读取的 `x_pred`。分别记录它们的槽位、最后写者、dtype 和位模式；同名复用不能代替这张数据流表。

默认应保留原始语义量供约定定义的谓词读取。若实现先执行 `x_eval = clamp(x_raw, ...)`，又让后续谓词读取被覆盖的 `x_eval`，clamp 可能把原本位于阈值两侧的输入压到同一点，使条件恒真或恒假。但“分支必须读原始量”仍以算法 oracle 为前提：若公开语义明确规定对 clamp 后的量分支，则 `x_pred=x_eval` 可以正确；缺少该依据时将分支输入语义标为 `UNKNOWN`，不靠数值稳定性猜约定。

区分实验同时选择谓词两侧的 trigger/control，并先确认两个分支在这些点的预测输出确实不同；若两支因舍入、饱和或特殊值处理得到同一位模式，该输入只有 `NO_DISCRIMINATION`，即使运行通过也不能排除谓词错误。一次只改变 `x_pred` 的来源，保持 clamp、公式顺序、dtype 和 CopyOut 不变，再检查分支选择、首个分叉点和最终输出是否符合事前预测。

反例：极大输入下两条分支都舍入到同一有限值，用该点观察到“切换前后无差异”，不能反证分支读错。另一个反例是为避免函数域错误而由算法约定明确要求先 clamp 再判断；此时强制读取 `x_raw` 反而扩大了语义。正式修复应保留两个角色或使用不易混淆的槽位，不能只改变量名；案例中的 clamp 常量和触发阈值不作为通用事实。

## 修复与回归

修正受影响的调用点，清理诊断哨兵，让变量名和注释明确区分槽位角色。根据改动选择相关 dtype 路径、分支边界或 tile/writeback 用例；API 调用语法与参数支持仍查询官方文档。
