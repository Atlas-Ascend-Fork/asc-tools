# 同步诊断：保护区域、条件路径与缓冲回收

这组代码分析示例说明三类同步问题：保护区域混用、条件路径漏通知、缓冲回收过晚。用于选择排查方法，具体写法仍需按当前产品和工程验证。

## 什么时候借用这些案例

Set/Wait 看似配对，仍出现旧 tile、某个输出分支异常、条件卡死或多轮才失败时，先区分下面三条调查分叉。下面通过三种同步代码关系选择验证方法；它们用于提出待验证的候选，具体 event/flag 语义和修复效果须在当前版本、架构与工程中确认。

| 当前观察 | 可能原因 | 先检查什么 |
|---|---|---|
| 只在多输出并存时异常 | 同步对象绑定错区域；临时 buffer 覆盖；输出地址/索引错误 | 各输出的最后写者、首次读者、真实 region、event 方向和申请身份 |
| 特定条件或首尾轮卡住 | 发布路径被跳过；合法跨轮等待；参与核提前退出 | 初始化、条件成立/不成立、首尾轮各自的等待与发布路径 |
| 首轮正常、复用 slot 后异常 | 数据就绪等待缺失；回收等待太晚；bias/索引绑定错误 | 同一 slot 上上一轮最后一次读取与本轮首次重写的先后关系 |

区域账本和路径账本分别见 [Buffer 生命周期、绑定与别名](../mechanisms/buffer-lifetime-alias.md)、[多核分区、所有权与核间协同](../mechanisms/multicore-ownership.md)；依赖类型与 API 分流见 [流水同步与数据可见性](../mechanisms/pipeline-sync-visibility.md)。只展开与当前症状有关的分叉。

## A. 多条输出路径共用同步对象

修复前的 attention 输出使用 `stage2OutBuf`，LSE 输出使用 `commonTBuf`，两条路径共用 `mte3ToVId[0]`。LSE 的 `V_MTE3` Set/Wait 还引用这个按 `MTE3_V` 申请的变量。修复同时做了三件事：

1. attention 与 LSE 分别申请并使用各自的两个方向 event；
2. LSE 的 `V_MTE3` 使用对应方向申请的 `vToMte3LseOutId`；
3. LSE 改用独立 `lseBuf/lseUb`，离开通用临时区。

这支持同时检查“事件与数据路径的绑定”及“临时区复用”，不能把整份修复简化为改一个 event 名称。不同依赖类型下数字 ID 恰好相等也不自动是错误；核对的是申请类型、使用方向与生命周期。

当前任务可先为两个输出填出各自的 `(物理根/基址, offset, 有效范围, generation)`，再追到 event 的申请、初始化、发布、等待和复用点。区分实验可按证据选择：

- 只隔离一条输出的事件身份，保持数据区域与算法不变；若跨输出通知混用被消除而内容仍错，继续查临时区。
- 只隔离可疑临时区，保持事件关系不变；若错误随最后写者或槽位复用消失，支持覆盖候选，但需排除同时改变对齐或越界落点的混杂。
- 两条输出分别运行与同时运行，给输出使用不同哨兵模式；若异常完全不随二者交叠变化，降低事件共享候选的优先级，回查 producer 内容和输出地址。

若两项隔离都需要才能恢复，分别检查中间 region 和通知顺序，允许组合缺陷。没有完整读写上下文时，“共用 event”只能是候选；已串行、无重叠且生命周期闭合的共享不能仅因名称相同被判错。

## B. 装载可跳过，但后续仍需要发布

在 Conv3D 的条件装载路径中，装载操作可以被跳过，但协作方仍可能等待通知。

`ReduceKCloseL0PingPong`、`ReduceKOpenL0APingPong` 和 `ReduceKOpenL0BPingPong` 中，修复将 `DmaSyncSet` 或 group/weight 等 `*SyncSet` 从可跳过的 AL0/BL0 装载条件内部移到条件之后。装载分支不执行，不代表与它协作的后续搬运等待也被跳过。这是路径闭合问题，不能直接概括成“缺一条 barrier”。

在当前工程列出至少两条路径：装载条件成立；装载条件不成立。对每条路径记录：等待者是否仍可达、等待的 region/轮次/方向是什么、哪个步骤证明可发布，以及初始化或其它路径是否已提供对应通知。

- 若条件为假时等待仍发生，且找不到对应发布，支持条件遗漏；可只调整这条通知的条件或位置，再比较同一路径是否越过原等待点，保留条件成立路径作为 control。
- 若条件为假时生产、消费和等待都跳过，条件发布可能完全合法；不应机械地外移。
- 若等待依赖上一轮回收，先补首轮 seed、跨轮映射和尾轮收尾；不要把当前轮没有前置 Set 当成遗漏。

移动 Set 前还要确认它表达的就绪或释放条件已经满足，避免用过早通知把死锁改成读旧值。不能把这份实现中的 `*SyncSet` 调用位置当作其它版本、其它协作路径的 API 规则。

## C. 写入后再等回收，已无法保护这次重写

bias 缓冲复用时，应分别检查上一轮消费结束和本轮搬入完成的通知。以下只分析这条局部依赖；跨核、跨卡同步需要另外验证。

目标文件的修复把 `WaitFlag<V_MTE2>(eventUbBiasVMTE2List[ubListId])` 从下游位置移到 `copyGmToUbBias` 之前，并放入 `ptrBias != nullptr` 分支。写后仍发布 `MTE2_V`。结合初始化、消费者和 `ubListId` 轮转上下文，可以分出两条不同的依赖：

```text
上一轮 V 消费完 slot r → 回收通知 → 本轮 MTE2 可重写 slot r
本轮 MTE2 写完 slot r → 就绪通知 → 本轮 V 可读取 slot r
```

半精度/bfloat16 bias 在 Cast 后发布回收；另一条 dtype 路径在广播加法消费后发布回收，因此最后读者应按实际 dtype 展开。首轮由 `InitFlag` 提供初始可写通知；收尾函数等待各 slot 的回收。

当前工程若怀疑覆盖，可只把回收等待放到被保护的写入之前，记录复用 slot 的最后读者与新写者。预测是旧一轮消费不再读到新 bias，而 producer→consumer 就绪通知仍完整。若读写确无时间重叠，或错值仍精确等于另一个绑定的参数，降低回收候选，转查数据绑定与内容。

对照应包括有/无 bias、不同消费分支、一个 tile 与足以重复使用 slot 的多个 tile。无 bias 时不可凭空等待一个不会产生的消费通知；只有一轮不发生复用的通过，也不能证明回收关系正确。具体实现是否需要显式等待、是否已由 queue/框架保证，须按当前版本及代码路径核实。

## 防止误报的最小对照

以下索引与循环对照用于检验候选能否成立，不能单凭静态形态判定设备故障。

| 对照 | 正确的调查结论 |
|---|---|
| 同一个 index 变量后来从另一 loop index 重新赋值 | 分开追踪两次赋值；若两个 loop 值均为 1，仅凭重绑定不能证明运行地址不同 |
| 同一 buffer 根上写 `idx * TILE`，读 `(idx - 1) * TILE` | region 不同是地址线索；还需核对 generation、环形复用及真实 producer/consumer，不能只看根变量 |
| 多输出 bundle 使用不同 loop 派生地址，同步只使用其中一个 | 逐输出追踪；未展开完整 consumer/Wait 时，仅能产生错配候选 |
| 非负整型索引的 `idx & 3` 与 `idx % 4` | 该范围内可等价；文本不同不能作为错配证据，不能泛化到任意模数或负有符号索引 |
| 循环前 seed Set；每轮先 Wait、搬运后 Set；循环后 Wait | 可以消费上一轮通知并闭合收尾；首轮、每轮与尾轮均可达时，“Wait 在 Set 前”不是死锁证据 |

最后一例使用核内 `MTE3_MTE2` event；它不证明跨核通知的作用域或参与集合。宏、alias、类型转换、有效范围和循环边界无法展开时，保留 UNKNOWN 并补地址/轮次观察。静态 finding 可被证据否定，静态零告警也不能替代这些关系的验证。

## 回到当前任务验证

选择与候选有关的首轮、重复复用、尾轮、条件真/假、参与核与输出分支回归；保留原失败输入和重复运行。用最小依赖修复验证首个分叉是否消失，撤销诊断用全局停顿或临时隔离，再检查精度、挂起、资源回收和产物采用。若多项修改同时生效，分别保留中间证据，结论只覆盖实际执行的路径。
