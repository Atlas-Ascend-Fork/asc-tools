# GRU bias：参考归约次序、尾列与修复后的漏写

适合在“逐元素输出正常，bias 归约失败”“有限值指标正常，NaN/Inf 却失配”或“改归约后只剩规律性尾区错误”时阅读。p2 与 p3 的原始问题属于同一个归约顺序根因族；下文的计数副作用发生在另一次 Agent 修复中，不属于原始案例的第二个根因。

## 实际计算链与观察边界

ThnnFusedGruCellGrad 的输入为 `[B,H]` 的 grad_hy 和 `[B,5H]` 的 storage，后者包含 r、z、n、hx、hn。逐元素计算采用 FP32：

```text
gin = go*(1-z)*(1-n*n)
gig = go*(hx-n)*(1-z)*z
grg = gin*hn*(1-r)*r
ghn = gin*r
ig = concat(grg, gig, gin)
hg = concat(grg, gig, ghn)
```

输出 0/1/2 分别为按目标 dtype 输出的 ig、hg 和 `go*z`。启用 bias 时，输出 3/4 分别沿 batch 维对未收窄的 FP32 ig、hg 求和，完成后才转换到目标 dtype；关闭 bias 时为空输出。

因此输出 0–2 正常是优先调查 bias 支路的线索，不足以单独证明归约入口完全相同。特别是 FP16/BF16 输出，收窄会掩盖上游 FP32 差异；局部对照应检查未收窄值，而不是重新累加输出文件。

## 两种表象，共用一个原始根因

失败实现先做 chunk 内 `ReduceSum(RA)`，再做主尾配对和缓存树合并；group 路径还要经过 workspace partial 和第二阶段归约。参考代码则对连续 `(B,3H)` FP32 张量执行 CPU `sum(dim=0)`。双方参与元素相同，不保证中间舍入和溢出位置相同。

| 案例 | 主要现象 | 有区分力的观察 |
| --- | --- | --- |
| p2 | 普通有限 FP32 输入，4 行公开失败集中在两个 bias；接近零的结果容易放大相对误差 | 比较未收窄输入、参考次序模型和设备的分块树；只换 FP64 不能证明满足原 FP32 reference |
| p3 | 极值与低精度输入，bias 的 NaN/Inf 类别或位置失配 | 逐坐标分类，追踪首次溢出；公开 L0_030 的 bias 曾各有两个 NaN/-Inf 位置互换，有限值误差为零但没有可比较的有限元素 |

有限输入经过不同加法树，也可能分别得到 finite、Inf 或 NaN，机理见[顺序与溢出](../mechanisms/special-values.md#有限输入的归约顺序也会改变非有限类别)。两例历史原始输出在各自两次回放中稳定；这支持确定性数值路径调查，但不凭稳定性单独排除地址、状态或同步。

## 主列通过后，尾列仍可能采用另一棵树

p3 尾列细化时记录的参考环境为 PyTorch 2.9.0+cpu、AVX2、单线程；设备记录为 CANN 9.0.0、Ascend950PR_9589、dav-3510、Kernel 直调。该参考环境的向量外归约在 `floor(3H/32)*32` 之前使用主列 cascade，后续列使用四路交错 `row_sum`；32 来自该路径的四路调度和 8 个 FP32 lanes，不是 NPU 的通用对齐要求。

初版 p3 参考修复保留 batch 顺序并实现四层 cascade，公开集达到 595/595，但看护集仍为 17/20，剩余三行仅 input bias 的非有限类别失配。补齐尾列交错链、各链的 cascade、余数追加和最终合并次序后，历史记录为公开 595/595、看护 20/20。这个反例说明“用了四层 cascade”还不足以证明复现了整个 reference。

从失败输出列反推路径时，保留原矩阵宽度与 stride。GRU 的两个 bias 各自是 `[3H]`，六个内部 segment 的逻辑列为 `(segment % 3)*H + aOff + col`；不能把 hidden bias 当作一个宽度为 `6H` 的参考张量继续累计列号。抽出单列再调用框架 sum 也可能改变参考路径，具体对照见[分层归约与主尾列分派](../mechanisms/accumulation-order.md#框架参考的分层归约与主尾列分派)。

历史最终参考方案采用单行 R tile、关闭 group，并在设备端完成所需次序。这证明一种方案在记录范围内有效，不证明必须串行整个算子，也不提供性能合格结论。公开需求规定 FP32 归约和特殊值匹配，但未逐项写出该 CPU 结合树；固定 oracle 的实现依赖应由评测维护者确认，不能升级为 GRU 数学定义或自行修改测试的理由。

## 修复过程中的另一种机制：可变计数污染后续输出

另一次 p3 修复曾在 CPU 归约模型上通过大量非有限类别对照，设备端却出现新的整段漏写。`FinalBiasVfImpl` 在 input bias 尾段直接调用 `UpdateMask<float>(aLen)`，而后面的 hidden bias 段仍需要这个有效长度。该 API 消耗引用参数后，后续段看到的是零。

在公开 L1_455 的修复快照中，`H=1743`，最后一个列块为 `aOff=1728, aLen=15`，每块容量为 64。前两个 input bias 段正常；第三段跨过参考主尾边界，在生成尾 mask 时消耗了 aLen；随后的三个 hidden bias 段均跳过写出。因此预测漏写位置为：

```text
[1728,1743)  [3471,3486)  [5214,5229)
```

这三个半开区间共 45 个位置，与该次保存的设备失配索引逐个一致。原始版本在同一用例仅有另一个位置失配；修复后的错误分布已经改变，不能继续只拟合求和树。

同一候选的清零循环还在 `UpdateMask(remaining)` 后再次手工扣减一轮。按该快照的控制流和每轮 64 个 FP32 元素推算，3840 个缓存元素只覆盖了 1920 个；这是独立的初始化缺口，不能把它未经干预验证地称为全部 45 个错误的原因。

保留跨段不变的有效长度，各段使用独立 remaining，并核对清零和写出覆盖，见[可变计数机制](../mechanisms/tiling-tail-state.md#可变计数被消费后续输出漏写与清零不完整)。上述定位由候选源码、API 语义和已存设备日志支持；修正该 Agent 候选后的完整 NPU 回归未记录，不能称为该候选已修复通过。

## 怎样缩短下一次调查

1. 先按输出区分逐元素、归约和写回支路；保存一组可复验失败，不必等全套测试结束才分析已经取得的错误。
2. 从固定参考源码推导层级和主尾分派，用会区分候选的长度、列边界和有限/极值输入核对；避免将“16 行块顺序累加”外推到所有 B。
3. 将通过的局部算术模型落实到设备时，核对相同输入、层级更新、余数、初始化、可变计数和写出范围。若错误结构变化，先检查新增 diff。
4. 保存当前修改、实际通过范围与未决项，再运行必要回归；可复现挂起与数值超差分别报告，基线也挂起不证明候选已完整通过。

历史最终参考补丁的两轮结果为 p2 公开 28/28、看护 20/20，p3 公开 595/595、看护 20/20；相应原始版本分别为公开 24/28、592/595，看护均为 4/20。这些是固定环境的既有设备记录，不是本次知识整理重新运行的结果，也不能证明更新后的 Skill 成功率已提升。
