## 冻结失败现场

先保存能重放原失败的信息，已有可信记录直接引用；其余字段按当前疑点补充，缺项注明。

| 对象 | 需要保留什么 |
| --- | --- |
| 输入与属性 | 实际输入文件，或已确认可复验的生成器、参数和种子；shape/axis/dtype/layout、有效范围及相关属性 |
| 比较依据 | actual/golden、实际比较器和验收规则，逐输出及组合判定 |
| 源码与构建 | 源码版本、相关改动、实际参与的 Host/Kernel/tiling 源码、构建目标和产物位置 |
| 环境与路径 | 本次 CANN/编译器、设备、调用方式与实际分派；必要时补 driver/firmware、SoC/NPU Arch、tiling key、核数和关键宏 |
| 执行与观察 | 命令、工作目录、完整日志、退出状态、可获得的错值/位置/误差，以及输入输出文件的位置 |

调用方式与编程形态分别说明，例如 Kernel 直调不表示采用 RegBase 或 SIMT。仅连续调用才失败时，还要保留调用顺序和状态复用条件；同一随机种子不自动保证实际输入相同。

关键事实写入[任务报告](reporting.md)，新建日志、输入快照与观察结果放在[任务产物目录](reporting.md#任务产物目录)。保留原输入和验收方式，诊断插桩、探索输入及修改后验证分别标识；输入、有效区或判据变化时说明差异。

## 核对环境与实际产物

重编后结果不变、切换构建配置或怀疑加载旧产物时，按缺口沿下列链路检查：

| 环节 | 具体检查 |
| --- | --- |
| 源码 → 构建 | 核对本次构建目标、实际源码和编译选项，从构建日志找到生成的目标文件 |
| 构建 → 加载 | 沿运行命令、工程加载配置和可获得的加载记录确认目标路径，结合实际分派或可区分行为核对本次执行的 Kernel/分支 |
| 执行 → 输出 | 保存旧结果，使用新输出路径或确认工程已刷新输出，再核对比较器读取的是本轮对应文件 |

版本从本次实际使用的 CANN/编译器根目录取得，构建目标与运行设备分别记录。编译成功、文件摘要改变或输出时间较新，都不能单独证明新 Kernel 被执行。执行记录中的命令或文件身份也不能单独证明框架动态加载了某个 NPU Kernel。

### 排除旧构建、缓存与输出残留

先保留原始输入、失败输出和日志，再按工程配置确认构建目录、相关缓存及加载路径。优先用独立构建/输出目录对照；确需清理时，仅处理已确认、可重建且属于本次任务的缓存，不套用固定机器路径。重建后仍需核对实际加载和输出刷新，结果不变也可能是输入对改动不敏感。

怀疑进程持有旧模块或状态时，可用新进程对照；原问题依赖连续调用时，仍需保留原调用历史。清理或重启后通过不能代替原条件验证，相关线索见 [Host 属性与构建采用](../patterns/mechanisms/golden-host-contract.md)。设备 DCache 可见性另按[同步与可见性](../patterns/mechanisms/pipeline-sync-visibility.md)调查。

## 核对真实退出码

优先直接执行被测命令，每轮使用新日志路径，保留完整日志与真实退出状态。使用重定向保存日志时，在命令结束后立即保存退出码；返回 0 不等于精度通过，数值判定看本轮有效 evaluator。

确需管道时，`pipefail` 可防止前端失败被末端成功掩盖，但它返回最右侧非零状态，不代替各环节退出码。例如前端返回 7、日志端返回 3 时，管道返回 3。以下为 **Bash 外部命令**示例，在子 shell 内先关闭遇错即退，保证失败后仍能保存状态：

```bash
(
  set +e
  set -o pipefail
  <command> <arg> ... 2>&1 | tee "<artifact-dir>/pipeline.log"
  run_codes=( "$?" "${PIPESTATUS[@]}" )
  printf 'pipeline=%s command=%s tee=%s\n' "${run_codes[@]}"
  exit "${run_codes[0]}"
)
```

保存数组必须紧接管道，前面不要插入 `rc=$?`、日志展示或其他命令。Zsh 使用 `pipestatus`，保存语句为 `run_codes=( "$?" "${pipestatus[@]}" )`；默认数组从 1 开始，汇总状态取 `run_codes[1]`，不能照抄 Bash 下标。

嵌套脚本仍需核对内部退出状态是否被覆盖；外层调用不能恢复脚本已经丢失的失败状态。只有历史日志而无可靠退出状态时，保留执行结果未知，条件允许再回放，不凭日志中是否出现 `FAIL` 推断。

## 记录复现结果

分别说明本轮执行结果、数值判定与原问题是否复现，用简短记录即可：

| 当前观察 | 记录与下一步 |
| --- | --- |
| 在可比原条件下，有效比较再次观察到原精度失败 | 保留实际 FAIL，可记为 `REPRODUCED`，沿相关计算链继续定位 |
| 针对原失败的回放有效比较通过，未观察到原异常 | 保留实际 PASS；未修改基线的回放可记为 `NOT_REPRODUCED`，核对历史与当前条件差异 |
| 构建/执行失败、输出陈旧或没有有效比较 | 记录具体执行结果与缺口；未取得有效比较的部分保持未知，不记作数值 PASS 或已复现精度失败 |
| 当前无法重放，只能使用历史证据 | 可记为 `EVIDENCE_ONLY`，说明缺失材料或条件，继续有边界的源码或历史数据分析 |

例如：`本轮 evaluator 为 PASS；原问题本次未复现；缺少可比的修复前后证据，尚不能确认修复。` 有效的修改后 PASS 仍应如实报告；修复结论另按[原失败回放与必要回归](../../SKILL.md#阶段-5原失败回放与必要回归仅修复任务)核对，不能因一次通过就覆盖历史失败。

当前未复现时，先比较历史与当前的输入、源码/产物、环境、命令、调用历史、tiling/核数和验收器。缺失材料注明其影响，后续观察追加保留；插桩或其他诊断改动的结果不替代原程序基线。

## 判断稳定性

在同一输入、产物和比较口径下重复观察，记录本批有效轮数、通过/失败数，按疑点保留错误位置、误差与输出摘要；少量展示点不能代表完整错误位置集合。无效轮次另记，不混入通过/失败计数。分类只覆盖本批样本及实际观察字段，不自动证明输出逐位稳定、内部边界稳定或根因。

| 当前观察 | 下一步 |
| --- | --- |
| 相同位置持续失配 | 选已有代表性错值或坐标核对公式、索引和数据来源；阶段未知时按[观察点设计](checkpoint-design.md)补观察 |
| 错误位置随轮次变化 | 对齐执行实例与调用历史，比较变化范围，再调查初始化、所有权、覆盖或同步；不要求先找到共同正常区 |
| 位置相同而误差幅度变化 | 比较已记录数值、状态复用和运算顺序，不直接认定为低精度或随机噪声 |
| 有时失败、有时通过 | 保留两类样本和出现条件，按疑点交错未修改对照；暂时找不到稳定触发条件也可继续调查 |
| 全部失败但缺位置或误差信息 | 只说明本批全失败，按当前疑点补定位信息，不推定稳定失配 |
| 本批有效比较均通过 | 保留 PASS 和未复现范围；有历史失败时继续核对条件差异 |
| 存在执行、刷新或比较无效的轮次 | 先补具体缺口，保留其他有效观察，不用无效轮次推断稳定性 |

诊断采样前明确下一轮能区分什么；重复运行不再推进判断时，换观察点或验证具体候选。项目要求的重复验收另按原方案完成，无法完成就报告缺口；不能因分类不再变化提前结束，也不反复运行直到得到一次通过。改变 shape、核数、分片或调用顺序属于新的诊断对照，按[实验设计](hypothesis-experiment.md#实验设计)核对实际联动。

数值失败也可能按工程约定返回非零退出码，需要结合本轮有效验收报告与执行日志解释；不要把它与崩溃、超时或旧输出混为一类。随机语义输出按[随机输出验证](baseline.md#随机输出边际分布与序列义务分开验证)检查，不仅凭输出摘要变化判错。

## 探测失败不回退典型值

核数、容量、架构或执行形态不明时，保留查询入口、参数、退出码、原始返回值及本次 CANN 根目录，说明信息来自 Host、Kernel、构建配置还是设备运行端。产品/架构映射和资源含义调用 CANNBOT `npu-arch` 技能查询，具体 API 及失败返回语义调用 CANNBOT `ascendc-docs-search` 技能核对。

交叉验证按冲突或疑点选择，先确认两种入口是否观察同一对象。例如 Host 配置与 `GetBlockNum()` 可核对本次逻辑 block 数，不能由此推定设备物理核数；构建目标信息也不等于当前设备实测。已有适用的可靠来源时，不要求每个字段都做双入口核验。

无法确认的字段保留 `UNKNOWN`，不拿典型配置、示例数字或另一设备/安装的结果兜底。`0` 按具体 API 的已确认语义解释；语义未知时，不擅自当作真实容量或“不支持”。缺值影响当前判断时，补来源或改做不依赖该值的检查，不把猜测写入 tiling。

## 执行停滞与证据保存

命令超出本环境已观察到的合理耗时而无新结果时：

1. **确认卡在哪一段**：查看完整日志、最近进展和本次进程状态，区分未启动、构建、输入生成、设备执行与比较；无输出也可能只是日志缓冲。
2. **保留现场并决定是否停止**：保存已有日志。长任务独立后台运行，保存日志和退出状态；按工程已有方式设置合理的超时，结束后核对本次任务的进程是否已收尾。需要手动停止时，只处理确认属于本次任务的进程。
3. **确认上一轮状态再继续**：仍有本次任务的活动进程时先处理，避免与新一轮重叠。根据已知停滞环节调整下一次检查，不只是延长超时或重复整套运行；缩减样本时保留它与原触发条件的关系。

超时不等于数值失败；未取得有效比较的部分保持未知。下一实验的预算与停止条件见[假设与实验](hypothesis-experiment.md)，本轮结果与未完成范围按[报告指引](reporting.md)交付。
