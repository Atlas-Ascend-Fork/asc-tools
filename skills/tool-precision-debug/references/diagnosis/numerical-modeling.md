# 数值对照与设备探针

需要区分舍入、结合序、dtype 或设备数值行为等候选原因时使用。围绕原始 NPU 失败，选择局部数值对照或最小设备实验；已有可信输入输出和运行记录可直接复用。

## 选择对照路线

| 对照对象 | 主要用途 | 何时使用 |
| --- | --- | --- |
| 项目 reference / golden | 按项目验收标准判断输出是否符合预期 | 确认最终精度结果，或取得语义匹配的阶段参考 |
| 局部算术模型 | 用 NumPy、PyTorch 或手算等方式模拟相关公式，比较候选对同一输入的预测 | 候选有明确的数值差别，可以利用已有样本降低区分成本 |
| NPU 实际执行 | 观察目标设备上的失败、关键中间值及修改效果 | 确认实际路径、检验候选预测或验证修复 |

已有局部模型和可信 NPU 失败时，下一轮定位可以这样安排，已确认的条件直接复用：

1. 先核对实际输入、有效区、dtype/layout、执行分支和已确认的舍入点，沿用项目 golden 与原验收口径。确认模型与设备正在比较同一段计算，再解释差异。
2. 用模型提出可检验的预测；某个模型更接近 actual 只提高候选优先级。优先选择候选预测不同的少量 NPU 中间观察，必要时用未参与拟合的样本区分。
3. 用设备实际阶段输入做局部重放，区分传入偏差和本段尚未解释的差异。根据下面的结果解释决定调查本段、回查上游或补可比条件，不从最终误差大小直接跳到根因。
4. 先用适用文档或已有设备观察回答关键语义；仍无法确定且会影响定位选择时，再考虑最小 NPU 探针。得到支持的解释后回到原始 Kernel、失败输入和原验收口径验证。

缺少 Kernel 内部 Tensor 值时，按[观察点设计](checkpoint-design.md)选点，在对应位置调用 [DumpTensor](dumptensor.md) 输出所需数值；涉及内存、竞争或同步时查[msSanitizer 官方仓库](https://gitcode.com/Ascend/mssanitizer)。具体接口和示例调用 CANNBOT `ascendc-docs-search` 技能查询，目标架构能力调用 CANNBOT `npu-arch` 技能查询。

## 建立可比条件

参与本次对照的模型与设备执行应复用同一实际输入和属性。尤其核对目标 dtype 量化后的输入值、shape/axis、layout 映射、有效区，以及模型假设是否对应实际执行分支；用同一随机种子重新生成数据不自动保证输入相同。必要的运行身份核对见[复现性方法](reproducibility.md)。

**最终验收**：沿用项目 reference 和比较器，具体见[比较与验收](baseline.md)。局部模型用于解释差异，不替换验收 golden 来消除失败；项目允许高精度参考与低精度实现按容差比较时，不要求两者内部舍入过程相同。

**中间定位**：对齐观察点的公式、输入来源、dtype、量化位置、layout 和有效区，再按[准备局部对照](checkpoint-design.md#准备局部对照)选择参考。高精度整式的最终结果不能直接充当任一低精度中间张量的期望值；累计偏差参考与基于实际阶段输入的局部重放也不能混成同一条正常/异常边界。

构建失败、命令未启动或未采到所需输出，属于执行或观察缺口，不记作数值 PASS/FAIL。比较有效时保留实际判定；参考或采集语义不足时按 checkpoint 方法保留 `AMBIGUOUS`，补对照或继续不依赖该观察的分析。

## 局部算术模型

结合序、clamp、错误中间量或不同舍入点都能解释 actual，且局部模型能降低区分成本时，模拟相关的算术链。按实际竞争解释建立候选即可，不要求每次实现完整的“当前实现、候选修复、oracle”三套模型。

按已确认的中间 dtype、Cast、累加方式与舍入点建模。末尾一次 `astype` 不能代替实际存在的逐步缩窄；也不能机械地在源码每个运算符后加 Cast。例如目标若执行融合乘加，乘法后没有独立舍入步骤，是否发生融合仍需按本次 API、编译或设备证据确认。未知的舍入或求值方式可分别作为候选，NumPy/标准库行为不自动等于设备 API。

先选能区分候选的少量原失败样本和正常对照，保留输入、实际输出、候选预测及采用的比较方式。问题涉及舍入、精确编码或特殊值时再保留必要位模式，NaN/Inf/subnormal 与边界样本按当前疑点及项目输入范围选取，不要求每次覆盖所有类别。缺 golden 时仍可比较候选预测，但这不构成最终验收。

先用源码数据流排除不可能影响失败输出的候选，再选择预测差异最大的输入或观察点。模型与 actual 吻合只提高候选优先级；根据 actual 调整过的模型，要用未参与拟合的数据或独立观察再区分，不能把同一批拟合结果称为独立证明。参考实现也不应复用可能掩盖错误的 helper。

后续实验应检验事先给出的错值、位置或数值类别预测，并控制相关混杂因素。只有观察有效且能区分竞争解释时，才支持相应机制；仅误差下降、按预测方向变化，或多个候选都预测同样结果时，仍需保留未决解释，具体按[实验结果解释](hypothesis-experiment.md#解释结果)处理。

用设备实际阶段输入重放时，上游传入的偏差已经包含在输入中。按观察的实际含义继续：

| 观察 | 能支持什么、下一步做什么 |
| --- | --- |
| 某个候选吻合，其他候选不符 | 支持该候选在当前范围的预测，结合源码和未被排除的解释验证机制；候选模型不是验收 golden，吻合不直接证明本段正确或根因成立 |
| 所有候选仍有残差 | 先核对参考与采集是否可比，再调查本段计算、实际读取、状态或遗漏的语义；不能直接判为上游根因，也不能只凭残差认定某种设备语义 |
| 已确认语义的局部参考能解释实际输出 | 这只说明当前局部比较通过；需要判断输入偏差的传播时，还要比较参考对实际输入与可信参考输入的预测，不能仅凭局部吻合宣称误差来自上游 |

具体按[区分传播与新增偏差](progressive-error-analysis.md#区分传播与新增偏差)准备对象。局部重放能解释当前输出、输入偏差也能解释后续现象时，可回查上游差异来源；其他已有上游线索仍可独立核验。

## 最小 NPU 数值探针

目标版本的文档或源码不能回答关键设备行为、与当前观察冲突，或需要确认实际生成代码时，再考虑 NPU 最小探针。能由当前权威资料或已有可信观察回答的问题，直接复用，不重复搭建探针。

围绕一个待确认行为固定相关 API、模式、dtype 和编译条件，使用触发样本及普通对照；调查表示边界时，再加入边界前后相邻的可表示值。检查数值产生、搬运和消费分别发生在哪里，避免把搬运或解析差异归因于算术。需要解释位级行为时保留输入与输出位模式，并确认缩减后的探针实际走到了目标路径。

记录实际芯片、CANN、编译选项、API 模式、输入范围和观察结果；重复性有疑点时按[复现性方法](reproducibility.md#判断稳定性)处理。结果只覆盖实际执行的组合，不能外推其他架构、版本或模式。探针与被检验实现共享同一近似算法时，二者一致不能当作独立正确性证明。

用探针结果修正候选模型后，回到原始失败输入和实际 Kernel 验证。若与适用的官方资料冲突，保留对应文档、设备环境、调用条件和原始观察，先排查路径与解释差异，不直接改写任一方的结论。

## 改变 dtype 时核对哪些变化

“改成 FP32 就通过”可能同时涉及输入量化、中间算术、编译分派和 tiling 变化。这样的观察可以缩小候选，但不能仅凭最终 PASS/FAIL 将原因归为累加精度。按实际改动核对以下层面，复用已有记录即可：

| 层面 | 核对内容 | 存在变化时怎样继续 |
| --- | --- | --- |
| 数学目标 | 公式、shape/axis、有效元素、常量和 reference 定义 | 先确认仍在比较同一任务，明确同时改变的算法或参数 |
| 输入表示 | Host 原始值、各 dtype 量化后的值与 Kernel 入口值 | 区分输入已经变化和同一输入在计算中产生差异 |
| 实际计算路径 | 模板/重载、API 模式、中间 dtype、已确认的融合与舍入点 | 将实现路径差异列为候选，选择能区分它与输入量化的对照 |
| tiling 与执行范围 | tile/repeat、核数、尾块、对齐和实际参与集 | 核查分片与参与范围；无法单独控制时保留组合解释 |

需要单独调查运算中的 dtype 影响时，可选各 dtype 都能精确表示的公共输入；调查输入量化或表示边界时，则保留各自相关边界点。比较的是入口解码后的数学值，不要求不同 dtype 具有相同位模式。两类样本的用途不同，按本轮问题选择。

若相关条件已受控，首次差异随明确的 Cast 或累加点变化，可提高该数值路径候选；分派和 tiling 同时变化时，保留实验的有效观察，再选择能区分这些解释的输入或局部检查。只在某 dtype 上拟合 NPU 的局部模型也不是设备机制证明。

## 记录结果与收口

记录比较范围、采用的 reference 或模型假设、关键差异、支持的代码候选及尚未区分的原因，沿用已有输入、产物和运行证据。保存实际执行命令、日志与退出状态，新增模型、采集值与报告保存到[任务产物目录](reporting.md#任务产物目录)，不重复建立台账。

结果应落到实际路径上的代码、数据依赖或仍待确认的局部范围，模型与设备的差异、首次可见分叉都不能直接作为根因。依据观察与源码事实按[假设与实验](hypothesis-experiment.md)验证具体机制；修复任务按[主流程阶段 4—5](../../SKILL.md#六阶段调试流程)回放原始 NPU 失败并做相关回归。正式修复有意改变内部 dtype 或 tiling 时说明影响，保留原外部接口与验收要求。
