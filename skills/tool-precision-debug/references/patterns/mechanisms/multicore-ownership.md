# 多核分区、所有权与核间协同

单核正确而多核错误、错误集中在核边界、部分核空转或输出随核数变化时，先建立每核数据所有权，再讨论同步。多核问题至少分为区间重叠、区间遗漏、尾核长度、跨核依赖和归约合并；它们不能由一个全局 barrier 统一解释。

如果错误位置在不同运行间错位，同时表现为单核正常、多核异常，应同时查询重复运行稳定性与多核所有权；“运行间错位”和“单核多核差异”都只是路由信号，不能跳过地址集合与 happens-before 实验。

## 所有权账本

对每个 `blockIdx` 写出输入区间、输出区间、有效长度、尾块、读集合、写集合和跨核共享状态。验证所有合法输出元素恰好由合同要求的核写入：普通写通常要求不重叠且无遗漏；原子或归约写则需另列合并算子、初值和完成条件。核类型、配比与架构差异调用 CANNBOT `npu-arch` 技能查询，实际核数从运行端确认；启动和同步 API 的支持范围调用 CANNBOT `ascendc-docs-search` 技能核对。

把每核区间写成半开集合并检查三项：所有 required 输出的并集完整、普通写集合两两不交、每次读都落在当前核拥有或由明确跨核依赖发布的区域。只验证 `offset = blockIdx * length` 的一行公式不足以覆盖尾核、空核、二维 stride 和输入输出分区不同的情况。

## 从逻辑任务集合反推地址

分区不一定是连续区间。先编号全部逻辑任务，再从真实循环写出每核任务集合，最后把每个 task 映射到输入/输出地址。对于跨步（交错）分配，若启动核数为 `N`、任务数为 `T`，应直接枚举 `Tasks(c)={c+q*N | q>=0, c+q*N<T}`，而不是用一段连续 GM 区间近似。该公式仅适用于这种跨步分配；当前 Kernel 的任务集合应从实际循环、步长和退出条件推导。

对普通“一任务一 owner”路径验证：所有参与核任务集合的并集恰好等于 required tasks，任意两核的集合交集为空，每个 task 的 tail 有效长度正确。对归约或 scatter 等允许多个 contributor 的路径，改用带重数的参与清单，明确重复贡献是否属于数学合同；不能用集合去重掩盖重复 partial。

## GMM 的 group → block 所有权

当错误从某个 group 开始、空组会让后续块错位、最后一组只错尾块，或启动核数大于有效 GMM task 数时查询本节。先按当前 tiling 为每组列出 `TM_g=ceil(M_g/baseM)`、`TN_g=ceil(N_g/baseN)`，再构造诊断用 task prefix `Q_g=sum(TM_h*TN_h, h<g)`。flat task `t` 若落在 `[Q_g,Q_{g+1})`，才能继续反解该组的 `(mTile,nTile)`；实际 Kernel 若使用循环跨步、轮转余数或对角线顺序，必须从真实循环重建映射，不能强行套连续除法。

每个 `(g,mTile,nTile)` 写一行 ownership ledger：候选 block/core、A/B/C 物理区间、M/N 尾部有效量、workspace slot、producer epoch、consumer epoch 和最终 GM 写集合。验证 required task 恰好覆盖一次；若一个 tile 合法地由多个 K-block contributor 产生，则另列 K-block 参与清单与合并规则，不能把它误报为重复 owner。

边界用例至少包含：首组为空、中间组为空、末组为空；`M_g<baseM`、`N_g<baseN`；最后一组只产生一个 task；task 总数小于启动核数；task 总数刚好多 1。空组不产生输出 task 不代表其所有 tensor storage span 都为零；无任务核不得写伪结果或读取未发布 workspace，但它能否退出/是否仍需参与同步取决于当前 API 合同，缺证据时保持 UNKNOWN。

### Cube producer → Vector epilogue consumer

混合 AIC/AIV 路径必须把每个 workspace slot 当作带 epoch 的有界通道，而不是普通临时数组：

```text
AIC producer: 产生 (group,tile,epoch) → 写 slot → publish ready
AIV consumer: wait ready → 读同一有效区 → dequant/activation/Cast → 写 GM → publish released
AIC reuse:    wait released → 下一 epoch 才能覆盖 slot
```

逐槽验证 producer、consumer、逻辑 tile、有效 M/N、地址范围和 ready/released 次数一一对应。AIC 结果正确而 AIV 输入错误支持 workspace offset/epoch/发布候选；AIV 输入正确而最终输出错误则转查 epilogue 公式、scale 索引与 Cast。只增加 barrier 后“偶尔好了”不能证明所有权或同步公式；普通高层 Matmul 的对象生命周期也不能证明 GMM 的 workspace/跨核合同。

固定来源中的 QuantGroupMatmul 样例只说明其自身实现，当前 Matmul/Mmad 接口调用 CANNBOT `ascendc-docs-search` 技能核对；其它分核公式、空核同步参与集和 workspace slot 数量须按当前 Kernel 与 API 合同确认。

## 启动核、参与核与空核

分别记录启动核集合、实际有任务的参与核集合和必须到达协同点的同步参与集合。`task_count` 小于启动核数时，空核可能不产生 partial，但它能否提前返回、是否仍须到达某个全局同步点，取决于当前版本同步 API 和 Kernel 模型；没有权威版本证据时保持 UNKNOWN。审计每条 early-return 路径与同步点，既不能让无任务核伪造一个 partial，也不能让需要参与协同的核提前退出。

最终合并阶段不得仅按启动核数盲读 workspace。逐槽记录写者、有效标志、identity 初始化与最终消费者：参与核应恰好贡献合同要求的 partial；空槽应被明确排除，或证明每个被读取空槽的 identity 在精确 reducer、dtype 与特殊值合同下为中性。空任务不得进入 count 或 Mean 的除数。尾任务、break 条件和最后一轮中“部分核有任务、部分核为空”的场景必须单独覆盖。

### 沿可达路径核对发布、等待与轮次

对每个实际参与核和共享 slot/region，按执行路径列出：初始化发布、循环第 `i` 轮发布、第 `i` 轮消费、early return、`break`/`continue`，以及尾轮收尾的 Set/Wait。文本中的 Set/Wait 数量和出现顺序只用于定位。先区分通知表示“数据就绪”还是“消费完成、允许复用”，再检查每条**可达** Wait 是否有对应 region、依赖方向与轮次映射的可达 Set：就绪边应约束 producer 写与 consumer 读，回收边应约束上一轮消费与下一轮重写；首轮还可能由初始化通知启动。等待前后还要核对该核是否仍属于本次协同的参与集合。

合法跨轮 ping-pong 是必要反例：循环前的初始 Set 可以使首轮 Wait 消费“上一轮”通知；循环内 Wait 上一 generation 的回收通知后 Set 当前 generation 的回收通知，循环结束后再 Wait 尾轮。这个核内 event 示例说明文本不相邻也可能形成闭合依赖；跨核场景还须另查作用域和参与集合。未覆盖的条件分支、提前返回、首轮索引下溢或尾轮缺少收尾，都应通过路径展开和 generation 账本验证，而不是仅按关键词计数。

跨核 API 是否要求无任务核参与、一个具体 `SyncAll` 的参与集合，以及 Set/Wait 的精确作用域都属于当前版本契约。没有对应 API 证据时，把“空核可退出”或“所有启动核必须等待”等结论保留为 `UNKNOWN`。需要区分条件发布或复用回收问题时，按需参见 [同步诊断：保护区域、条件路径与缓冲回收](../cases/sync-dataflow-handshake.md)；本节不从案例外推具体 API 或参与核合同。

## 跨核通知与等待范围

- 消费者依赖其他核写入 GM 时，等待应覆盖所有实际贡献者和同一轮数据；先查漏核、重复贡献与提前退出，再调整通知。
- 等待只约束指定流水的形态下，随后标量操作未必一起等待。分别记录真正消费者与被阻塞的流水，调用 CANNBOT `ascendc-docs-search` 技能核对 CrossCoreWaitFlag 的产品和重载；插全局停顿后恢复只支持时序相关。
- 无界 tile 序号直接作为 flagId 时，检查实际编码是否与另一通道或保留资源碰撞。编码、次数、区域与轮次都要对应，不能只比较源码字面值。
- 通知计数范围不直接等于循环总轮次上限。若一次发布已被消费，资源可能再次使用；按当前事件规则检查未消费通知与首尾轮，不用总迭代数代替配对分析。
- 纯 Vector/Mix 或多流并发挂起时，列出实际参与核、可达退出和等待环。等待尚未获得执行资源的任务，可能形成调度上的循环依赖；调用 CANNBOT `ascendc-docs-search` 技能核对当前 SyncAll 的执行形态与调度条件。

## 跨卡通信的缓冲所有权

对 HCCL 集合通信或点对点交换，把 `(rank, core/block, round, buffer region)` 一起记录。主机通道建好、本 block 完成、所有生产者完成、远端可读，是不同条件。若 Kernel 下发后等待远端地址，检查各 rank 的建链与就绪次序；需要跨 rank 协调时按当前通信实现建立完成关系，不能用本地一个 block 的完成通知代替。

| 现象 | 优先检查 |
| --- | --- |
| recvBuf 偶发旧值或随轮次变化 | 所用接口的 Commit/Wait 是否覆盖本次读区间，读是否发生在完成之前 |
| 本卡分段一直是旧值 | 跳过本卡复制的配置是否与下游完整结果要求一致，本轮是否确实写过该段 |
| 通信数据整体错位 | dataType、元素数/字节数、count/repeat/strideCount 与物理布局是否一致 |
| 多轮切分只有部分分段更新 | 每轮收发地址递推和有效数是否属于同一轮，缓冲是否提前复用 |
| 远端收到通知仍读到旧值 | 通知是否覆盖全部实际生产者，接收端是否过早消费 |

跨卡路径中，Prepare、Commit 与 Wait 各自的职责按所用对象协议确认，下发不等于完成。启用 SetSkipLocalRankCopy 时还要核对本 rank 数据段由谁写入、是否会被消费以及产品支持；只改变该设置的对照必须保持缓冲容量、传输计数和参与 rank 一致。

Device 通信的接口支持与提交/等待语义调用 CANNBOT `ascendc-docs-search` 技能核对，Host 上下文另见[通信上下文的身份与生命周期](golden-host-contract.md#通信上下文的身份与生命周期)。Hcomm/URMA 的 Drain、通知和工作区含义需按实际实现确认；这里只使用读写与完成关系排查，不假定统一的容量、原子类型或等待范围。

## 支持与反证

- 错误索引与核区间端点一致，或地址集合能证明重叠/遗漏，支持所有权候选。
- `blockDim=1` 改善只说明并发或分区相关，不能区分重叠、同步和每核状态初始化。
- 单核仍在第二行或第二 tile 出错，优先检查跨 tile 状态，而不是继续归因于核间竞态。
- 结合[msSanitizer](https://gitcode.com/Ascend/mssanitizer)的读写或同步告警核对相关指令和核，不直接据此证明逻辑所有权公式。

## 区分实验

使用相同输入比较 1、2、典型核数和尾核场景；为每核输出增加诊断标签或保存区间元数据，确认修改真正采用。对跨核 A 写 B 读，分别验证地址所有权和 happens-before；只增加一种最小协同，并预先声明应消失的边界。对归约同时检查合并顺序是否改变数值误差。

多核对照还要区分“并发消失”和“每核工作量改变”：`blockDim=1` 会同时改变分片、尾块、循环次数和归约顺序。优先构造保持每核语义可比的 1→2→N 对照，并记录各核的实际 ownership ledger。

因此，单核通过不是“已证明核间同步缺失”，单核失败也不是“已证明与多核无关”。单核会把原本分散的任务串到一个核上，可能消除地址竞争，却增加同核循环次数并暴露旧 tile/旧 buffer；还会改变 partial 数量与归约树。把 `blockDim=1` 只作为混杂较多的反事实：同时比较实际任务集合、每任务地址、循环 epoch 和合并顺序。若条件允许，再设计一个保持任务内容不变、只改变 ownership 或共享写入的对照，其因果信息量高于直接比较最终输出。

## 归约中的两层顺序

先区分跨核 ownership 与单核内部归约分组。即使 `blockDim=1`，向量 repeat 内仍可能采用分组或二叉树累加；这属于 [累加、归约顺序与消减](accumulation-order.md)，不是多核竞态。反过来，多核每核各自产生正确 partial sum，也不能证明最终参与集合、workspace 槽位、发布时序和跨核合并顺序正确。

对“多行、每行独立归约”先写出每个输出行的唯一 owner，再写每个 owner 内的有效元素集合和归约顺序。只有错误随 blockDim、核边界或读写集合改变时才提高本页优先级；单核仍稳定失配时应继续比较元素集合、dtype、API 重载和 repeat 层级，而不是用“已经单核”排除所有顺序问题。

Batch MatMul 可按两级边界检查：先核对实际启动核与 tiling 参与核，排除无 ownership 的核；再检查参与核的 GM 半开区间及尾部归属；核内继续按 UB 可承载行数核对完整迭代与 tail。各级分片和尾部处理规则都须从当前实现确认。

自然症状“最后一核错”“增加核数后相邻区间被覆盖”应触发四项对照：多余核是否早退、start 是否已超有效区、尾核长度是否由总长减 start 得到、核内 tail 是否仍错误使用完整块长度。使用区间并集和交集验证，而不是只比较最终输出；dtype 或 buffer 数改变后还要重新计算 UB 二级分块。

## 修复与回归

修正区间公式、尾核长度或已确认的依赖，不以降低核数作为正式修复。回归覆盖元素数小于核数、整除、余 1、最大尾部、不同 blockDim、原子/非原子路径和强消减数据；同步、Cache 和原子语义必须按当前 CANN/平台说明核实。

## 事实边界

核数、同步参与规则、地址对齐、原子支持和具体 API 行为必须查询当前版本 官方 API 文档及本地平台说明，缺少权威证据时保持 `UNKNOWN`。
