# Golden、Host 属性与构建采用

精度调试首先验证比较双方是否描述同一个合同。冻结输入字节、shape/layout、dtype、属性、数学公式、特殊值规则、有效区和容差；golden 生成脚本、随机种子及依赖版本也属于证据。

归约还要记录实际参考路径：框架默认 `sum`、pairwise/tree、按 repeat 分组和显式逐元素循环即使作用于同一集合，也可能产生不同浮点结果。`sequential` 需要说明累加 dtype、索引顺序和中间舍入位置；记录这些用于复现与解释，不自动给所有算子增加内部树必须相同的要求。

框架 reference 对 shape、stride、CPU SIMD 或线程分派敏感时，仅固定 Python 脚本和 dtype 不够。原矩阵求和后取列，与先抽取该列再求和，可能走不同结合树；应保留原布局或用已核对的逐操作模型建立局部对照。具体例子与适用边界见[框架参考的分层归约](accumulation-order.md#框架参考的分层归约与主尾列分派)。需求未规定结合树却观察到 oracle 对其敏感时，如实记录需求与实现的差异，不自行放宽原 evaluator。

## 比较模型随输出语义选择

当用户问“该用哪种误差标准”时，先查输出承担的公开语义，再查 dtype。非计算搬运或索引通常先验证坐标和值是否保持；整数算术通常先查精确数值与溢出合同；浮点计算需要冻结公式、逐步 dtype、求值顺序和项目阈值；量化路径还要冻结 scale、zero-point、舍入、饱和、量化轴及最终输出类型；随机输出则先查分布和重复性合同。它们是不同 evaluator 家族，不能互换。

判定比较模型是否可用时，至少回答四个问题：它来自哪项项目义务；它是否覆盖当前输出的有效区和特殊值；故意破坏该义务时 evaluator 是否会失败；阈值是否在看见本次结果前已经确定。任一项未知，模型只可用于探索，不能支撑最终 PASS。高精度 reference、位级比较或统计检验本身都没有天然更高的证据等级，关键是它是否忠实于当前公开合同。

## 三个常见伪差异

- Golden 忠实度：参考实现使用不同公式、累加 dtype、归约顺序或边界语义。
- Host 合同：属性未进入 tiling/cache key，旧 tiling 或旧二进制被复用。
- 构建采用：修改了未参与构建的文件、产物未更新或运行加载了另一目录下的二进制。

## Oracle 来源、降级与独立性

没有可直接使用的项目 golden，或需要为中间 checkpoint 构造局部 oracle 时，按证据目的逐级寻找：

1. 项目验收明确指定的 reference 与 evaluator；它定义最终通过口径。
2. 与目标实现独立、语义相同的现成实现或可证明数学性质；先核对公式、边界与 dtype。
3. 由较小基本算子组合出的 reference；逐步保留量化、Cast、layout、有效区和求值顺序。
4. 自建 CPU 算术链、不变量或手算小例；适合筛选候选和局部边界，除非另有合同依据，否则不自动升级为最终验收 oracle。

“降级”表示可用证据范围变窄，不表示后一个来源必然数值更差。每次降级都记录共享依赖：若 golden 和 kernel 复用了同一个索引公式、常量表、生成器或 helper，两者一致可能只是共同错误。用手算小例、第二个独立实现、守恒/对称等性质和故意违反义务的敏感性反测来校准。高精度整式只证明数学参考；若目标合同包含逐步低精度舍入、特殊值或固定顺序，它不能直接判定每个实现 checkpoint。算子 reference 的通用降级分层与无 golden 时的独立依据见[算子建模](../../diagnosis/operator-modeling.md)与[Checkpoint 设计](../../diagnosis/checkpoint-design.md)；本节保留该阶梯在 golden/Host 合同场景的应用。

## 稳定式与逐步 oracle

稳定重写或移位指数在实数域可以等价，却未必与合同的有限精度求值链等价。构造 oracle 时保留实际的中间 dtype、Cast 和舍入点；例如实现按“移位 → 指数 → 缩放”执行，就分别记录每一步的量化结果，而不以未舍入的理想移位指数值直接替代。再用能使中间类别、舍入格点或最终输出分叉的输入比较原链、重写链与项目 oracle。

高精度表达式适合说明数学目标，但不能自动裁决逐步低精度合同。若项目 golden 已定义该顺序，先复用它；若没有，局部逐步 oracle 只能支撑候选和实验，最终验收仍需回到项目比较模型。

## 派生 probe 的输入保真

为解释疑点而自建 CPU/probe 时，优先复用正式 materializer、dtype 量化、序列化和 oracle；先证明 probe 与正式 harness 在同一输入上使用相同字节/位模式、有效区和比较口径。没有复用输入链的手工脚本只能作为探索证据，不能单独推翻 Kernel 或 golden；若两者不一致，先定位输入、量化、layout 或 evaluator 的分叉，再解释计算结果。

## Host 属性、缓存身份和采用的四向实验

当错误依赖同一进程中的调用历史，尤其是同 shape、同输入但不同标量属性的第二次调用像第一次时，先做四向实验，不先修改 Kernel：

| 实验 | 固定项 | 主要回答的问题 |
|---|---|---|
| 新进程单独执行 A；另一个新进程单独执行 B | 输入、shape、环境和产物 | 单次属性传递及 Kernel 路径是否本来就错误 |
| 新进程执行 A→B | 同上，仅改变调用顺序 | B 是否受到首次 A 的历史影响 |
| 新进程执行 B→A | 同上 | 历史影响能否随首次属性反转 |
| 在第二次调用只改变 shape | 属性 A/B 和公共输入语义 | shape 是否改变缓存身份、分支或 tiling；这是对照，不是单独结论 |

每次保存 Host 实参、实际进入 tiling/Kernel 的属性、tiling key、kernel 符号、blockDim、二进制身份和 fresh 输出。若 A→B 的第二次像 A、B→A 的第二次像 B，而新进程单独 A/B 都正确，支持“首次调用状态污染后续调用”的缓存身份候选；若新进程第一次就错，优先查属性传递、tiling 或 Kernel；若属性已经到达但分支未随之变化，转查动态分派；若行为只随重建产物变化且不随顺序反转，转查构建采用。

换 shape 后恢复不能单独证明缓存键遗漏，因为 shape 还可能改变 kernel、tiling、核数和 tail。四向实验只收窄候选，最终仍要定位实际声明或数据流，并证明修正后的属性身份进入真实运行路径。不要把清空宽泛用户缓存目录作为默认实验；先识别项目内真实产物、缓存对象和加载路径。固定阈值、框架专名或缓存实现断言不作为通用合同；历史材料一律不作为 API 强事实来源。

## 通信上下文的身份与生命周期

通信配置中出现确定性或缓冲字段，不证明当前初始化和真实路径已采用它。Host 的 internal 头文件只提供声明线索，不能当作公开支持矩阵，也不能用新版声明补齐旧版的 Host 接口规则；分别核对实际链接版本、初始化和运行状态。

跨卡直调中，同一缓冲或上下文被不同通信域意外复用，会表现为内容互相覆盖、建链异常或释放阶段崩溃。核对 HcclChannelAcquire 与 HcclEngineCtx 的 engine、ctxTag、通信域及实际初始化是否对应；描述符先按当前接口初始化，再填写并检查真正下发的字段。配置数字和标签限制调用 CANNBOT `ascendc-docs-search` 技能查 Host 通信原文，不跨版本照搬枚举。

释放时区分用户申请的内存与库管理的内置缓冲、引擎上下文；按当前组件的生命周期结束通信域，再处理设备重置，不能把库内存当作用户 aclrtMalloc 内存直接释放。若只在第二次建链或先后运行两个通信域时失败，沿上面的 A→B/B→A 方法比较对象身份与残留状态。

通信域级与进程级确定性配置应和链接版本、执行形态一起记录。只看到字段被设置，不代表实际通信路径已经采用它；数值顺序的对照见[跨卡归约](../operators/reduction.md#跨卡归约对照)，通道就绪和远端完成见[通信缓冲所有权](multicore-ownership.md#跨卡通信的缓冲所有权)。

## 验证方法

先用小输入手算或第二个独立 oracle 交叉验证 golden，再保存产物哈希、构建日志和加载路径。对影响 Kernel 语义的每个 Host 属性做成对实验，确认 tiling 字段和产物随属性变化。仅当相同输入与合同下 actual 首次分叉，才进入设备侧机制定位。

Golden-only 自比较只验证 golden 生成链自身的一致性，不能替代 actual-vs-golden。用例清单中的 required、optional 或 invalid 标签也不能代替执行事实：只有对应 shape/dtype/输入实际物化、进入目标入口并按冻结 return-code/evaluator 记录后，才计入该类覆盖。

Oracle 需要逐层忠实于当前验收：数学公式、求值顺序、中间 dtype、特殊值、padding 有效区和输出 Cast 都应可追溯。高精度解析解、框架表达式和逐操作硬件模型用途不同；来源名称不能替代实际行为验证。对极值域或分支边界，使用第二个独立实现或逐点实验交叉检查。

先按算子公开合同选择验收模型，再冻结 evaluator 实现和阈值来源。整数精确比较、浮点容差、量化误差、随机分布检验和非计算类位级一致不是可互换模板；若项目合同未说明，保持 `UNKNOWN` 并补充独立依据，不能从 dtype 名称推导固定行业阈值。特殊值是否相等也必须由同一 evaluator 明确定义。

放宽容差、重新生成 golden 或清空缓存只能作为诊断动作；除非新合同有独立依据，否则不能把失败改写成通过。修复与回归按[工作流阶段 4—5](../../../SKILL.md#六阶段调试流程)推进。
