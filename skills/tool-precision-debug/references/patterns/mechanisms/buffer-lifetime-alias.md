# Buffer 生命周期、绑定与别名

当某个中间量稳定等于另一个张量、跨 tile 继承旧值或修改 buffer 数量后现象变化时，分别检查物理内存所有权、逻辑 Tensor 绑定、生命周期和流水依赖。相同地址不必然是错误，错误绑定也不必然越界。

## 所有权账本

为每个 TBuf/TQue/LocalTensor 记录分配字节数、获取 offset、元素 dtype、有效区、生产者、消费者、首次写、最后读和释放/复用点。对 ReinterpretCast、切片和偏移 Tensor 记录共享的物理基址，不能把类型不同误写成独立分配。

再按当前版本 API 的真实单位计算每次读写的字节区间，分别标出 logical valid、padding 和 allocation capacity。独立 buffer 对照若同时改变 OOB 落点、alignment 或有效 lane，只能记为混杂实验，不能把结果单独归因于 alias 或生命周期。

同时建立“逻辑角色—物理槽位”表：变量名、预加载目标、VF 实参位置、VF 写回槽位和 CopyOut 源槽位必须能够串成同一条数据流。输出恰好等于某个中间量时，先用错值反解核对槽位；源码注释与实际 producer 冲突时，以地址和值证据为准。

### TPosition 是逻辑位置

Ascend C 用 `TPosition` 表达张量的逻辑用途，再映射到物理存储。常用映射如下，依据 CANN 9.0.0 的通用说明；带产品条件的位置继续按原文解释。[TPosition 定义][buffer-source-5]、[逻辑位置与物理存储映射][buffer-source-11]

| 逻辑位置 | 对应物理存储 | 语义 |
| --- | --- | --- |
| `VECIN` / `VECCALC` / `VECOUT` | UB | 矢量输入、临时计算和输出；三种名字不代表三块独立硬件存储 |
| `A1` / `B1` | L1 | 左、右矩阵的数据分块 |
| `A2` / `B2` | L0A / L0B | 送入 Cube 的左、右矩阵分块 |
| `CO1` | L0C | Cube 输出和累加结果 |

例如，输入队列和输出队列都可能占用 UB，但具体缓冲区是否重叠由分配和复用方式决定。`LocalTensor` 的逻辑位置也不能单独说明 layout、dtype 或当前内容是否就绪。需要确认分配与队列用法时，调用 CANNBOT `ascendc-docs-search` 技能查当前 Buffer、Tensor 与队列接口。

### region 身份不由变量名决定

把同步和生命周期账本中的对象写成 `(物理根/基址, offset, 有效范围, generation)`，而不是只写 buffer 变量名或 index 文本。下列情况需要得到不同的审计结论：

- 同名 index 在后续分支或流水重新赋值后，可能已选择另一个物理 slot；应分别记录重绑定前后的值域。
- 同一根 buffer 即使 index 名称相同，写入与读取的 offset 或有效范围不同，也应视为不同 region；要展开本轮的地址范围再核对。
- 不同表达式不能直接判为不同 region。只有在当前 dtype、符号和循环取值域下证明映射相同，或运行时地址观测一致，才可合并；例如非负整型范围内 `idx & 3` 与 `idx % 4` 可指向同一模 4 region。

复合 alias、宏展开、指针转换或无法取得实际循环范围时，既不能断言同一 region，也不能断言错配，应标为 `UNKNOWN` 并补充基址、offset、有效范围和 epoch 探针。该约束能避免把“同步已配对”误解为 “当前消费者读取的区域已准备好”。

## VF 跨文件端到端账本

遇到无类型区分力的 VF 裸指针时，不在调用点或定义点单独停下。对每条 dtype/分支路径分别追踪：

```text
调用实参位置/物理地址
  -> VF 形参位置/语义角色/读写方向
  -> 进入的 UB 槽位
  -> 本次调用后的最后写者
  -> 下一 VF 或 Cast 的读取槽位
  -> CopyOut 的最终源槽位
```

表中至少记录 `R/W/RW`、进入前 producer、退出后 last-writer 和最终消费者。类型相同只能说明调用可编译，变量名相似也不能证明按位置绑定正确；某个 LocalTensor 名称保持不变时，其物理槽位仍可能已被另一 VF、Cast 或复用写覆盖。FP32 与 FP16/BF16 若走不同 Cast 或 CopyOut 路径，应拆成独立账本，不能用一条已闭合路径代替其他 dtype。

### 用数值指纹反解槽位

为候选输入和中间槽位选择符号、数量级或位模式明显不同的探针值，先计算“若实参交换”“若搬出中间槽”“若读取旧 tile”各自应得到的输出，再比较 actual 与候选值的类别、位模式和逐元素关系。actual 稳定逐位等于某个中间量，比“误差很大”更能支持错槽位候选；只在容差内接近则仍可能来自舍入或公式近似。若候选槽位在所选输入上数值相同，该实验没有区分力，应更换输入而不是报告反证。

### 静态 `0 finding` 的边界

静态审计未报告问题，只能说明当前规则对当前输入文件没有命中。调用与 VF 定义未同时提供、宏或模板展开不可见、alias/offset 过于复杂、名称 token 缺少语义，都会留下漏报面。因此 `0 finding` 不能证明实参顺序、读写方向、last-writer、有效 lane 或 CopyOut 源正确；发现 VF 后仍须完成人工账本。反过来，静态 finding 也只是候选，必须用可区分输入和单变量修改确认，不能直接写成根因。

#### 跨文件 VF 的漏报审计

当编译通过、全域稳定错值像参数置换或错误 CopyOut，但只对入口文件运行静态审计得到 `0 finding` 时，查询本节。先确认审计输入是否同时覆盖调用点、VF 定义、本地 include、目标 dtype/宏分支和实际生成源码；再检查工具是否能解析当前位置参数、模板展开、alias/offset、last-writer 与最终搬出槽。“加载了多个文件”也不等于这些语义均被追踪。

人工账本至少选一条实际执行路径，从调用实参地址一直连到最终 CopyOut；对另一个 dtype 或 Cast 路径建立独立 control。随后用可区分哨兵让各槽位位模式不同，一次只交换一个实参或搬出源，并预先计算 actual 应匹配哪个指纹。若修改后的目标产物按预测改变，才支持错位/错槽候选；工具后来出现 finding 仍只是附加线索。

无法获得展开后源码、实际分支或产物采用证据时，把静态覆盖范围和结论写成 `UNKNOWN`。反例：仅把调用文件交给工具时为零命中，加入 VF 定义后出现候选，这不表示前一次证明源码正确，也不表示工具对所有跨文件调用都无效；它只暴露了那次输入和规则的覆盖边界。宏生成的调用即使文件齐全仍可能漏报，因此不能把“零告警”当成阴性实验。

## 时间维度：生命周期与旧 tile

把“绑定了错误槽位”和“同一槽位在错误时间被读取”分开。为每次写入附加 `epoch=(row, tile, stage)`，再核对消费者读取的 epoch 是否属于当前轮。第一行正常、后续行的 tile 0 像上一行最后一个 tile，支持参数未刷新或状态沿用候选；所有 row 都稳定等于另一中间量，则优先检查语义绑定和 VF/CopyOut 接力。两种机制可以同时存在，先修全域错槽位后可能才显出旧 tile 边界。

用每轮不同哨兵能确认读取的是哪个 epoch；哨兵必须进入真实 producer 路径，不能只改未被当前分支消费的临时变量。`blockDim=1` 仍可能让一个核处理多行和多 tile，因此单核失败不排除生命周期或旧状态，只削弱纯核间竞争解释。

当同一 slot 的旧 generation 与发布/回收路径同时可疑时，按需查看 [同步诊断：保护区域、条件路径与缓冲回收](../cases/sync-dataflow-handshake.md)；先分开验证 region、路径闭合和最后消费者，不把生命周期现象直接归为一条同步 API。

### Queue/Double Buffer 的槽位时间线

当实现使用 TQue 或 Double Buffer 时，不能把变量名、Queue `depth` 和物理实例数视为同一个量。先从当前版本 API 页取得 `depth`、`InitBuffer(num)`、EnQue/DeQue/FreeTensor 的强事实，再为每个实际 slot 建立状态账本：

```text
epoch i: FREE -> Alloc -> producer写 -> EnQue -> DeQue -> consumer最后读 -> Free
epoch i+1: 只允许在另一个空闲slot上重叠，或在slot i完成回收后复用
```

账本至少记录 `(row,tile,stage)`、LocalTensor 基址、Queue/slot、producer 完成证据、交接点、最后 consumer 和 Free 点。Double Buffer 的价值来自相邻 epoch 可在不同实例上流水重叠；它不允许 producer 覆盖仍由上一 epoch 消费的同一物理区。提前 Free、漏 Free、EnQue/DeQue 交接了不同地址，或下一轮 Alloc 比最后消费更早，均是可证伪候选，不因输出稳定而自动排除。

验证时分别做两种单变量 control：一是固定 tile/shape 仅把 `num=2` 改为 `num=1`，记录实际实例与事件时间线如何改变；二是保持实例数，仅延后目标 Tensor 的 Free 或增加 checkpoint，验证最早分叉是否按预测移动。前者同时改变并行调度，单独通过只能支持“slot/时序相关”；后者若 checkpoint 本身改变调度也仍是混杂证据。拿不到实际 slot 地址、生成同步或最后消费者时，结论写 UNKNOWN。

资源预算继续使用两本账：`InitBuffer` 等真实分配形成的**保留占用**，以及各 epoch/alias 的 **并存数据峰值**。队列 `depth` 不能直接乘进物理保留占用；只有 `InitBuffer(num)`、静态分配或真实地址证据才能确定物理实例数。反过来，两个实例已保留也不表示数据生命周期必然同时活跃。

## 资源申请与共享容量

| 现象 | 需要展开的关系 |
| --- | --- |
| 前几轮正常，后续申请失败或读到旧值 | 本轮是否归还了前一轮占用的槽位；Alloc/EnQue/DeQue/Free 是否交接同一区域；新分配区是否已写满有效输入 |
| 只在后续 stage 或非零偏移出现 NaN/Inf | 各 stage 对同一 slot 的元素数、字节数和对齐后跨度是否一致；首槽 offset 为零可能掩盖大小错配 |
| 混用多个队列与手动事件后异常 | 分别记录队列和 TPipe 事件的申请、释放及同时存活数量，再查当前资源限制；不能先假定统一池或统一上限 |

实际分配的补齐、偏移、队列 depth、绑定和支持通路调用 CANNBOT `ascendc-docs-search` 技能查所用 Buffer 接口。未写满的输入应补齐有效写入；归约临时区的初值由具体操作决定，不能一律清零。

### 系统与用户 workspace 的分区

直调与框架入口的初始化责任可能不同。使用 Matmul 等高阶接口时，分别列出系统区、用户区的容量和半开地址范围，核对传给 Kernel 的指针如何到达实际读写点；把整个 workspace 头指针当用户区，会与系统状态重叠。概念边界见[Host 资源口径](tiling-tail-state.md#查询容量时区分阶段与用途)；所需初始化、取址和编译选项调用 CANNBOT `ascendc-docs-search` 技能查当前调用，不能假定直调自动完成框架步骤。

容量足够也不保证复用安全；给各区写入不同的合法诊断标记，追踪首次覆盖发生在哪个调用。跨 stage 的字节常量应来自同一布局推导，修复时同步更新全部分支和消费者。

## 最小实验

1. 输出实际基址、offset 和 buffer 标识，确认源码符号与物理存储的对应关系。
2. 只将一个可疑中间量换到独立临时区（独立 buffer）；预测若别名是原因，最早分叉点应随之移动或消失。
3. 对多 tile 循环在每轮写入不同哨兵，确认参数或中间量是在本轮产生，而非沿用上一轮状态。
4. 在复用边界前后保存数据；添加同步只能作为区分实验，并需证明它覆盖了正确 producer-consumer 边。

对绑定候选还应逐项核对 `LocalTensor<T> = buffer.Get<T>()` 与真正写入该 buffer 的预加载路径。用 NumPy 或 CPU 模型通过只能说明其覆盖的数学语义合理，不能证明真实 Kernel 绑定正确。`blockDim=1` 只能削弱纯核间解释；如果单核仍负责多行或多 tile，生命周期和状态残留仍然可能存在。

## 阴性结果

独立 buffer 无效且基址绑定正确时，不再以“UB 复用”解释结果；转查计算参数、搬运地址和真实依赖。扩大 buffer 后通过只说明布局改变影响现象，也可能改变流水调度或越界落点。必须用绑定和生命周期证据确认后再形成最小修复。

正式修复要同步修正所有 dtype 分支和调用点，并回归独立 buffer、原复用布局、首尾 tile、跨行和 CopyOut。诊断阶段扩大 buffer 或关闭复用产生的通过结果，不能直接作为生产补丁。

## 事实边界

VF 调用模型、接口支持和同步语义必须查询当前版本 API 文档，缺少权威来源时保持 `UNKNOWN`。查询 CANN 9.0.0 的 TQue、depth、实例数与事件语义时，调用 CANNBOT `ascendc-docs-search` 技能选择对应版本与接口。
