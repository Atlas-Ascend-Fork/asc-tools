# Ascend C 编译修复

输入是**编译错误日志＋工程访问入口**。你负责判断和修改；工具提供确定性证据，不调用模型、不自行循环修复。保留用户的接口、功能、实现路径和目标。

方案和验收指**编译失败的修复方案及其补丁验收**；工具/API的一般用法咨询和从零开发不因同属Ascend工具链而进入本技能。只请求编译修复方案或验收判读时，给出下一步和验收依据，不执行命令，不冒称已解析、修改或验证。用户要求“分别”判断的工程、文件或情形，逐项使用各自证据；除非明确指向同一失败单元，不把它们当成互相竞争的解释，不用一项的生成关系否定另一项已核实的无依赖结论。

验收评审可以核对用户已提供的构建、diff和回归记录，指出参数、输入、产物或收据不对应的证据缺口，区分编译结论与整个任务是否完成。审查已有记录不等于接管运行故障：需要后续动作时，明确是本技能的编译/补丁验证，还是交回调用方的其他验收；不把必要验证受阻写成编译失败，也不为审查材料默认启动新实验。

本技能只负责编译修复及补丁的必要验证。当前答复中的独立运行、精度或性能子项，保留编译结论并交回调用方后结束；不指定接管技能，也不代调用方安排取日志、环境调查等独立排查步骤。重新进入须有新的编译失败，或能关联本次diff与异常的具体回归证据；仅在编译之后发生、怀疑补丁有关，不足以进入补丁验证。

## 第一动作：解析已有日志

先按证据决定第一动作，方案答复也遵守这个顺序：

| 已有证据 | 第一动作 |
|---|---|
| 首错、唯一有效声明、调用域、消费点和任务契约已核清，无未决宏分支或生成关系 | 足证快路径：直接保留契约地修改并原配方验证，不为统计调用补诊断 |
| 完整失败日志已有，但声明、条件头或生成关系等仍未确定 | **先用下方完整命令做轻量诊断，再定向补证**；方案也按这个先后顺序列出命令但不执行，不先列源码调查再说“改代码前诊断” |
| 同日志内容、同解析版本已有有效诊断 | 复用首错及原文位置，继续填证据缺口，不重复调用 |

日志须有已解析的首错依据，不能凭印象跳过，也不把首诊拖到长期搜索后才考虑。

默认不预载源码、不检查全环境、不构建。先确认日志文件路径，不把长日志全文读入上下文或先列出整个工程的源码清单。

从本次加载位置取得技能绝对路径，选宿主允许的独占输出目录（如本会话TMPDIR），替换占位路径后直接执行：

```bash
python3 "/实际技能目录/scripts/run.py" diagnose \
  --project "/实际工程根" --build-log "/已有完整失败日志" \
  --out "/本会话输出目录/diagnosis-1" --json-stdout
```

首诊不带`--run-probes`或`--verify`。准确SKU已知时加`--soc Ascend910B1`等值，未知时说明缺口，不猜目标。只请求方案时也给出完整调用形态：工程、日志、独占输出、`--json-stdout`及已知SKU；未知路径用待替换占位，不省略参数或声称执行过。先看摘要的`error`、`observation_status`与首错`primary_error`；说明首错及原文位置，只补读首错/note对应区间。空日志、未知格式或无错误命中不证明编译成功。

没有日志时先取已有记录，确需复现才沿原配方构建一次并保存输出。解析工具失败则记录具体错误，按[脚本契约](references/using-scripts.md)修正调用；确实无法使用时明确标记工具路径未完成，再按原文继续有限分析。不能把“读过日志”记成“已运行解析”。

## 修复闭环

解析后核任务和原配方的必要约束，再读取报错直接指向的使用方、声明及依赖。源码按需查看；相似名字、知识候选和同名声明不能替代当前配置的证据。

| 当前情况 | 下一动作 |
|---|---|
| 首错、声明/使用关系和原任务已支持保留契约的修改 | 修改同源错配，沿原配方验证；不为小题补齐全量环境调查或知识包 |
| fast_path候选被当前声明、目标或任务契约反证 | **撤销该 fast_path 假设**及自己据此作出的无依据试探，保留用户和已证实的改动；说明反证，再定位兼容修法并沿原配方真实编译 |
| 尚有会改变修法的歧义 | 按第一动作完成或复用轻量诊断，再明确待决问题、取最小区分证据；需要时调用下方CANNBOT基础技能 |
| 首次修改后原问题仍在 | 解析新日志，核修改是否进入实际单元；查影子源码、生成覆盖、配置和反证，不原样重试 |
| 新日志进入另一阶段或独立问题 | 判断新阻塞或补丁回归，继续取证；仅行号变化不另起根因调查 |
| 原目标完整编译通过，最终diff保留契约，必要验证已完成 | 立即交付结果；不因还有可选检查而继续消耗预算 |

需要结构化取证时：

```bash
python3 "/实际技能目录/scripts/run.py" inspect \
  --project "/实际工程根" --file "失败源码相对路径" \
  --out "/本会话输出目录/source-1.json"
```

默认最多16源码文件/256KiB，元数据另有预算。`--question build --build-dir PATH`读已有构建记录；外置build需显式路径。`--question environment`核SDK；`--question knowledge --symbol NAME`查API候选；`--mechanism ID`查机制问题。按已知事实加target/配置/版本过滤，具体参数见[脚本契约](references/using-scripts.md)。

先读`evidence`缺口：词法候选不证明宏分支有效；选中命令不证明记录最新；response未完全展开、版本或目标未知时不猜。普通小范围read/grep也可使用，不要求每次读源码都再调工具。只有需要联合规则诊断才用`diagnose --context-mode focused`；`full`和编译探针均按必要性显式选择。

有下列线索时，先读对应参考再作该类判断；只读相关页：

| 线索 | 取证与判读 | 参考 |
|---|---|---|
| Host/Kernel归属 | 核首错函数、声明、修饰、有效宏和实际命令参数/目标；目录、后缀、编译器名和分类仅作线索，混合单元逐处核域 | [调用域判定](references/error-categories/README.md#host与kernel的判定依据) |
| 头来源、语言路由或在线文件 | 核实际依赖及生成顺序；本地足证则直接修复；涉及在线搜索或文件时，答复包含下方交付项中的来源约束 | [头文件判别](references/error-categories/header-missing.md) |
| 模板、类型、API | 核完整签名、拒绝原因及数据契约 | [模板判别](references/error-categories/template-error.md) |
| Host/Kernel共享数据 | 核对字段名/类型/顺序及生产消费契约 | [Tiling判别](references/error-categories/tiling-consistency.md) |
| 构建生成的源码/头与消费方 | 核当前生成源、输出和实际消费映射；与运行样例的数据生成分开 | [生成契约](references/error-categories/schema-consistency.md) |

其他问题从[错误类别](references/error-categories/README.md)或[知识专题](references/knowledge/README.md)选对应页。零命中只覆盖实际搜索范围，不证明API不存在；在线搜索也不证明已取得有效源码。异常见[搜索有效性](references/hard-cases.md#先确认搜索取得了什么)。

## 验证和停止

修改前明确要保留的dtype、shape、布局、算法/调用路径、目标和完整配方。**编译通过、契约保持、数值验证是三种结论。** 不删功能、造stub、换target、改golden/容差、放宽模板或改实现路线来换通过；SDK支持另一种写法不等于用户允许替换。

优先复用覆盖最终源码、依赖、配置及原目标的真实构建证据。需要独占副本和结构化构建收据时用`run.py verify`，参数见[脚本契约](references/using-scripts.md)；也可执行原可信配方，保存完整日志和原退出码。`diagnose`的日志解析JSON不能代替新的构建收据，足证快路径不为补报告调用诊断。不能用Host成功代替必需Device编译，或用一个成功target覆盖遗漏目标。

```bash
python3 "/实际技能目录/scripts/run.py" verify \
  --case "/实际工程根" --json-out "/本会话输出目录/verify-1.json"
```

verify使用`--case`和`--json-out`，不套用diagnose的`--project`、`--build-log`、`--out`或`--json-stdout`。原配方参数与已知准确SKU按[验证入口](references/using-scripts.md#保留原配方与全部目标)追加；需要前态时传`--previous-result`。

先按验证覆盖的风险确定归属：本次diff涉及dtype、布局、地址空间、生命周期、同步等未决补丁风险时，由宿主在**本技能闭环内**推进针对性回归，包括必要输入准备、实际执行和结果核对；范围见[验证范围](references/workflow.md#按补丁风险选择验证)。**同一回归即使也是原任务要求，仍按补丁验证办理**，输入准备、执行和结果核对不能拆分成独立任务交回调用方，也不能退出后等待“新的回归证据”才重入。权限或资源受阻时保留义务，交调用方协调缺失前提；只请求方案时说明责任但不执行。仅原任务另加、与补丁风险无关的运行或数值验收，**交回调用方/原任务流程**。两种情形都不展开独立运行/精度排查；必需的Kernel编译覆盖仍由本技能补齐。

最终diff保留计算/数据/资源语义、原目标已验证且无未决功能风险时，交付编译修复结果，使用结论句**“无需默认追加NPU运行或额外形状测试”**并附依据；原流程的其他验收不因此被宣布通过。有未决补丁风险时不能套用这句停止结论。

补丁回归确需运行，或正在评审已有运行记录的有效性时，先读[运行前提与证据](references/pitfalls.md#需要运行验证时怎样读结果)：区分构建输入与运行数据，核参数、设备映射和收据。仅报告题面或实际记录支持的事实，数量不替代映射，缺少检查不等于已证实故障；保留失败并区分补丁引入与独立问题。

报告引用工具回执时，保留原字段名、原状态及证据范围，另写解释，不缩写字段或合并结论。`compile_passed`只证明本次编译；`compile_failure_fixed`另需适用失败前态及覆盖，不为得到后者而撤回补丁重造失败。`prior_failure_coverage.status=unconfirmed`表示**旧失败覆盖未确认**，须保留`prior_failure_coverage`字段名，不能改成含义不明的`coverage`或声称旧失败已修复；输入采用`prior_failure_coverage=unconfirmed`简写时原样引用并解释。超时、缺日志或缺收据同样保持未确认。字段路径和类型见[JSON契约](references/json-schemas.md)。

`contract_check.status=violated`时区分**两种形态：统一改名或删除调用/功能**，核对diff、当前声明与调用语义；需继续修改或缺少证据才沿原配方**重验**。名称映射、`tolerated`或`status=ok/not_applicable`均不证明功能等价。保留原状态，按[契约判读](references/json-schemas.md#标识符消失后的契约判读)另述人工核验，复用已有完整有效证据。

## 多轮未修复时的升级与交接

同一问题≥2轮修改/编译无新证据时，换区分问题或取证方法；这是升级提醒，不是强制先失败两次或复杂题最多两轮。设施失败不算源码修复失败轮次。围绕缺口协同宿主提供的其他技能，带去已有事实和反证、带回可改变判断的证据；没有新证据不在技能间循环。

尚未修改但定向查询仍无法区分API、架构或布局候选时，也应升级：明确缺口，调用对应CANNBOT基础技能或取得实际编译参数，不用连续扩大源码搜索代替决策。宿主给定时限时，用已观测构建耗时为原配方验证和简短交付预留时间；长构建在途先收取状态，不重复派发。具体见[预算与收尾](references/workflow.md#预算与收尾)。

复杂任务跨轮可用`run.py memory`保存可核对的观察、反证、义务与采纳记录；显式文件/配置依赖改变后局部失效。`inspect --question knowledge --mechanism ID --memory FILE`列出尚缺的证据和结果分支；不自动认定根因或执行探针。简单题不建账，格式见[证据状态](references/evidence-memory.md)。

中断后先观察已有执行：`verify --observe-run RUN_DIR`；首次verify指定新`--recovery-dir`后，可用`verify --recover-verification DIR --json-out NEW_FILE`收取完整报告，不派发、不补丁、不补跑剩余阶段。`build_invoked=null`是未知，不是未消耗机会；写报告失败看stderr恢复指针，见[恢复契约](references/repair-state.md)。

编译修复仍有取证缺口时，按[交接报告与路由](references/handoff.md)协作；预算不足、资源不可用或适用路线穷尽时交回调用方，说明已证实范围、补丁风险、未决问题、在途运行与下一条所需证据。权限拒绝不换入口绕过；仍可推进的编译修复继续推进。

## 与其他技能协作

以下协作只服务当前编译失败或补丁回归的取证缺口，不用于独立运行、精度或性能请求。只安装锁定的必要CANNBOT技能子集及资源，禁止全量下载后筛选。技能同级安装，按宿主提供的**技能精确名**加载；不拼接固定目录、不把技能名当shell命令。缺依赖时报告缺口，不自动全量克隆。

| 缺口 | 基础能力 |
|---|---|
| 工具链/环境冲突 | CANNBOT `ascendc-env-check` 技能 |
| API声明、头或版本 | CANNBOT `ascendc-docs-search` 技能 |
| API参数、类型、对齐 | CANNBOT `ascendc-api-best-practices` 技能 |
| 目标SKU/架构 | CANNBOT `npu-arch` 技能：核SKU、NpuArch、条件宏与代际支持 |
| SIMT契约 | CANNBOT `ascendc-simt-best-practices` 技能：核入口头、类型/API声明与线程调用契约 |
| Blaze/tensor_api | CANNBOT `ascendc-blaze-best-practice` 技能的排障分支 |
| RegTensor/asc_vf_call | CANNBOT `ascendc-regbase-best-practice` 技能 |
| Host/Kernel共享数据 | CANNBOT `ascendc-tiling-design` 技能 |
| 已明确授权的迁移 | CANNBOT `ascendc-blaze-migration` 技能；编译失败不自动授予迁移 |

一次只交接一个具体问题、失败单元/命令、精确SDK/目标和相关引用。技能不可用时，逐个保留待核事实和替代来源，继续查当前SDK声明、实际编译参数或生成/调用链；环境检测不能替代API声明和调用契约核查，也不能用检测到的设备覆盖用户指定的编译目标。不能只列缺失技能便结束，或因缺依赖改变目标和接口。返回后核来源、适用条件及是否回答问题；发现、加载、执行、适用和采纳分别记录。搜索成功/空页不证明支持或不存在，旧版本默认不能覆盖当前任务。详见[协作契约](references/cannbot-contract.md)。

## 环境与交付

需要Linux、Python≥3.9和PyYAML；主要宿主OpenCode，兼容Claude Code。支持下限CANN≥9.0.0，当前知识域9.0/9.1。低于下限仍可通用排查并依据实际SDK修复，明确说明**不强制升级**；版本敏感知识不直接套用，迁移须有授权。更高或未知版本的敏感修法也以当前SDK及真实构建为准；状态判读见[版本与目标](references/workflow.md#版本与目标的条件判断)。`--soc`传准确SKU如`Ascend910B1`或`Ascend950`，不传架构号、不擅换目标。缺工具链可分析，不能声称已编译。

技能目录只读；本项目由`harness/skill/`等真源生成`delivery/tool-compile-debug/`。所有输出用宿主允许的本会话独占路径，工程内输出须排除于源码收集。安装/解释器异常才运行`preflight.py`或`face_selfcheck.py`；对外分享前按需用`redact_bundle.sh`脱敏，其他故障见[工具排障](references/troubleshooting.md)。

最终简要交付：首错和依据、最终diff的实际修改、原配方及SDK/SKU/目标、验证日志和通过/失败/未确认范围。回退过的编辑不列为最终修改；日志工具未执行或失败要如实说明。方案答复也交代取证路径、验收范围及停止条件，不把计划写成完成。

答复前核对以下适用项，写进当前答案；不要求额外执行：
