# header_missing — 头文件查找、语言路由与包含依赖取证

## 诊断信号与级联消歧

常见信号为 `fatal error: '...': No such file or directory` / `file not found`，或因核心入口缺失导致的限定符/基础类型未识别。单一缺头诊断本身不决定应补搜索路径、恢复生成步骤、修正编译语言路由还是移除无用途残留引用；生成顺序与跨目标依赖可配合 [dependency-missing.md](dependency-missing.md) 与 [cmake-config.md](cmake-config.md) 联查。

## 本地确定性取证动作

1. **先核失败单元的真实编译命令与语言路由**：用 `run.py inspect --question build --build-dir <构建目录>` 或构建日志核对编译器、语言模式（普通 CXX vs 设备侧 ASC）、`-I` 目录及目标参数。设备单元误走普通 CXX 时恢复构建语言配置，不靠手堆 SDK 内部子目录路径硬凑；Host 单元使用 CXX 属正常路径，不盲目把全工程改为 ASC。
2. **按实际使用的声明集合恢复公开头入口**：用 `run.py inspect --file <失败文件>` 统计该单元消费的类型、API、宏与注册项，在本机活跃 SDK（解析符号链接后）核实覆盖该集合的公开头文件入口，避免只补单个内部窄头遗漏同单元其余声明。
3. **严格区分必需依赖与无用途残留 `#include`**：核查缺失头是否由代码生成产出，或承担注册、静态初始化、条件宏、模板特化、对齐属性等无直接符号引用的行为。仅当现有有效头已提供全部声明且确认无隐藏副作用时，才可移除残留 `#include` 并沿完整原目标（含必需设备阶段）编译验证。

## cannbot-knowledge 查询路由

| 未决领域问题 | 宿主加载技能 | 返回后本地核对项 |
|---|---|---|
| 特定 API、类型或注册宏在目标版本所属的公开头文件入口 | cannbot-knowledge `ascendc-api-knowledge-query` 技能 | 读取正文并在本机活跃 SDK 安装目录中核实头文件路径与导出关系 |
| 跨版本头文件路径调整、构建模块自动注入机制或生成头规则 | cannbot-knowledge `knowledge-query` 技能 | 核对卡片适用版本域与当前工程 `CMakeLists.txt` 及真实编译命令 |

## 契约保护与外部来源红线

严禁新建空头文件、用 `__has_include` 静默跳过必需功能依赖或篡改已安装 SDK 头。若材料或方案涉及在线搜索或取件，必须遵守并交代**来源约束：检索结论仅限已查路径和版本；后续取件须核源码正文、目标版本及适用条件，拒绝HTML错误页**——检索零命中只覆盖已查范围，绝不作为删减功能的依据。
