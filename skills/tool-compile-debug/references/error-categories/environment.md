# environment — 环境配置问题

## 根因

构建所需的工具链、依赖路径或目标配置与原任务不一致。环境候选可以来自失败日志或当前机器探测，但两者描述的时间和环境可能不同。常见线索：
- 工程采用的 `ASCEND_HOME_PATH` / `ASCEND_TOOLKIT_HOME` 指向缺失或错误的安装；
- 工程配置中的 `SOC_VERSION` / `CMAKE_ASC_ARCHITECTURES` 与用户目标不符；
- 原构建引用的编译器、头文件或库路径在当前环境不可用。

## 典型报错（真实日志样貌）

环境类失败常表现为配置时找不到工具链，或构建参数引用了错误目标。当前机器缺少 CANN 只说明重新构建能力受限，不能覆盖已有日志中的源码、链接或工具错误。引擎分别保留首错和环境检查；离线日志与源码分析仍可继续，真实编译验证须另有可用工具链。

## 修法

1. 从原构建命令、日志和工程配置核对实际工具链路径与版本，再检查相关环境变量；某个变量未设置本身不证明工程不可构建。
2. 对照用户指定的准确 SKU、工程配置及编译参数，按[目标条件核验](../knowledge/soc-arch-gating.md)查明差异。当前机器的 NPU 型号不能代替编译目标。
3. 确认需采用的安装后，在本次构建 shell 中加载该安装提供的 `set_env.sh`，保留原构建选项并重新核对命令解析到的编译器和依赖。不擅自切换版本或目标，不通过叠加多套环境脚本碰运气。

## 与 unfriendly_error_code 的区别

- `environment`：失败证据指向工具链或依赖配置；当前机器的就绪检查另行判读。
- `unfriendly_error_code`：工具日志明确拒绝某个参数值，例如当前后端不接受的 arch。按实际命令和工具支持范围定位，不仅凭错误码推断失败阶段。
见 [unfriendly-error-code.md](unfriendly-error-code.md)。

## 说明

建议动作由随包引擎生成，需与本次失败现场核对；`environment_checks` 与 `primary_error` 分别读取。SoC 与架构参考记录见 `scripts/engine/harness/knowledge/soc_feature_matrix.yaml`。

## 多版本 CANN 共存与 ABI 混链

同一台机器上 8.x 与 9.x 并存时，头文件/库/运行时的版本可能交叉链接，产生编译期或链接期的隐晦报错。

### 检查序列

1. 从原构建日志与实际安装元数据确认版本，不假设环境变量后还需要拼接 `latest`。
2. 记录原编译和链接命令中的编译器、`-I`、`-L`、sysroot、目标及宏；必要时沿原配方获取详细命令。脱离这些参数运行一个空预处理命令，不能证明失败编译单元采用了哪些头文件。
3. 对任务实际产物检查依赖，例如 `readelf -d "$ARTIFACT"` 的 `NEEDED`、`RPATH`、`RUNPATH`。这些项是动态依赖信息，不能单独还原历史链接时使用的库文件路径；与原链接命令、构建记录交叉核对。
4. 有符号版本错误时，用 `readelf --version-info` 分别检查报错产物需要的版本和实际解析到的库提供的版本。区分 `GLIBC_*` 与 `GLIBCXX_*`，后者来自 libstdc++，不能用 `ldd --version` 代替核验。

### 常见混链形态

| 形态 | 报错表现 | 处置 |
|---|---|---|
| 新头旧 .so | 链接或加载时缺符号 | 先确定失败阶段；链接阶段核实际库路径及导出，加载阶段核动态解析路径，再修已证实的混用 |
| 旧头新 .so | 编译可见声明与所选库不一致 | 依据用户版本和原配方统一头库来源，在独占构建副本中复验 |
| GLIBC/GLIBCXX 版本不匹配 | 所需符号版本未找到 | 对比报错产物与实际 libc/libstdc++ 的符号版本，核工具链和依赖的兼容要求 |
| 多个 `set_env.sh` 冲突 | 编译器或依赖路径混用 | 在本次构建环境选用已确认的安装，重新核对实际命令与头库来源 |
