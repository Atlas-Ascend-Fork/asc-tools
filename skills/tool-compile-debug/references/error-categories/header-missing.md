# header_missing — 头文件查找失败

## 错误说明

当前编译单元无法解析某条 include。可能是必需头文件缺失、搜索路径不完整、生成步骤未执行、源文件走了错误的语言或工具链，也可能是已经没有用途的残留 include。分类本身不能决定应补依赖、修改构建配置还是移除该引用。

## 典型诊断与关联症状

```
fatal error: 'xxx.h': No such file or directory
fatal error: 'xxx.h' file not found
fatal error C1083: Cannot open include file
```

缺少 Ascend C 核心声明还可能表现为以下错误；它们也可能由错误的编译语言、条件宏或接口用法引起，不能只凭符号断定缺少某个头。

```
unknown type name '__aicore__'
constructor cannot have a return type
```

## 按证据选择修法

| 现场证据 | 下一步 |
|---|---|
| 所需头位于当前 SDK，但设备翻译单元实际使用普通 CXX，缺少原设备构建参数 | 核对源文件语言属性、目标声明和工具链选择；恢复该翻译单元需要的设备编译路径，不逐个补全局 include 来模拟另一种语言的环境 |
| 编译语言和工具链正确，但当前目标缺少合法依赖的 include 路径 | 在必要目标或依赖接口上补路径，并检查声明及消费者；不是一律禁止增加 include |
| 头由配置或代码生成产生，源码目录仅有模板 | 核生成真源、生成命令、输出目录及目标依赖；恢复生成到消费的顺序，不只修改生成物；旧产物会掩盖结果时使用独立干净构建目录 |
| 源码使用 Ascend C kernel API，缺少其可见声明入口 | 核对应版本的公开头及当前源码实际使用的声明；恢复能覆盖这些声明的入口，不只补第一个类型的窄头后遗漏同一单元其他API |
| Host 注册代码中的类型、注册宏等同时未声明，而源码未包含相应公开入口 | 核当前 SDK 的声明及本机同类模板，恢复 `register/op_def_registry.h` 等实际声明入口；不由缺头推导必须改写 tiling 数据表示 |
| 缺失头没有生成或依赖来源，当前使用的声明由其余有效头提供，且没有依赖该头的注册、宏或其他功能 | 可移除这条残留 include，并验证原目标及受影响配置；保留计算、注册、特化和其他有效包含关系 |
| 当前版本安装中没有所需头 | 核依赖来源、版本和任务要求；搜索未命中本身不足以证明 API 已移除或功能可删除 |

构建日志中的 `Building CXX object`、实际编译器命令、CMake 源语言属性和 `compile_commands.json` 可帮助核对路由；以本次失败编译命令为准，旧缓存或静态配置文字需要交叉核对。Host 实现使用 CXX 可以完全正确；不能因为扩展名是 `.cpp`、路径含 kernel 或工程使用 CANN，就把所有源文件改为 ASC。

已有源码和构建证据足以区分上述情形时，直接做对应的局部修改。临时添加路径只排除了一个症状，不证明它是独立必要修复；若随后确认语言或工具链才是根因，复核临时改动是否仍有依据。

**按失败单元实际使用的API集合选择公开入口。** 当源码同时使用Tensor、队列、搬运或计算API时，
仅找到第一个缺失类型的窄头不足以说明依赖完整。若当前SDK或同类模板确认`kernel_operator.h`等公开聚合入口覆盖这些声明，
且原编译语言正确，就恢复该入口并运行原构建；已有证据只需某个独立公开头时，不强制改用聚合头。
不要求逐一追完入口下的每个宏、序列化辅助函数或工具链生成器。框架注入的声明仍由原框架提供；不能因尚未找到其定义，
就额外改写注册方式或生成链。只有新构建仍在相关符号处失败，或已有证据显示独立错配时，才扩大调查。

## 区分必需依赖与残留 include

缺失文件的名字不是用途证明。围绕失败单元核对实际用到的类型、函数、宏和模板特化由哪些头提供，
再看目标的 include 路径及生成依赖。布局类型已由现有公开头定义，不意味着一个名称含 layout 的缺失头必需；
同样，搜索不到与文件名相似的标识符，也不证明该头无用。

只有现有声明和构建关系支持“此引用无用途”时，才删除该条 include 并沿原配方编译。
**没有直接符号引用不等于没有行为**：注册、静态初始化、条件宏、模板特化以及对齐或打包设置都可能由头文件引入。
任务需要这些行为、头应由生成步骤提供，或用途仍不清楚时，应恢复真实依赖、纠正头名/版本或修生成链，
不能删掉相应功能、放一个空头、用 `__has_include` 静默跳过必需依赖来换取通过。
编译通过只验证实际参与的目标和配置；若删除触及任务要求的条件分支或注册行为，再核相应构建或已有功能用例，
不把未启用的分支也报告为已验证。

已有用途与无副作用证据充分时，沿原配方验证受影响目标即可；不把符号表比较、二进制逐字节一致或额外行为测试设为统一门槛。生成顺序问题核当前依赖关系、生成产物和实际消费证据；是否补干净构建或增量生成检查由尚缺证据决定，不固定要求两次全量干净重建。

上游资料用于解决具体缺口，例如确认某版本的头名迁移或生成规则；先核对应版本与本地改动。本轮材料或方案提及在线搜索或下载时，答复保留一条**来源约束：检索结论仅限已查路径和版本；后续取件须核源码正文、目标版本及适用条件，拒绝HTML错误页。** 只给方案、用户仅提供搜索未命中或本地用途证据已充分时也适用；这是约束结论范围，不要求额外联网。
在线取文件须先确认**源码正文、目标版本和适用条件**：核最终返回内容、仓库/tag或提交与文件路径，并核声明的宏、目标和版本条件；HTTP 200 也可能返回HTML错误页或登录页，仓库页面不等于头文件正文。无关版本、来源不明或未取得正文时，不能作为当前声明存在、缺失或适用性的证据。fetch部分失败或历史不完整时保留已取证范围。
一份当前上游文件未引用该头，只能作为旁证，不能覆盖用户本地扩展。局部声明和用途已经明确时，
无需再证明该文件在所有历史 tag 中都不存在；若版本来源或头内副作用仍决定修法，则继续有针对性取证。
检索零命中只覆盖实际检查过的路径和版本，不能据此断言文件从未存在或源码来自错误注入。

目录含符号链接时，先解析实际头文件位置再搜索；某个目录零命中不等于 SDK 不提供该声明。若手工探针因缺框架参数或 include 失败，回到失败编译单元的真实命令或原目标取证，不连续补路径来猜出一个不同的编译环境。

沿完整原目标重新构建，确认所需源文件和产物参与；生成工程的默认`all`若只覆盖Host，不能据此推定单独设备目标也通过，
仍须执行原配方要求的设备阶段。出现新的真实首错时复用完整日志继续分析，不删除仍有声明或行为依赖的包含链、计算来绕过失败。
生成依赖另见 [dependency-missing.md](dependency-missing.md)，构建语言与配置另见 [cmake-config.md](cmake-config.md)。
