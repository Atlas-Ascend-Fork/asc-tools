# schema_consistency — 算子原型与生成接口不一致

## 根因

算子原型、Host 侧参数准备与 Kernel 侧消费约定不一致，或生成代码未反映当前定义。
工程可能以 `.json`、注册代码或模板作为生成源；先确认本工程实际使用哪种形式。
原型输入/输出、属性、workspace、tiling 等在各层的表达不必一一同名或具有相同参数个数，
应按生成规则和实际调用核对映射，不能把签名字面差异直接当作错误。

## 典型线索

```
prototype ... schema mismatch
opcheck: input_desc missing / required dtype ...
host_kernel arg mismatch
generated code is stale
```
这些文字用于寻找相关原型、调用或生成链，不单凭关键词认定哪一侧应修改。

## 修法

1. **定位实际契约**：核当前原型/注册定义、生成入口与版本、Host 调用及 Kernel 参数用途，找出与原功能矛盾的那一处。原任务或工程说明约定的实现方式同样需要保留；接口相同不代表可以替换实现。先修有证据支持的错误，不强制同步修改每一层。
2. **修复同一生成链的已知错配**：头文件名称、结构体成员与调用参数若来自同一模板，同时检查生成源和受影响使用点。涉及共享结构时核对字段名/类型/顺序，并按真实生成规则检查生产消费映射；不要求不同接口层的名字或顺序字面相同。把已有依据的连贯修改合在一轮验证，避免只改 include 后才发现同处可见的成员错名。
3. **保留用户修改再生成**：确认为陈旧输出时，按原工程规则更新；需要比较生成结果时在独立目录操作。核明生成物与手写代码的边界，不能直接删整份工程或重新生成后覆盖手写实现。
4. **原配方验证**：保留生成、编译、链接及任务要求的打包阶段和全部目标。诊断可按需补定位线索，实际声明与构建结果才用于确认修复；工具未列出全部映射不妨碍继续核对源码。

声明与受影响消费者已经共同指向一个名称或字段错配时，在原工程形式内修正后验证；无需为了理解全部生成宏而追查每层工具实现。裸结构体与注册宏的数据路径以当前工程和 SDK 的实际支持为准，不能由“这是注册算子”推导必须迁移序列化方式。新的真实首错、生成物与声明不符或有证据支持的独立错配，才是扩大检查范围的依据。

## 与 tiling_consistency 的区别

- `schema_consistency`：算子原型/注册、生成接口与调用约定层面的不一致。
- `tiling_consistency`：**tiling 数据结构字段**（定义与 Kernel 消费方）层面的不一致。
见 [tiling-consistency.md](tiling-consistency.md)。

## 说明

诊断的 `static_findings` 与修复指导是定位线索，不承诺枚举完整原型映射或替调用方选择修法。Tiling 字段修改也不自动要求修改原型的输入/输出描述。
