# 常见误判与证据核对

diagnose 未命中（`category=unknown` 或 `kb_evidence` 为空）、你自己判类别时，这些是最容易判错的地方。**看到左列现象，别急着跳到"错误结论"，先做右列的核对。** 本表沉淀自真实编译问题排查（含 CANN 官方 catlass troubleshooting 要点）。

## 分类误判红线

| 看到 | 易误判为 | 先核对 |
|---|---|---|
| `Fatal Err` / Stack dump / ICE | `compiler_internal` | 向前找非法 arch、幻觉 API、jump range 或第一个源码错误——ICE 常是下游 |
| `AscendC` 大量未声明 | 幻觉 API | 先看是不是缺 `kernel_operator.h`（头没包全，不是 API 不存在） |
| `no member named 'X' in '*TilingData'` | API 不兼容 / 幻觉 | 核实际接收者类型、定义/生成链和Host/Kernel消费方；定义缺失与消费方拼写错均可能成立 |
| `no matching function for call to 'F'` 且列出候选签名 | API 不存在 | 读候选被拒原因，核调用层、类型和模板条件；候选存在不保证它满足当前功能 |
| 引用参数重载可以编译 | 可用一个新建对象替代原返回值 | 核引用是纯输出还是消费已有状态；跨函数同名局部对象不共享资源，见[API数据流](error-categories/template-error.md#返回值与引用参数的契约差异) |
| `candidate function not viable` | 幻觉 API | 核本次编译可见的完整签名和实参，不能只凭KB收录或短名决定修法 |
| `candidate template ignored: deduced conflicting types for 'T'` | 函数不存在 | 核两个实参的用途、值域/单位及期望类型；转换须保留这些约束，不能任意窄化或改变符号 |
| `no viable constructor or deduction guide for deduction of template arguments` | 无从下手乱改 | 读构造/推导候选及拒绝原因；只在目标实例正确时显式给模板参数，否则修正调用或定义关系 |
| `use of undeclared identifier 'AscendCC'` + did-you-mean | 幻觉 API | 核实际声明与调用意图；证据支持拼写错误时局部改名，不将did-you-mean视为无需核对的指令 |
| `Softmax` / `ReduceMean` 不可见 | 直接判幻觉API | 核大小写、完整namespace、调用层、目标声明及头入口；近名只作为候选，不直接分解或删功能 |
| `register/*.h file not found` | 注册或序列化框架必须重写 | 核实际SDK文件、原编译单元与include覆盖；头文件或入口已能解释首错时先局部修正再构建，不从目录名推断迁移要求 |
| 某 API 在新 arch 上不可见 | 幻觉 API | 可能是 arch 门控（高层 API 仅在部分 arch 存在），读[头入口与目标](knowledge/soc-arch-gating.md) |
| 某目录搜索无命中或上游请求失败 | 整个 SDK 不存在该 API，或调用可以删除 | 只报告实际搜索范围；需要区分修法时再核真实 include 路径、条件声明和使用方。是否删除调用仍由原功能及依赖证据决定 |
| 只有 CANN 错误码、无源码行 | 已定位 root file | 证据不足，索要完整日志 + 构建命令 + 上下文 |
| 含 catlass 内部 `static_assert` 报错 | 无从下手 | 报错信息通常有详细说明，读它——线索通常已包含消息里 |

## 流程误判红线

| 倾向 | 问题 | 正确做法 |
|---|---|---|
| "这个错看着简单，可以直接猜着改" | 尚未核对报错定义、使用点与任务约束 | 已有本地证据足以确定保留功能的修法时直接修改并沿原配方验证；定位有缺口时再诊断，已有同状态产物可复用（见SKILL.md） |
| 盯着 build.log 末尾的异常改 | 末尾常是统一包装/rethrow，不是首因 | 找**第一个**足以解释后续失败的致因报错 |
| 一次混入多个无关修改再编 | 结果无法区分假设 | 一组连贯改动验证一次；保留对应源码与日志证据 |
| diagnose 建议没修好，再套一遍同建议 | 缺少新证据，可能是假设或实际编译输入不对 | 核实际编译单元和新日志；换问题重新诊断，反证成立时撤回旧假设 |
| 凭记忆判 API 用法对不对 | AscendC API 名/签名易记错 | 调用 CANNBOT `ascendc-docs-search` 技能或读 toolkit 头核对，别凭记忆（CANN 官方红线） |
| `verification_not_run`/`environment_unavailable` 后反复重试 run_verify | 未做真实验证，未查原因 | 核dry_run、soc/参数形态、环境与构建配方；按授权修正条件后再验，不宣称成功或失败 |
| SDK支持另一种实现且数值冒烟相同 | 误以为可以替换任务明确指定的标量/向量、算法或调用路径 | 修改前读取相关实现要求，修改后核最终diff；编译、数值与实现约束分别报告 |
| 副本编译已确认，但目录名与原配方拼写不同 | 为路径外观相同重复完整构建 | 比较最终源码、完整目标/选项、工具链、产物要求和新鲜编译范围；范围缺失或源码变更才补验 |
| 为消除所有怀疑连续修手工探针的include和宏 | 探针自身环境偏离真实编译单元 | 从实际构建取得参数；无法忠实复现时回到原项目验证，不把探针缺环境当作工程根因 |

## 日志收集协议

第一次执行构建时就固定原配方工作目录、目标和参数，保存完整 stdout/stderr 与构建自身退出码。
相对源码、脚本和数据路径均按该工作目录解析，不假定上一次工具调用的 `cd` 或变量仍有效。
在宿主允许的本次独占输出目录准备日志和收据父目录，选择未使用的路径，不覆盖失败前态。
已有完整日志和收据时直接复用；需要新执行时，可用下面的 Bash 记录函数，前台与后台只选一种。
`VERIFY_CWD`、`VERIFY_LOG`、`VERIFY_RC` 由调用方设置为本次实际绝对路径，日志及收据路径必须尚未使用。
每次工具调用重新提供这些变量和函数；函数参数是原命令及其参数，不拼接为待解释的字符串。
原入口应等待其所有必要阶段结束并传播失败；包装不能补救入口自身吞掉的错误。

```bash
record_command() (
  : "${VERIFY_CWD:?}" "${VERIFY_LOG:?}" "${VERIFY_RC:?}"
  if [[ -e "$VERIFY_RC" || -e "$VERIFY_RC.tmp" ]]; then
    printf 'recording_error=receipt_path_already_used\n' >&2
    exit 125
  fi
  cd -- "$VERIFY_CWD" || exit 125
  # noclobber只作用于记录文件创建，不改变原命令继承的shell选项
  (set -o noclobber; : > "$VERIFY_LOG") || exit 125
  exec 3>> "$VERIFY_LOG" || exit 125
  # 使用外部命令，例如 bash build.sh；if 可保留非零状态，不依赖调用方 set -e
  if "$@" >&3 2>&1; then command_rc=0; else command_rc=$?; fi
  exec 3>&-
  # 完成前没有最终收据；临时文件与最终文件位于同一目录
  if ! (set -o noclobber; printf '%s\n' "$command_rc" > "$VERIFY_RC.tmp") ||
     ! mv -T -- "$VERIFY_RC.tmp" "$VERIFY_RC"; then
    printf 'command_returncode=%s; recording_error=receipt_not_saved\n' "$command_rc" >&2
    exit 125
  fi
  printf 'command_returncode=%s\n' "$command_rc"
  exit "$command_rc"
)
```

默认以前台执行，让宿主等待同一次命令完成；将示例替换为已确认的构建入口或必要运行入口：

```bash
record_command bash build.sh
```

确需后台执行且宿主允许任务持续运行时，用同一函数执行一次并取得完成状态：

```bash
record_command bash build.sh &
command_pid=$!
# wait 只能在启动任务的同一 shell 中使用
if wait "$command_pid"; then wait_rc=0; else wait_rc=$?; fi
printf 'wrapper_returncode=%s\n' "$wait_rc"
exit "$wait_rc"
```

跨工具调用不能用新shell的 `wait` 取得旧任务状态，应查询宿主原任务并读取该次唯一收据及日志。
前台工具返回、PID消失或日志尾出现成功字样均不替代完成状态。示例在目录/日志打开失败时不生成命令收据；
收据写入失败时保留已取得的命令状态并将包装返回置为125。125也可能是原命令自己的返回码，须结合收据及错误区分；
记录失败不证明编译失败，收据存在也不证明验收通过。

收据未出现时先区分任务仍在运行、包装进程终止和写入失败，查询已有任务及日志，不立即再启一份构建。
取得完整失败日志后从该文件搜索报错和上下文，不原样重编只为更换筛选命令。旧日志不完整时，先核已有原生、
生成/子任务日志和收据；无法恢复且缺失部分仍影响修法或验收，再按授权补跑对应范围。工程只能由用户访问时才请用户提供材料。

注意事项：
- **按证据决定是否全新构建**——已有本次完整原配方日志可以复用。需排除旧产物或任务明确要求 fresh build 时，按真实构建工作目录确认并清理该任务独占的构建目录，再执行原配方；不要凭目录名删除源码或其他任务产物。
- **管道状态分别保存**——`$?` 在普通 `build | tail` 后通常是末端命令状态。确需 `tee` 时，在Bash管道结束后、任何其他命令前用 `pipeline_rc=("${PIPESTATUS[@]}")` 保存全部状态，分别检查构建和日志写入；启用 `set -e` 时应在条件分支中立即保存，避免失败退出前丢失状态。验证脚本入口完成还不代表编译成功，最终读取 `after.returncode` 与覆盖证据。
- **先落完整日志，再摘要**——构建和运行输出不要直接管给 `head` 等会提前关闭管道的命令；它可能中断被测进程。对保存的日志提取首错、必要上下文或尾部，未解决的细节再展开，无需将整个日志反复灌入上下文。
- **TBE 信封包裹的日志**——如果外层是 TBE/opbuild 的包装日志，需要提取内层编译器输出。
- **保留实际失败阶段**——源码行级报错有助定位；配置、链接或打包失败可能没有源码行，仍需保留首个失败命令、完整错误与相关配置，不能因缺源码行排除这些失败。

## 从执行记录到验收结论

记录回答“这次实际执行了什么”，结论回答“它证明了哪一项要求”。先将命令、工作目录、目标/输入、
完整日志和真实状态对应到本次最终源码及相关依赖；再按[必要范围](workflow.md#按补丁风险选择验证)分别判断编译、实现约束与运行。
不要求新增报告格式，在已有日志、收据或最终说明中保持这些对应关系即可。

| 本次证据 | 可给出的结论 |
|---|---|
| 原目标构建实际覆盖最终源码和必要阶段，命令成功且所需产物有效 | 该构建范围通过；没有运行证据时不扩大为数值通过 |
| 输入匹配、读取与实际设备执行成立，原可信比较器判定通过，程序正常完成 | 所列输入上的运行/比较通过；不能替代实现约束审核或代表未测组合 |
| 真实构建失败，或有效输入下实际运行/比较失败（即使程序退出0） | 保留相应失败阶段及事实；是否由补丁引起仍须因果证据 |
| 尚未执行、启动受阻、超时、缺真实状态或覆盖与最终源码不符 | 对应验收未完成/未确认；保留已有有效范围，缺口不记为通过 |
| 退出0或“Compare success”与缺输入、读取失败、ACL失败等并存 | 记录该次执行异常，数值未确认；先恢复前提，不用成功字样覆盖错误 |

后台无收据但有部分成功输出时只能引用已取得的观察，不能报告退出0。完整测试框架已有可信结果记录与失败传播时，
无需强求固定成功字符串或重新执行。新增修改影响到哪一项证据，就重新核验哪一项；不同源码或输入的收据不拼成整体通过。

## 需要运行验证时怎样读结果

本节用于编译补丁的必要回归，也用于只读评审已有验收记录；读取本节不授权执行运行任务。最终diff仍有功能风险时，按[补丁风险](workflow.md#按补丁风险选择验证)推进相关既有用例；与补丁风险无关的附加验收交回调用方。已有匹配证据可复用，不为重复取得同一结果另建验证程序。保存完整输出和程序自身退出码，不把后续 `grep` 或日志显示命令的状态当运行状态。

**先核运行条件，再解释失败。** 仅编译时不要求设备检查；需要运行时按下面三类证据准备，不靠轮流猜编号或参数重试：

| 前提 | 核对方法与边界 |
|---|---|
| 逻辑设备 | 优先用已有有效运行配置；有映射疑问时，用当前SDK或运行框架查询本进程可见的逻辑设备。物理节点编号不能直接当作程序设备参数；`npu-smi`等管理工具缺失、没有同号设备节点或某个编号初始化失败，都不能单独证明没有可用设备。命令不可用时改用能提供相关事实的已有接口，不反复执行同一缺失命令 |
| 本次安装产物 | 按本次安装/环境脚本核vendor/OPP和库路径，确认程序加载所修目标的产物；`ASCEND_CUSTOM_OPP_PATH`应按实际vendor配置，不能仅因父目录名为`vendors`就视为配置完成。安装或加载尚未成功时，先处理这项前提，不能归因于算法 |
| 输入与参考 | 核对原生成器、程序参数和实际文件共同描述的输入组合；影响数据契约的参数或布局变化后，重新生成对应数据和golden，已有文件能证明匹配时可复用。读取失败或配置错配时先恢复有效输入，不用该次比较判断补丁正确性 |

设备查询成功及设备数量仅说明该查询的结果，不独立证明具体逻辑ID、授权分配或设备空闲。
按当前运行时/框架的映射和本任务分配确认实际ID；程序默认0也只是解析规则。未核映射与错误码前，
不能把一次初始化失败定为编号越界或断言与补丁无关；先前失败仍保留。

**区分构建生成物与运行输入数据。** 运行参数、样例mask、输入文件或golden不对应时，先按用户
要求用原可信生成器准备对应运行数据。仅当该参数实际参与源码/头生成、宏、模板或构建配置时，
才重建受影响目标；不能看到“生成记录”便重跑工程构建，也不能擅自换成旧样例参数缩小任务。
vendor父目录与安装清单同时存在，不证明路径已经正确；核环境变量经本工程加载规则实际解析到的
vendor根和所修产物，再报告路径是否适用。

查询设备等探针须先检查API自身是否成功，再解释输出参数。初始化为0的计数在查询失败后不是
“成功枚举到零个设备”；探针进程退出0也不提升内部API失败为成功。临时设置可见设备、库路径或
预加载项后取得的结果只适用于该环境，不能反推原环境不可用。

动态库或初始化故障若发生在自行追加环境变量之后，先核这次改变。优先复用当前安装的受支持
环境脚本或已有有效配置，在同一进程环境启动原程序；不把编译链接所用的桩库目录猜作运行库并
反复前置到搜索路径。只有疑点仍在时再核实际加载库与缺失符号；环境恢复也不保证所有运行故障消失，
须以本次执行结果判断，不无证据归因机器忙或算法错误。

**保留可信的生成器与独立参考。** 原验证入口有问题时，先区分工作目录、参数、依赖与访问范围。原生成器受阻不证明其算法错误，不默认复制改写、内联复刻或换入口绕过限制。能在授权范围修正执行条件时，继续使用原数据生成和判定规则；确需新增验证程序时，以既有SDK编译/链接配方和独立参考为依据，记录覆盖，不用被测输出反推golden。必需验证受阻则保留未完成项，可选验证受阻则交付已确认范围；两者都不将未知记为通过。

**先确认命令实际被解析成什么。** 复用当前版本已验证的调用形式；有疑问时读程序的参数解析或对应帮助，区分位置参数与命名选项。命令写着 `--m=128` 不证明程序收到128：若程序把整段字符串交给整数解析，可能得到0或默认值。核解析后的shape、dtype、布局、步长、padding、mask与设备；参数总数合法，也可能因漏项使设备号落入形状参数。有效零尺寸是独立边界用例，不能替代要求的非零计算；打印帮助、提前返回或零元素比较不证明目标路径执行过。

**先确认比较的是同一个用例。** 参数变化后核生成器、实际文件与golden是否对应本次解析结果，按物理布局核字节数和读取是否成功。文件过大、短读、沿用旧数据或读取失败后仍继续比较，都不能提供该用例通过的证据；没有尺寸警告也不保证数据匹配。若同时看到零尺寸、分配/ACL错误和成功文字，先修已证实的输入或调用形式问题再重验，不立即改库路径、调容差或另造探针来解释算法。输入有效后仍失败，再沿真实错误调查设备、依赖或实现；不能把全部ACL错误归因参数。

警告与成功文字矛盾时，结论是本次成功证据不足，不据此断言比较器实现有缺陷、文件不存在或
已经发生短读；这些归因还需实际读取结果或实现证据。题面给出的事实可用于判读，未给出的布局、
读取行为及因果关系保留未知，不能从恰好相符的元素总数反推出实现。

运行覆盖按**实际到达的路径**与输入组合记录。修改dtype分支、尾块、对齐或流水配置时，选择能到达受影响路径的合法用例；只跑另一个dtype、整块路径或提前退出分支，不补齐该风险。已有证据足够时不为凑数量增加用例，也不把更多运行次数当成覆盖了原输入集合。

**padding归因需要索引证据。** 先确认生成器、kernel和比较器的逻辑形状及物理布局一致，再将实际错误下标映射到逻辑元素和填充区，分别核对有效区结果及填充值契约。仅凭错误数量、填充比例或另一个无填充样例通过，不能证明当前有效区正确；尚无逐元素证据时将padding保留为假设，不调整golden或屏蔽比较区来获得通过。

总差异数大于已知有效元素数，至多证明部分差异位于有效区之外；不证明有效区全对，也不证明其
全部出错。具体归因仍需索引映射，不能因有效区基数已知就省略这项证据。

按[执行记录与结论](#从执行记录到验收结论)核对程序状态、真实执行与比较，不改golden、容差或退出逻辑来消除失败表现。
若失败由编译补丁引入，继续修正补丁并重验；独立的运行或数值问题交回调用方，保留已有证据及尚未确认的补丁影响，不扩展为独立故障排查。

设备或资源不可用时，保留首次完整错误，核当前版本错误含义、逻辑设备映射和可用性；自写重试脚本打印“busy”不是占用原因的证据。条件修正、资源释放或调度许可后再验证对应范围；同一条件持续失败时停止追加循环，报告编译结果与运行未确认。必要运行、失败调查和等待成本照实保留，不为减少调用跳过功能风险验证，也不把重复等待算作新增质量证据。
