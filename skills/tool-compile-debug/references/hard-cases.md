# 深层排查方法

**这是一份方法菜单，不是执行步骤。** 根据当前诊断、源码、日志与待区分假设，选择最小有效取证方法，不需要先走完知识页或其他阶梯。每条说明适用条件与风险；简单局部问题无需扩成复杂排查。

从当前失败日志、源码和已有诊断中提出待检验假设。复杂或仍有歧义的问题，先按[SKILL.md](../SKILL.md#修复闭环)运行或复用结构化诊断，再选择本页方法；工具确实不可用时记录阻断并继续源码取证。方法菜单不预设哪个假设必然正确，也不取消入口的诊断触发条件。

---

## 方法 1：隔离副本中的二分缩减

- **何时用**：大范围报错、错误信息指向的位置明显不是真因、或怀疑某段代码整体有问题而编译器
只报了下游症状。
- **怎么做**：在隔离副本中逐步把可疑代码块 `#if 0 ... #endif` 或注释掉，缩到"去掉它就编过"
的最小触发集；再逐步恢复，定位真正引入错误的那一处。
- **何时别用**：当前源码、声明与诊断已足以支持局部修法，直接修改并验证。
- **风险**：注释掉的代码可能有依赖（删了 A 引出 B 的新错），需理解依赖再动；别把注释当最终修复。

## 方法 2：最小复现剥离

- **何时用**：错误埋在大算子（上千行）里，上下文太多看不清；或怀疑是某层依赖引入的。
- **怎么做**：在隔离副本中保留触发错误的最小编译单元，逐步缩减无关代码与依赖。继承原失败单元的编译器、目标、宏、include 和强制注入头；优先从实际编译命令取得这些参数。某层移除或恢复使错误改变时，再核对其具体声明与调用关系，不能仅凭关联就判定该层有错。
- **何时别用**：错误明显是工程配置级（CMake/find_package）——剥离 kernel 无助于配置问题。
- **风险**：剥离过程可能丢失框架注入的声明。探针连续卡在缺路径或缺宏、不能检验原假设时，回到原目标或保留构建系统的副本；不反复猜 include 来构造另一个环境。原日志与声明已排除的候选无需再写入源码验证一次。

## 方法 3：符号溯源（配合知识库）

- **何时用**：`no member named X` / `use of undeclared identifier X` / `undefined reference to X`。
- **怎么做**：先区分工程自有符号与vendor API，沿已有声明/调用线索取证；当前日志已指明定义时直接读它。
缺API线索时查相关知识页和本次实际CANN安装中的声明头，核namespace、签名、Host/Device 归属及目标条件；工程字段则对照定义、生成链和消费方。tiling错的根因可能在定义处，也可能是消费方拼写或类型错误。共享声明与消费者已经解释一个局部错配时，修改并构建，不要求先追完全部生成宏；缺总头能解释级联未声明时也先恢复入口，不提前重构下游。
- **何时别用**：diagnose给出的 `root_cause_localization.root_file` 与当前源码证据吻合时直接用；有反证时继续查证。
- **风险**：toolkit 头里同名符号可能有多个重载/命名空间，核对清楚归属再改。

### 先确认搜索取得了什么

零命中、命令失败、结果被截断和内容被改写是不同状态。搜索没有解释当前矛盾时，先核这一次取证，
不立即扩大到整个SDK或推断API不存在：

- 核真实目录、文件过滤与可见范围。SDK兼容入口可能是符号链接，工具是否跟随链接须确认；必要时定位到该入口的真实目录再查，不遍历无关安装。
- 核工具参数与原始输出。`rg` 默认递归，`-r` 是替换匹配文本，不是递归开关；`rg -rn` 或 `rg -rln` 可能把类型名显示成替换文本。查看匹配行用 `rg -n -- 'pattern' path`，列出文件用 `rg -l -- 'pattern' path`；关键声明回到原文件读取。
- 保留搜索自身的状态和stderr。`rg` 的1表示此次范围内无匹配，2表示错误；末端 `head` 的0、隐藏stderr后的空输出都不能代替它。长输出只展开相关位置，不把截断结果当完整符号集合。
- 搜索或技能加载因ripgrep缺失、临时下载失败而报错时，不把失败当零命中，也不反复触发下载。在允许路径用宿主read、已安装grep或Python读取已定位文件/有限目录；已发现的技能可直接读取其SKILL.md和所需资源，记录加载退路。日志解析仍用本包Python入口，不依赖rg。不得据此绕过权限拒绝或扩大目录范围。通用技能包不内嵌与机器架构绑定的rg二进制；宿主预装与能力检查由运行环境负责。

同一次探针先取得有效结果、后续步骤又失败时，分别保留已取得的事实和未执行的部分。
例如库加载报出未定义符号后，辅助脚本另一个调用发生参数错误：前者仍是加载证据，后者是探针问题，
不能互相覆盖。HTTP成功也须核返回内容确实是所需版本源码，而非登录页或HTML错误页。

## 方法 3.5：模板/重载错误的候选声明核对

- **何时用**：`too few/many template arguments`、`no viable constructor or deduction guide`、
`no matching function` + `candidate template ignored`、`deduced conflicting types for 'T'` 这类 **模板/重载/推导**错误。
- **怎么做（关键：编译器已经把定义处指给你了）**：
  1. **先看错误块里的 `note:` 行**——模板类错误编译器几乎总附一条 `note: template is declared here` / `candidate ... declared here`，**它直接给出定义处的 `文件：行`**（哪怕和报错行同文件、
     相隔几百行）。直接跳到那一行读模板/构造声明，**不要**先 grep 全库。
  2. 对照声明的模板参数、候选被拒原因与实际传参。类型推导冲突先核各值的用途、值域与单位；
     修改声明、调用或显式转换都须符合契约，不能为了消除错误任取一个较窄类型。
     Tensor dtype、指针地址空间及布局不靠强转变正确。显式模板实参只适用于目标实例本来就正确的情形。
     返回值改为引用参数时，另核初始化、生产/消费间的对象或句柄传递与生命周期；细则见[API数据流](error-categories/template-error.md#返回值与引用参数的契约差异)。不为了保留已证错误的实例配置而迁就另一重载。
  3. 只有 note 没给、或定义确实在别的头文件里查不到时，才用方法 3 的符号溯源去 toolkit 头找。
- **何时别用**：diagnose已给出与当前源码/声明吻合的定义位置，复用该证据；位置候选有反证时继续核对。
- **风险**：模板报错可能级联，也可能包含多个独立问题；note指向候选声明不等于该声明应被修改。
按最能解释当前失败的证据形成局部修复假设，再用原工程验证。类型可用与实现符合要求分别检查：任务要求保留的标量/向量路径或设备调用不能以另一条能编译的路径替代。见 [template-error.md](error-categories/template-error.md)。

## 方法 4：连贯修改与原配方验证

- **何时用**：一个错误需要动多处、或你不确定哪一处是关键修复。
- **怎么做**：每组有依据的连贯改动沿原配方验证，保留源码、配方和完整日志；工具入口按 SKILL.md 选择，已覆盖最终源码与目标的有效证据可复用。`new_compile_error`仅表示观察到不同错误，
可能是暴露的下游错误、另一独立问题，也可能由本次试探引入；先区分，再用新问题日志诊断。只有行号平移或同状态重编时复用已有诊断。真实编译开销大，不应每改一行或为取得某个标签就重编。
- **分阶段推进**：配置、生成、Host、Device、链接或打包依次解锁时，可先验证当前受影响阶段，不必预先猜完尚未暴露的源码错误。记录实际到达的阶段与新首错；确认局部修改有效后继续原配方。最终汇合的阶段证据仍须覆盖相容的最终源码、依赖和配置，且包含全部必需目标，不能以某阶段通过代替整条构建链通过。
- **区分已证问题与顺手清理**：连贯修改可以包含由声明或语言规则已证实的关联错误，不要求每处都先失败一次。但宏参数、生成语法或表面标点可疑时，要核展开后的语义；尚无诊断或静态证明，就不能称为“必然暴露的下一错误”。没有功能必要性的清理可留待独立维护，不计为本次额外修复成果。
- **何时别用**：环境不能真实编译（`environment_unavailable`）——那就靠静态推理，标注未验证。
- **风险**：`compile_passed`确认本次编译；`compile_failure_fixed`另需适用前态、同目标和必要源码覆盖。
缺历史时陈述当前结果与变化未知，不为fixed标签补调用。两者均不代替接口、功能或数值验收。

## 方法 5：假设检验（给深层排查一个收敛框架）

- **何时用**：第一次编译前反复查找同一候选，或修复过程中多种解释仍不能区分。无需等到两轮构建失败才检查调查是否停滞。
- **怎么做**：把待决问题具体化到当前工程，例如“这个编译单元是否注入了声明头”，而不是“整个宏框架如何工作”。在再次取证前明确：哪种结果会改变补丁、哪种结果会支持现有修法，或者该查询能补齐哪项必要验收。已有结果能回答这个问题时立即使用；这是一项决策检查，无需另写报告或每条命令重复说明。

取证后只保留得到支持的解释，并按SKILL.md决定修改、继续查证或构建。若结果没有区分候选，检查问题是否选错或证据来源是否有效；确有新范围、新版本或新调用链可区分时再搜索，不靠改变关键词重复同一零命中。知识页提供的是判别依据，实际声明与调用关系决定它是否适用；不是读完后继续照原计划穷举。

| 调查状态 | 下一步及边界 |
|---|---|
| 同一范围反复零命中，问题本身未变 | 核路径、符号归属和目标版本；需要时查对应知识页或换一个能区分假设的证据源。不把重复搜索或更多历史版本当作进展 |
| 本地与目标版本资料存在实际矛盾，生成头/注册副作用或ABI仍未说明 | 继续核条件分支、实际注入头、生成调用或适用版本；已有疑点未解决时不能因调查较长就猜一个修法 |
| 想确认实际架构、目标或源文件是否被编译 | 优先看本目标生成配置和真实编译命令；实际值缺失或矛盾时才追其配置来源，不由警告自动扩成平台源码审查 |
| 当前源码和用途已明确，只想让补丁与网上版本逐字节相同 | 停止与修复无关的历史、排版或接口重组；任务明确要求对齐特定版本或本地契约仍缺失时才继续 |
| 探针连续失败在自身缺路径、宏或链接依赖 | 继承原失败单元的完整参数，或回到原项目配方。探针自身错误不成为原工程根因，不能据它判定候选API不存在 |

搜索先取命中位置与必要上下文，再展开影响判断的完整声明或调用链；原始日志继续保存，不以截断输出替代验收证据。Tiling表示或头文件来源仍未确认时，分别取[Tiling判别](error-categories/tiling-consistency.md)或[头文件判别](error-categories/header-missing.md)中适用的区分方法。若下一步只能重述已知事实，结束这一条调查；继续已支持的局部修改、必要验证或对真正缺口的协作，不把停止调查当作任务已完成。

本方法不规定总搜索数、调用数或token上限。必要的依赖、类型、实现路径和生命周期调查应完成；仍无安全修法时按SKILL.md协作或说明具体缺口，不把“停止重复搜索”当成“必须立刻修改”。

## 使用边界

- 这些方法**都是可选的**；首次诊断、证据复用与换问题接续遵循SKILL.md，不在这里复制另一套流程。
- 修复主体是你：方法只帮你观察和收敛，判断与决策权在你。
- 修复结论需要实际编译和任务契约证据；只读到rc=0或成功标签仍需核实际目标、源码覆盖及未验证层。
