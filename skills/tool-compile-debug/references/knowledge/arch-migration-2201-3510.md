# 2201 / 3510 目标迁移核验

只有任务确定需要迁移时才修改目标。目标SKU、编译器架构和头宏分别核验；运行设备仅在具体补丁风险或原任务确需设备证据时核验。不能以宿主NPU型号代替编译目标，也不能把一次交叉编译通过说成真机运行通过。

现有 CMake/ASC 工程可在实际编译命令中使用编译器选项 `--npu-arch=dav-2201` 或 `--npu-arch=dav-3510`；msopgen 工程还需核对 `OpDef::AICore().AddConfig(...)` 及 `ASCEND_COMPUTE_UNIT` 等生成配置。沿工程采用的机制修改并复验完整命令链，不能只修改一个宏或环境变量后宣称迁移完成。

需要补充核对 SKU 与架构对应关系，且宿主提供相关技能时，调用 CANNBOT `npu-arch` 技能取得架构事实。技能通过宿主加载；上述编译器选项仍由实际构建命令传入。

固定以下事实再测试：

- 准确CANN版本/build、编译器身份、目标后端以及头库依赖；
- 同一最小正控与待测调用，保持namespace、dtype、布局、模板参数和入口可比较；
- 实际参与的TU/目标、完整argv、依赖和新对象证据，以及任务要求的link/package阶段；
- 仅当具体编译补丁风险仍需运行或数值证据时，再固定相应设备、合法输入、独立golden和判据；
能用现有源码、声明或依赖证据排除的风险，不增加NPU或数值测试。

SoftMax/Silu/Exp等同名接口的支持取决于入口与调用层；旧聚合扫描不能证明3510不可用。 Subnormal、舍入、溢出及精度模式也应按具体接口配置核验，不从架构短名统一推定。片上缓冲预算取实际依赖版本和目标平台配置，不把另一工程的tile或内存常量作为本工程答案。

交叉编译可在具备准确后端、头库及正控的机器进行。若要声明目标设备运行支持，需对应真机证据；数值正确也需相应验证，但这些不是只请求编译修复的固定门槛。更多入口问题见[头入口与目标](soc-arch-gating.md)。
