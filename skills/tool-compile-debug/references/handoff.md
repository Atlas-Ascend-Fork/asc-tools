# 交接与升级协议（停滞时）

编译修复停滞时，通过路由表协同基础技能补齐证据。本页是 [SKILL.md](../SKILL.md)「停滞时交接并带回证据」的实施细则：判定线、交接报告模板、路由所需的输入和输出、反模式。表中技能由 CANNBOT 提供，只有宿主可用且适合当前编译证据缺口时才加载；实际调用遵循宿主的技能机制，不假定仓库、安装目录或克隆方式。

需要某项知识时可直接调用相应技能，不必先失败两轮；以下判定线用于停止无进展的同路径修复。已有本地证据足以确定修法时，直接修补和验证，不为履行交接流程追加搜索。

本表只处理编译失败或本次补丁回归的取证。独立运行期、精度或性能请求直接交回调用方，不由本技能沿表分流、列出接管技能或启动排查；没有新编译失败或补丁回归证据时，不进入下列升级流程。

## 判定线

以下三条共同判定“同路径无进展”，用于提醒更换取证方法；不是调用基础技能的前置门槛。有会改变修法的知识缺口时，可在首次修改前协作取证：

1. **同一首错**（`primary_error` 相同或已核同一声明/调用根因）已过 **≥2 轮**完整的
「修改 → 原配方真实编译验证」，且各轮日志仍指向同一首错或根因。使用run_verify时，可结合失败状态（`same_error_remaining` / `compile_failure_remaining` / 反复 `new_compile_error`）核对；直接原命令构建的完整日志同样可用；
2. **无新证据**：没有新的源码事实、日志、环境变化或声明证据能区分现存假设；
3. 工具与构建配方本身可用——`environment_unavailable`、`case_not_reproducible`、超时/缺日志
属未确认验证，先按[脚本契约](using-scripts.md)读取reason、已有日志与覆盖证据，需要时补工具/构建配方/环境，不算源码修复失败轮次，也不表示原错已修好。

新问题（新编译单元、独立错误、推翻原定位的证据）回喂诊断重新开始计数；仅行号平移不算新问题。

### 非证据型停滞

两类场景不走≥2 轮判定线，但有各自的处置协议：

- **用户裁决挂起**：涉及换目标/改接口等需用户确认的选择，用户未响应时等待一段时间后，按宿主支持的结构化协议（若有）交回调用方，并附已验证事实与两个选项的影响分析；没有该协议时使用报告中的自然语言未决项。不擅自替用户选边，也不无限等待。
- **被引技能不可得**：宿主未提供所需技能，或当前调用机制不能访问该技能时，不查找固定路径、不克隆仓库、不把未执行的路由写成已完成。继续核对本地源码、SDK声明、构建命令和可用官方资料；只有这些路线仍无法补齐必要证据时，才在报告中注明「路由未执行（技能不可得）」及未决缺口并交回调用方。缺少某个技能本身不是停止修复的理由。

## 交接报告模板

由你（调用方）从最新诊断产物与各轮验证结果合并，写到报告目录（与 diagnosis/verify 产物并列），对外分享前过 `redact_bundle`：

```markdown
# 编译修复交接报告（tool-compile-debug）

## 1. 已验证事实
- primary_error / failure_stage / category：
- root_cause_localization（root_file/root_line/evidence）：
- version_compatibility / 目标 SKU（requested/log/device 三方对照）：
- 各轮验证：原命令、cwd、目标、实际退出码、编译与产物证据；使用verify时附transition、
  error_comparison（remaining/disappeared/observed_new）、built_target、contract_check：

## 2. 已尝试的修法与被证伪原因
- 每轮：改动要点 → 验证结果 → 为什么不足以修复（反证证据指针）

## 3. 未决假设与缺失证据
- 仍无法区分的候选、需要但拿不到的证据（环境/权限/版本/设备）及原因

## 4. 建议的下一个技能与理由
- 按路由表选择，写明停滞类型与期望该技能补齐的事实

## 5. 证据文件清单
- diagnosis.json / verify.json / report.md 等路径（含轮次标注）
```

## 升级路由细则（带去 / 带回）

调用时使用下表中的精确技能名（例如 CANNBOT `ascendc-docs-search` 技能），并由宿主决定如何加载或切换技能。表中“期望带回”是取证目标，不是任何宿主都必须实现的返回字段；调用方应把结果整理为报告中的证据与未决项。

每次停滞只选择一个适用且可用的技能，由宿主按需加载；只有它带回能区分假设的新证据时才回流并继续。没有新证据就结束该路由，不把整张表当作必须遍历的重试清单。

| 目标技能 | 带去 | 期望带回 |
|---|---|---|
| CANNBOT `ascendc-env-check` 技能 | env.json、preflight 输出、失败的构建命令 | 环境缺项与修复动作 |
| CANNBOT `ascendc-docs-search` 技能 | 完整符号名+namespace+实参类型+目标版本+SKU | 声明存在性、签名、示例、兼容性证据 |
| CANNBOT `ascendc-api-best-practices` 技能 | API 名+报错实参 | 参数限制与正确用法 |
| CANNBOT `npu-arch` 技能 | 目标 SKU、`__NPU_ARCH__`、门控裁决卡内容 | 代际特性与条件编译分支归属 |
| CANNBOT `ascendc-simt-best-practices` 技能 / CANNBOT `ascendc-blaze-best-practice` 技能 / CANNBOT `ascendc-regbase-best-practice` 技能 / CANNBOT `ascendc-tiling-design` 技能 | 报错上下文与路线约束问题 | 路线正确入口、结构与契约 |
| CANNBOT `ascendc-blaze-migration` 技能 | 原实现与迁移动机 | 迁移路径与改造步骤 |

带回的新证据可回流本技能重新诊断（同一问题的「升级→回流」不设次数上限，但每次回流必须携带新证据；无新证据的回流视为穷尽）。**新证据**指改变假设空间的新事实——新声明/签名、新门控或架构事实、新环境结论、新日志证据；重复检索得到的同质结果不算新证据。每次回流都要把新的 `failure_evidence.json` 或等价诊断证据作为下一次适用前态，同时保留最初失败前态，不能只保留最后一轮。

## 终局（路由穷尽）

把交接报告交回调用方或官方工作流：需要改变接口、算法或目标取舍的情况，按宿主实际支持的结构化协议交回；若宿主没有该协议，就在报告中明确列出需要用户决策的选项、已验证事实和影响。其余按编译修复的局部完成交还，附完整证据链。**不以无出口等待收尾，不向用户抛「建议自行尝试其他技能」后结束。**

## 反模式

- 为凑编译通过删功能、造 stub、改 golden、换无关 target——见 SKILL.md 行为红线，升级流程
同样适用；
- 伪造或美化交接报告（把未验证的推测写成已验证事实）；
- 适用协作技能可用时，只出报告不调用，或调用却不记录交接证据；技能不可得时按上文继续取证并记录缺口；
- 把升级动作当用户建议（应由你调用后带回结果继续工作）。
