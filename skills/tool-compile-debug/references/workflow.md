# 操作顺序参考

操作次序以 [SKILL.md](../SKILL.md) 为准，参数与返回以 [using-scripts.md](using-scripts.md) 为准。

## 操作入口

使用随包 `scripts/run.py` 或三个 shell 入口（diagnose/verify/redact），显式传工程、日志、输出和目标。
这些入口选择随包引擎并保护安装目录输出。直接导入随包引擎模块不属于稳定调用契约。

`SKILL_DIR` 来自本次宿主加载的 `SKILL.md` 所在目录；源码仓的 `harness/engine/`、`tools/`
不是运行时调用兄弟技能的路径前缀。不同工具调用不保证共享shell变量，每条命令设置实际路径，
或直接使用脚本绝对路径。`ASCENDC_DOCTOR_PYTHON` 可指定shell入口的解释器。

安装能力确有疑问时才执行下面的预检；已有同环境有效结果可复用，不能把预检当作工程编译：

```bash
python3 "$SKILL_DIR/scripts/preflight.py" --json
python3 "$SKILL_DIR/scripts/face_selfcheck.py" --json
```

这两个入口使用 `--json`，不是诊断入口的 `--json-stdout`。诊断默认不探测NPU，
`env.npu_probe_status=not_requested`、`env.npu_devices=null`表示未取得设备信息，
不是无设备；目标工具链可用即可交叉编译，运行验证另核实际设备。

## 诊断返回后如何使用建议

已有完整失败日志且不满足足证快路径时，第一步运行或复用轻量诊断，再按摘要取证；足证条件、参数及复用统一按[第一动作](../SKILL.md#第一动作解析已有日志)。日志须有首错解析依据，源码不整仓预载。诊断不另做构建，探针与修复后验证各自按证据缺口选择。

建议只在声明、任务要求和实际编译单元支持其前提时成立。`top_suggestion.patch`为空，
修改仍由调用方完成；未知类别或低置信度不是要求无限搜索的信号。

| `fast_path.kind` | 需要确认的事实 |
|---|---|
| `compiler_suggested_rename` | 候选声明、调用层与接口意图一致；Host代码不能仅因近名建议改调用Device入口 |
| `kb_known_symbol` | 当前SDK的header、namespace、signature及版本条件与KB一致 |
| `signature_deterministic_fix` | action前提成立，原功能及指定实现路径保留 |
| `needs_localization` | 定义、使用方和相关任务约束已对应；只补剩余缺口 |
| `ambiguous_fix` | 取得能区分候选的声明、目标或实际编译证据，不默认选边 |
| 空值或未知kind | 用首错及源码继续定位；无建议不表示不可修复 |

判断只需要当前问题的证据。调用位置和声明已矛盾明确时，先最小修改再原构建，
不用为获得更高置信度标签而查遍整个SDK。新日志推翻假设时撤销该假设并说明反证，
不撤回其他已证实有效的修复。

## 版本与目标的条件判断

轻量解析尚未探环境时，依据已有项目配置、实际编译器和日志判断；无需只为填字段调用全环境探测。版本歧义会改变修法时，按需inspect环境或调用CANNBOT补证；资料中的默认版本不能替代当前SDK。
运行诊断后同时看 `version_compatibility.status`、`resolution` 和 `environment_checks`，
不能仅凭 `status=match` 宣称所有建议已经过当前版本验证。

| 状态 | 处理 |
|---|---|
| `match` + `supported` | 在知识条目的 `since`/`until` 范围内使用建议，并核当前SDK声明与目标 |
| `match` + `ahead` | 保留通用排查；版本敏感修法以当前声明及真实构建为准，不擅自降级工具链 |
| `match` + `conflict_in_domain` | 披露日志与环境差异，核失败日志版本，并确认验收使用用户要求的工具链 |
| `mismatch` + `below_floor` | 低于知识下限；保留通用定位并按实际SDK修复，不套用域内版本敏感建议，明确说明不强制升级；迁移仅为需授权的可选方案 |
| 其他 `mismatch` | 按 `resolution` 核实版本或证据冲突，不因标签改换工具链 |
| `unknown` | 保留未知；只有修法依赖版本时才补工具链版本或目标声明 |

记录用户目标、工程配置和真实编译参数。`--soc`接收准确SKU，不接收架构号；
`--npu-arch`是编译器选项，不是技能调用。架构与SKU关系确有疑问时，
调用宿主可用的 CANNBOT `npu-arch` 技能核对事实。目标已确定时不替换为本机型号。

## 需要额外探针时

先由当前失败日志与实际构建配方提出待区分假设；只运行相应探针并记录其输入、目标、输出与覆盖，
不能把探针通过当完整工程通过。编译选项、include、宏、生成链和目标须来自当前失败任务，
不默认跑全矩阵。

## 验证方式

默认 verify 检验当前工作副本；独立 patch 才使用 patch 模式。dry-run 未真实编译，
不构成修复成功。轮次前态、每轮证据、新首错重诊与最终整链审核见[脚本使用契约](using-scripts.md#轮次证据闭环)。首诊、复用、换错误、反证撤销和停滞处置均不在本页复制第二套规则。

### 按补丁风险选择验证

验证归属及“原任务验收与补丁风险同时存在”时的优先级，以[入口验证和停止规则](../SKILL.md#验证和停止)为准。覆盖未决补丁风险的输入准备、执行和结果核对保持在本技能闭环内；受阻单列缺失前提，不把必要回归降为外部任务。下面的矩阵确定实际范围，不另设一套归属规则。

再从最终diff确定必要回归范围：**必须保留哪些目标与实现，补丁影响哪些使用路径，现有证据还缺什么。**
修改一行模板参数也可能改变数据布局或资源状态；是否需要构建、运行或SDK查证取决于这些问题，
不按改动行数、已有调用数或其他案例的测试数量决定。已有有效证据覆盖时复用，新增检查须补一项真实缺口。
多生成一份报告或重复同一成功命令不会自动增加正确性证据。
以下按本次实际变更选用，不是每题都执行的清单。

| 补丁影响 | 需要核对的证据 | 对应验证范围 |
|---|---|---|
| 声明可见性、名称或构建路由 | 被选中的声明和实现符合原接口，宏、类型和实际工具链未带来未解释的行为变化 | 原配方覆盖受影响的Host/Device及必要目标；无剩余功能风险且任务仅要求编译时，可据此交付 |
| dtype、shape、布局、序列化或Tiling传递 | 生产方与消费方的类型、字段、字节数及解释方式相容，最终diff没有绕过原计算 | 对受影响路径执行相关既有用例；涉及边界/填充时检查该边界，不能用另一个未受影响分支代替 |
| 队列、引用参数、缓冲区或同步 | 有效资源从何处建立、如何传给使用方、何时释放或复用；同名局部变量不是传递证据 | 核当前SDK的实际重载及状态要求，并用相关用例检查修改后的路径；单次运行通过仍不证明所有时序 |
| 多个目标或明确指定的实现路径 | 最终补丁逐一保留必需路径和接口，没有用一个成功目标替换另一个 | 构建要求的全部目标；本次补丁影响行为时回归相应路径，原任务独立运行验收交回调用方 |

先根据任务要求和上表确定必要范围，再采用原工程可信的验证入口，保留其输入和判定规则。
声明/名称修复已保留原行为且没有剩余补丁风险时，到完整编译证据即可交付本技能结果；
本次变更涉及数据、资源等未决风险时，必要回归不因编译已过而变成可选。原流程的数值验收单独保留状态。
配置、设备选择或数据准备失败后，必要验证仍待完成；在授权范围修正前提后继续，不把一次启动失败当作取消验证的依据。
必要运行检查与可选覆盖扩展分别记录；额外用例围绕尚未解决的风险选择，不默认遍历整套矩阵。
覆盖按实际的dtype、shape、mask等组合记录；不能把三个不同组合通过说成覆盖了另一组两个组合，
也不能用未受影响分支代替受影响分支。
输入生成、逻辑设备、数据契约及矛盾结果的处理见[运行结果的判读](pitfalls.md#需要运行验证时怎样读结果)。

结论先对应最终源码、目标及本次实际输入，再分别说明编译、实现约束和必要运行是通过、失败还是未完成。
执行退出码是记录事实，不直接决定这些结论，见[执行记录与验收结论](pitfalls.md#从执行记录到验收结论)。
必要运行受阻时可以交付已验证的编译范围，同时保留功能验收未完成；未要求的可选扩展不阻止编译交付。
已有比较失败则保留事实，补齐有效输入与因果证据后再判断它与补丁的关系；不能仅因编译通过就认定运行错误无关。

### 复用构建证据的边界

第一次执行就固定原配方的工作目录、目标和参数，保存完整日志与执行自身退出码；
失败日志也可复用：只为换成grep或查看另一段输出时读取原日志，不原样重编。
不同工具调用可能从不同目录启动，相对路径按此次实际工作目录解析。后台完成收据、管道状态及
日志缺口处理见[日志收集协议](pitfalls.md#日志收集协议)，已有完整收据无需另套包装后重跑。

副本或构建目录变化时，判断实际输入是否等价，不比较路径外观。主源码未变，但生成输入、
被选中的头/库、宏或编译/链接选项变化，都可能使旧收据不再覆盖当前任务。只有这些差异有疑问时，
才对照实际命令、相关依赖或有效构建配置；不用为每题新增全环境盘点。已证明等价就复用，
不等价则只补受影响范围，仍无法确认的部分保留为未确认。

同一最终状态的多个阶段收据可以共同说明覆盖范围；不同配置、依赖或源码状态的成功不能直接拼成
整体验收。增量构建显示无工作时，只有此前对应范围的有效编译证据仍适用，才能沿用该结论。
修复Host首错后才暴露生成调用、Device或链接错误时，按新首错补齐对应契约和验证；
这是取得新证据后的必要推进，不因调用增加而跳过，也不重启已证实无关的调查。

TBE/opbuild 等间接构建可能没有被收集器完整观察。按缺口核原生或子任务日志、实际输入及产物关联；
产物存在、文件时间或返回码只能各自提供部分证据。保留工具的原始状态，另列原生证据已确认的范围，
不要把缺失字段补成成功，也不要用另一配置的成功报告代替。已有材料不足时再补对应构建或记录。

### 预算与收尾

宿主给出修复时限时，把模型等待、取证和构建都计入。先用已有同配方耗时估算必要验证窗口；没有可信估计就保留未知，不套固定“每题应在几分钟内修完”的假设。时间不足时减少可选搜索、排版和额外测试，不能缩减原目标、类型或必需验收。

已有构建在运行时，读取它的日志和完成收据；不要因为一次工具等待返回而再起同样的构建。构建结束后，只核最终diff对应的原目标、原退出码与必要产物。配方本身没有要求的库或包装产物不因名字相似就成为新验收项。覆盖已成立就提交简短结论；未成立则明确缺口，不用反复列目录拖到会话超时。

首轮修改暴露新的独立错误时，保留有效修改并沿新首错续接。对于尚无可支持修法的复杂问题，定向查询未缩小候选就改变取证方法：核实际命令/宏分支，或携带当前矛盾调用对应基础技能。没有新证据时不轮流搜索近义词；仍未解决则交接候选、反证和下一条区分证据。

evals 定义位于 `evals/evals.json`。实际模型评测须由对应宿主和测试框架运行并保存证据；
结构校验不能替代原生激活或真实编译会话。
