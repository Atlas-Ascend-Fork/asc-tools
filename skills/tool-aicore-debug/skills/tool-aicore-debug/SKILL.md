# NPU AI Core 异常识别、索引检索与修复

先按用户目标确定范围：只定位时输出证据、候选原因和待验证项，不修改正式实现；定位并修复时执行完整四步；方法问答按问题查阅对应指南，不启动修复。

## 四条必守执行纪律

1. **只改生效源码**：通过源码里的注册宏（`IMPL_OP`、`OpDef`、`SetTiling`）和运行芯片型号锁定真正生效的入口与架构目录（如 910B/910_93 对应 `dav-c220 / arch22`），跳过未引用代码与其他芯片目录，不假设存在 `build.sh` 等特定脚本。
2. **隔离主从内存**：主控 CPU 代码禁止直接解引用设备显存指针，也禁止把主机虚拟地址直接传给核函数；核查指针真实位置与安全拷回方式按对应主控指南执行。
3. **分清主控报错与核内钳制**：违反入参契约或超出算子固定规格上限的输入，在主控直接返回错误码拦截；需要正常跑完的动态越界下标或超物理容量长度，在核函数内过滤或钳制，禁止截短合法输出。
4. **按证据推进，及时验证**：不因环境预装同名算子同样报错就误判源码无错；重复检查没有新证据时更换取证方法。仅在证据支持具体缺陷且任务允许修复时做最小修改，先回放原失败用例，再完成项目要求的相关回归。无法运行或尚未确认根因时，继续可行的静态分析并明确证据缺口，不因阅读步数或时间比例强制修改。

## 第一步：按报错与运行现象识别硬件表象分类

提取日志中的十六进制硬件 `error code`、`errorStr`、同步返回码、进程 `exit_code` 与独立十进制标量 `errcode`，按 **P1 -> P6** 命中即停确定**硬件表象分类**，随后打开 `references/index.md` 查找具体修复指南：

| 优先级 | 日志与报错特征 | 硬件表象分类（6 类标准名称） |
| --- | --- | --- |
| **P1** | 硬件错码含 `0x800000`、`0x8000`；或含 `read GM invalid`、`write GM invalid`、`SMMU`、`mte_biu_rdwr_resp`、`dcache_biu_response`、`fixp_err_out_write_overflow`、`biu_l2_write_oob`；或标量 `errcode ∈ {1, 141}` | `全局显存访问异常` |
| **P2** | 硬件错码含 `0x4000000000000000`、`0x4000`、`0x200000000`、`0x1000000000000`、`0x1000000008000`、`0x4000000000`；或含 `ub address out of bounds`、`wrap_around`；或标量 `errcode ∈ {24, 26, 42, 47, 48, 93, 103, 124, 125, 154}` | `片上缓存越界` |
| **P3** | 硬件错码含 `0x10`、`0x10000`、`0x1000`、`fixp_error0=0x9e`、`fixp_error0=0xa0`；或含 `illegal instruction`、`ADDR_MISALIGN`、`misalign`、`INSTR_ILLEGAL_CFG`；或标量 `errcode ∈ {30, 31, 35, 36, 53, 101, 126}` | `指令非法或地址未对齐` |
| **P4** | 同步返回码 `507014`（`aicore timeout`）；或进程超时 `exit_code=124`（`stderr` 为空或含 `timeout or trap error`）；或含 `rdwr_cflt`、`padding_cfg`；或标量 `errcode ∈ {14, 39, 41}` | `核函数超时挂死` |
| **P5** | 含 `div0`、`neg_sqrt`、`ln_nonpositive`、`cube_invld_input`、全 `NaN`/`Inf`；或标量 `errcode ∈ {3, 9}` | `数值异常`（此前未命中 P1~P4 时，无论是否伴随硬件报错） |
| **P6** | `exit_code=0`（或主控返回码不符）但出现越界索引、精度失真、跨调用脏数据或副输出残留 | `无硬件报错的静默结果或返回码异常` |

- **易混码区分**：`stderr` 十进制标量 `errcode=124` 是 UB 写越界（走 **P2**）；操作系统 `exit_code=124` 是超时挂死（走 **P4**）。`errcode=41` 常伴随核挂起，优先查三维加载对称补齐可行性。`errcode=141` 按 `SetAtomicAdd` 生效状态区分原子加写越界与普通矩阵写回越界。`errcode=14/39` 同属 L0B 读写冲突。
- **上板前静态检查与缺线索边界**：仅提供源码无运行日志时，打开 `references/index.md` 第七节按模块做静态核查。未提供源码时只输出分类与排查方向，不编造行号；仅有 `exit_code=1` 无 `stderr` 时提示收集 `stderr` 或查阅 `cannbot-knowledge` 的 `msaicerr`/`asys`/`msnpureport` 采集方法。

P1~P6 是路由优先级，表象不等于已确认根因。十六进制码须按完整字段识别，不按字符串子串匹配；复合码按目标芯片的字段定义核对，尚未核实则保留不确定性。

## 四步定位与修复流程

1. **Step 1（定表象并查索引）**：对比报错信息与成功/失败输入差异，输出**硬件表象分类**，打开 `references/index.md` 定位匹配的 **1~2 篇** `references/guides/*.md` 专题指南。
2. **Step 2（对照指南核查源码）**：按指南中的检查清单先查主控源码（`op_api` / `op_host` / `infershape`），主控无疑点再按 `tilingKey` 查激活架构核函数；规格或 API 不确定时定向查 1~2 处 `cannbot-knowledge` 或本地 CANN SDK 头文件。
3. **Step 3（最小修复并验证，仅修复任务）**：根据已确认的缺陷，避开指南列出的常见误区，完成最小源码修改，先回放原失败用例，再完成项目要求的相关回归。只定位任务跳过本步。
4. **Step 4（输出缺陷根因分类）**：按最终实际修复层输出**缺陷根因分类**：① `主控入参校验缺失`、② `主控切分计算或状态错误`、③ `核函数访存下标或空指针缺陷`、④ `核函数流水同步或缓存一致性缺陷`、⑤ `编译链接或芯片架构配置错误`。
