# 按阶段执行的数据定位示例

以下示例分别演示模型 Dump、重复单算子调用和 kernel 直调。每个示例均说明工程输入、采集方案、阶段产物、数据表现及结论适用范围。请求名、shape 和数值均属于示例工程；实际任务应根据自身运行入口、golden 和判据独立核验，不直接套用示例结论。

三个示例均演示有 golden 的完整比对任务。只咨询配置、只采集或只解析时，完成相应产物即可交付，不要求走完六个阶段，也不要求先提供 golden。完整字段见[acl.json 参数参考](acl-json.md)，stats 与 tensor 的用途见[数据处理路线](compare.md)。

示例工程均有运行入口、`inputs.npz`、`golden.npz` 和记录观察点及判据的 `manifest.json`。这些文件名是示例工程的约定，其他工程可沿用已有组织方式。本页中的逐元素判据均为 `abs(actual-golden) <= 1e-5 + 1e-5*abs(golden)`，非有限值不一致单列；统计筛查也使用该工程单独声明的 `atol=rtol=1e-5`。两类阈值在本例中数值相同，不代表含义相同，更不是 Skill 的默认阈值。坐标均从 0 开始，文中的区间包含两个端点。

| 场景 | 需要解决的难点 | 主流程路线 |
| --- | --- | --- |
| 双分支模型 | 96 个逻辑观察点、融合节点与 Cast 配对、局部差异传播 | 1 → 2A(stats) → 3 → 2A(tensor) → 4 → 5 → 6 |
| 多轮 ACLNN 算子链 | 24 个请求、同名 API 重复调用、有限误差与 NaN 并存 | 1 → 2B(stats) → 3 → 2B(tensor) → 4 → 5 → 6 |
| 多 shape kernel 直调 | 初始 Host 尚未接入 Dump、统计盲点、两个输入的身份核对 | 1 → 2B(tensor) → 4 → 5 → 6；已有 stats 时可先做 3 |

配置模板见[配置与采集](capture.md#四份可改写的配置)，解析、官方比对与辅助脚本命令见[数据比对](compare.md#官方工具怎样选)。工作目录中的配置、日志、raw/CSV、转换 NPY、配对记录、官方结果和报告按轮次保存；具体 Dump 文件名和数量由实际运行决定，不根据示例推定。

## 场景一：双分支模型，从统计候选走到融合节点配对

### 阶段 1：确认工程和参考范围

输入工程加载 `build/model.om`，Host 通过首次 `aclInit` 接收配置，再执行 `aclmdlLoadFromFile` 和 `aclmdlExecute`。模型有两个分支，各连续执行 12 次缩放，输入和观察点 shape 均为 `[7,136]`，4 个请求使用各自的数据。

| 输入材料 | 能确认什么 |
| --- | --- |
| 运行入口及实际加载的 `model.om` | 走模型路线 2A；本例文件加载的模型名为 `model` |
| `inputs.npz` 的 `requestN/x`、`constant/zeros` | 请求输入与自定义节点的常量输入参考 |
| `golden.npz` 的 `requestN/b0_n00` 至 `b0_n11`、`b1_n00` 至 `b1_n11` | 4 × 24 = 96 个逻辑观察点都有参考 |
| `manifest.json` | 任务指定的最终输出是每请求的 `b0_n11`、`b1_n11`，共 8 个；给出对应关系和判据 |
| 已有模型 JSON；缺少时从该 `.om` 导出 | 编译后的融合节点、各输出索引和 Cast 连接 |

为便于核验，本例在编译前将各逻辑节点的结果显式保留为模型输出；任务的最终输出仍以上述 8 个为准。一般业务模型不保证保留每个中间点，不能据此假定所有原始层均可单独 Dump。

本阶段输出：运行命令、4 个请求的输入身份、模型身份、96 个可比观察点及 8 个最终输出的列表。尚未采集，不填写实际 raw 路径或宣布异常节点。

### 阶段 2A → 3：采模型 stats，确定补采范围

本例采用 stats 展示多观察点筛查；张量本身并不大，若直接采 tensor 的成本更合适，也可跳过统计轮。配置以模板 A 为基础，为同时观察边界输入统计，将方向改为 `all`：`model_name=model`、`dump_op_switch=off`、`dump_level=op`、`dump_mode=all`、`dump_data=stats`。通过工程已有入口运行，按请求保存 CSV 和日志。

阶段 2A 输出原生 CSV 与运行记录；阶段 3 按请求、节点、输出索引、shape 和 dtype 配对 golden，得到：

| 范围 | 统计筛查结果 | 本轮判断 |
| --- | --- | --- |
| request0 的全部观察点 | 已比较统计无差异 | 作为正常对照候选，仍需 tensor 验证 |
| request1—3 的 `b0_n00…b0_n11` | 36 个逻辑输出观察点存在统计差异 | b0 分支值得核验，不能直接把 36 点都当独立首错 |
| 四个请求的 b1 分支 | 已比较统计无差异 | 暂无统计候选，不能据此宣布逐元素通过 |

上述 36 表示观察点数量，不代表 CSV 文件数量。一个文件可以包含多行，同一逻辑点也可能涉及融合输出和 Cast 等不同表示。

阶段 3 交给下一轮的范围是：异常请求的 b0 首节点输入输出、后续传播点、任务最终输出，以及用于核验的正常请求和 b1 观察点。本例完整核验了全部 96 个观察点；实际任务若只检查部分，就只报告该部分覆盖。

### 回到阶段 2A，再进入阶段 4：采 tensor 并解决融合映射

保持输入、模型与 `op` 层级一致，使用 `dump_mode=all`、`dump_data=tensor` 和新目录。本例为复核全部 96 个观察点，保持模型范围且不设置 `layer`；只需局部定位时，可以按模板 B 指定候选与必要边界，但报告覆盖范围也随之缩小。采集后由官方 `convert` 得到 NPY，再建立对应关系。

| 要比较的逻辑数据 | 实际身份与参考 | 必须核对的内容 |
| --- | --- | --- |
| `request1/b0_n00` 输出 | `ProbeAffine.b0_n00` 的 output.0 ↔ `golden.npz` 同名 key | 请求、节点、方向、索引、shape 与布局 |
| `b0_n00` 的 input.0 | 实际输入 Dump ↔ `inputs.npz` 的 `request1/x` | 不能拿 Host 输入文件本身代替设备侧输入证据 |
| `b0_n00` 的 input.1 | 实际常量 Dump ↔ `inputs.npz` 的 `constant/zeros` | 常量也要核对，不能遗漏第二输入 |
| `request1/b1_n11` | 本例融合节点 `b1_n06b1_n07b1_n08b1_n09b1_n10b1_n11` 的 output.5，经 `trans_Cast_24` 输出 | 先由模型图确认连接，再核对保存数组；不能仅凭名称接近或数值相似配对 |

b1 的融合输出为 FP16，后续 Cast 输出为 FP32；本例图连接与数组核验证实两者无损对应，因此可以解释同一逻辑观察点的不同表示。其他模型若 Cast 有损、节点被完全融合消除或缺少映射，就保留未匹配项。

阶段 4 输出：转换 NPY、可信的 raw ↔ NPY ↔ golden 对应关系，以及原始/转换类型说明。即使某个融合输出能配对，也不能据此虚构融合 Kernel 内部的独立观察点。

### 阶段 5 → 6：确认输入、误差区域和传播

将已确认的 NPY/golden 配对整理为 tensor pairs，按阶段 5 调用 `summarize.py`，保存官方 `file_compare` 指标、坐标与完整掩码。已有有效结果时直接引用，不为获取坐标构造整网参考目录。得到的代表性结果如下：

| 观察点 | 超差数 / 元素数 | 最大绝对误差 | 数据层含义 |
| --- | ---: | ---: | --- |
| request0/b0_n00 | 0 / 952 | 0 | 该请求在该点通过 |
| request1/b0_n00 | 184 / 952 | 2.4375 | 最前端计算节点输出已出现差异 |
| request1/b0_n11 | 184 / 952 | 4.873809814453125 | 该分支最终输出仍在相同位置超差 |
| request1/b1_n11 | 0 / 952 | 0 | 已核验的另一分支最终输出通过 |

request1—3 的 `b0_n00` 两路实际输入均与参考逐元素一致。完整掩码给出的异常区域是第 5 行列 88—135，加上第 6 行全部 136 列，共 48 + 136 = 184 个位置，约占 19.33%。例如 request1 的 `[6,50]` 处，actual 为 4.875，golden 为 2.4375。后续 b0 各点的掩码保持相同；这些结论来自完整数组核验，不能只从这个 Top-K 样本推导。

报告可写：4 个请求中 3 个异常，最早可观察偏差位于 b0 首节点输出；全部必要输入已核验，b0 后续各点在相同位置持续超差，8 个任务最终输出中 3 个超差。位置持续不证明下游没有新增误差。request0 的全零输入通过只证明这组数据满足判据，不能据此证明所有输入均正确。保留配置、统计筛查结果、融合配对说明、官方结果、完整掩码和报告，停止于数据层结论。

## 场景二：多轮 ACLNN 调用，区分首异常、传播和 NaN

### 阶段 1：确认请求、调用链和完整输入

输入工程包含 24 个请求，shape 循环覆盖 `[8,64]`、`[13,64]`、`[9,128]`、`[7,136]`。每请求执行 4 轮，每轮依次为：

```text
上一轮结果（首轮为 x） + offset → nK_a
nK_a + operand                  → nK_b
nK_b × post_scale               → nK_c
```

Host 分别调用 `aclnnAdd`、`aclnnProbeAdd`、`aclnnMul`，最后一轮输出 `n3_c` 是任务最终输出。每请求有 12 个观察点，共 288 个；golden 覆盖这些输出，`inputs.npz` 保存各请求的 x、offset、operand 和 post_scale。`aclnnAdd` 的标量属性也从 Host 元数据核对。

本阶段输出：24 个请求及调用依赖、288 个参考观察点、24 个最终输出和两路输入的来源。确认走单算子路线 2B。不能将请求内四次 `aclnnProbeAdd` 混成一个调用，也不能只根据四个同名文件的排序认定轮次。

### 阶段 2B → 3：筛查重复调用

配置采用模板 D：`dump_op_switch=on`、`dump_mode=output`、`dump_data=stats`。从新进程首次初始化前启用 Dump，按请求保存目录与 Host 的 `STAGE nK_a/nK_b/nK_c` 记录，核对本轮 CSV 中的调用标识。工程支持可选的采集窗口，但内部模型已缓存时，中途启用未必生效。

原生统计与对应 golden 配对后，得到：

| 请求组 | stats 观察 | 交给下一轮的问题 |
| --- | --- | --- |
| 6 个 `[8,64]` 请求 | 已比较统计无差异 | 作为正常对照，用 tensor 确认 |
| 12 个 `[13,64]` 或 `[9,128]` 请求 | `n0_b` 开始出现均值等统计差异 | 输入是否已经不同，还是该调用输出首先出现差异？ |
| 6 个 `[7,136]` 请求 | `n0_b` 的 NaN 计数为 191，golden 为 0 | NaN 是否来自输入，出现在哪些位置，是否继续传播？ |

阶段 3 输出候选请求与调用，下一轮至少覆盖 `n0_a`、`n0_b`、相关实际输入和 `n3_c`。需要报告全部 24 个最终输出的状态时，应覆盖它们；不能将一次代表性请求的结果推广为其余请求均已验证。

### 回到阶段 2B，再进入阶段 4：保留调用标识和两路输入

改用模板 C 的 `all/tensor`，保持同一组请求和计算参数，使用新目录。原始输入与输出可能分别落在不同记录编号的 raw 中；按 Host 调用记录、方向、索引及 shape 配对，再用官方工具解析。

以 request1 的首候选 `n0_b` 为例，阶段 4 应得到以下对应关系：

| 实际 Dump 张量 | 参考文件与 key | 目的 |
| --- | --- | --- |
| `n0_b` 的 input.0 | `golden.npz`：`request1/n0_a` | 验证传入目标调用的上游结果 |
| `n0_b` 的 input.1 | `inputs.npz`：`request1/operand` | 验证第二输入，不能以主输入正常代替 |
| `n0_b` 的 output.0 | `golden.npz`：`request1/n0_b` | 判断当前输出是否超差 |
| `n0_a` 的输入与 output.0 | x、offset 及 `request1/n0_a` 的参考 | 检查更早边界，避免把传播误认成首错 |
| `n3_c` 的 output.0 | `golden.npz`：`request1/n3_c` | 验证任务最终输出 |

阶段 4 输出每份实际 raw、转换 NPY、参考 key 的对应记录。`input.1` 必须指向真正的第二输入文件，不能复制 `input.0` 路径后只修改标签。

### 阶段 5 → 6：分别报告有限误差和非有限值

将已确认的配对交给 `summarize.py`，按工具调用时限分批；每对结果随完成保存。官方比较与逐元素检查确认：18 个异常请求的 `n0_a` 正常，`n0_b` 两路实际输入与参考一致，`n0_b` 输出首次超差。代表性数据如下：

| 请求 / shape | `n0_b` 超差数 | 有限值最大绝对误差 | 非有限值不一致 | 后续情况 |
| --- | ---: | ---: | ---: | --- |
| request0 / `[8,64]` | 0 / 512 | 0 | 0 | 12 个观察点均通过 |
| request1 / `[13,64]` | 166 / 832 | 0.125 | 0 | `n3_c` 仍有 166 个超差，最大绝对误差 0.1171875 |
| request2 / `[9,128]` | 230 / 1152 | 0.125 | 0 | 失配位置沿后续调用保持 |
| request3 / `[7,136]` | 191 / 952 | 0（仅有限子集） | 191 个 NaN 对有限 golden | NaN 传播到最终输出，不能写成整体误差为 0 |

完整掩码确认这些异常位置满足 `(row + col) % 5 == 0`。这条区域描述是核验所有元素后得到的结果，不能预先用它筛数据。request1 的 `[0,0]` 处，actual 为 0，golden 为 0.125；request3 的相应位置 actual 为 NaN，golden 仍为 0.125。request1/n0_b 的官方余弦相似度约为 0.999791，但仍存在 166 个逐元素超差。

报告可写：24 个请求中 18 个异常、6 个正常；首个可观察输出偏差位于各异常请求的 `n0_b`，输入证据和更早的 `n0_a` 均已核验；后续调用的输入与上游输出衔接，完整超差位置保持一致，但不能据此排除后续新增误差。分开列出有限误差、NaN 数量和最终输出覆盖，不将 288 个观察点称为 288 份 CSV，也不将它们当成 288 个最终输出。输入中的特殊数值可以作为数据现象描述，不推断计算代码的错误机制。

## 场景三：多 shape kernel 直调，接入 Host 后直接核对坐标

### 阶段 1：确认已有运行入口与缺失的采集接入

输入工程有 32 个请求、8 种 shape，每个请求只执行一次 `launch_probe_channel`，其内部封装 `probe_channel<<<...>>>`。每次计算目标为 `y[row,col] = x[row,col] × operand[col] + 0.125`，golden 覆盖唯一输出 `requestN/y`，输入参考来自 `inputs.npz`。

| 已有信息 | 实际含义 |
| --- | --- |
| 可运行的 Host 与预构建计算库 | 计算能够执行；本次只补 Host 采集接入，不修改计算体 |
| 首次 `aclInit` 已能读取 JSON | 可以配置 Dump，但初始 Host 尚未提交具体张量采集 |
| x 和 y 为连续二维 FP32，operand 为连续一维 FP32 | 可以从真实设备地址、shape、stride 和 stream 构造描述 |
| `opType=ProbeChannel`、`opName=target` 及独立请求目录 | 标识本次调用，不能将手工名称当作模型图节点 |
| 最大输出为 `[11,256]`，约 11 KiB | 每请求只有一个小输出，直接采 tensor 足以核对坐标，无需先做 stats |

本阶段输出：2B 直调路线、待补的 Host 接入点、实际张量描述及请求对应关系。`aclInit` 接受 JSON 不代表具体张量已完成采集。

### 阶段 2B：先接入，再采输入输出 tensor

采用模板 C 的 `dump_op_switch=on`、`dump_mode=all`、`dump_data=tensor`。按[直调 Host 接入](capture.md#kernel-直调的-host-接入)核对配套接口与依赖，用已有设备缓冲区构造三个张量描述：

| 张量 | shape | 连续 stride | Dump 身份 |
| --- | --- | --- | --- |
| x | `[rows,columns]` | `[columns,1]` | input.0 |
| operand | `[columns]` | `[1]` | input.1 |
| y | `[rows,columns]` | `[columns,1]` | output.0 |

本例均使用 FP32、ND、viewOffset=0，storage shape 与逻辑 shape 一致。实际接入保留原 launch、地址与计算参数，在其两侧加入采集：

```cpp
// inputTensors/outputTensors 由上述真实张量元数据和设备地址创建。
check(aclDumpOpTensors(opType, opName, inputTensors, 2, 0, stream));
launch_probe_channel(x, operand, y, length, columns, stream); // 原有调用保持不变
check(aclDumpOpTensors(opType, opName, outputTensors, 0, 1, stream));
check(aclrtSynchronizeStream(stream));
// 同步完成后，再按工程流程销毁张量描述和释放设备缓冲区。
```

这是接入位置示意，实参采用工程原实现。本例通过已有 `build_host.py` 重建 Host，再由 `run.sh` 执行；真实项目沿用自己的构建和运行入口。先用少量请求检查采集，再完成任务所需覆盖，正常和异常状态由后面的实际比较确定。若返回 0 但目录为空，应检查启用开关、首次初始化，以及是否提交了采集任务。

阶段 2B 输出配置、Host 接入说明、运行日志和原始 tensor Dump。本例每请求有输入、输出两份 raw，输入 raw 含两个张量；32 个请求得到 64 份 raw，不能按“一个 raw 等于一个张量”统计。这些数量用于解释本例，其他工程以实际落盘为准。

### 阶段 3：本次直接 tensor 路线跳过

本轮不采原生 stats，报告写“未采集”，不能将后续从 NPY 计算的摘要列成原生 CSV。

若接手的是已有原生 stats 的同类任务，可先进入阶段 3：这组数据的 Max/Min/Avg 和 NaN/Inf 计数可以与 golden 相同，但元素位置已经不同。统计相同只能说明没有发现摘要差异，仍应转到 2B 采 tensor。这个分支不要求为直接 tensor 的任务额外补跑 stats。

### 阶段 4：确认三个张量各自的对应关系

用官方 `convert` 解析每请求的 raw，本例得到 96 份 NPY：32 个输出、64 个输入。按请求及元数据逐项对应：

| 转换数据 | 参考 | 核对重点 |
| --- | --- | --- |
| input.0 | `inputs.npz` 的 `requestN/x` | 二维 shape、FP32、ND、真实计算前输入 |
| input.1 | `inputs.npz` 的 `requestN/operand` | 一维 `[columns]`，不能错误引用 input.0 |
| output.0 | `golden.npz` 的 `requestN/y` | 二维输出；NPY 与 golden 的逻辑布局一致 |

阶段 4 输出完整的张量配对记录。同一请求中所有涉及 input.1 的记录都要指向该请求真实的 operand 数据，不能在报告的一处写对、另一处写错，也不能跨请求复用输入文件；Host 回拷的 `target.bin` 仅用于复现，不替代 Runtime Dump。

### 阶段 5 → 6：用完整掩码判断位置错乱

按阶段 5 将各请求的输入输出配对交给 `summarize.py`，由它保存官方指标并核对每个元素。本例结果为 24 个异常请求、8 个正常请求；异常请求的 48 份必要输入均与参考一致。代表性输出如下：

| 请求 / shape | 超差数 / 元素数 | 最大绝对误差 | 完整超差区域 |
| --- | ---: | ---: | --- |
| request0 / `[1,64]` | 0 / 64 | 0 | 无 |
| request2 / `[3,64]` | 128 / 192 | 4.8984375 | 第 1—2 行全部列 |
| request4 / `[17,128]` | 2048 / 2176 | 28.79296875 | 第 1—16 行全部列 |
| request7 / `[11,256]` | 2560 / 2816 | 59.578125 | 第 1—10 行全部列 |

所有异常输出第 0 行在判据内，第 1 行到末行的全部列超差，即 `(rows-1) × columns` 个位置；双方均无 NaN/Inf。request2 的 `[1,22]` 处 actual=0.46875、golden=5.3671875，绝对误差为 4.8984375。完整区域必须来自整张掩码，不能从这一个坐标推断。

报告可写：该次直调的两路输入已核对一致，输出 y 是本次可观察到的异常边界；所有单行请求通过，多行请求在第 1 行起发生位置差异。各请求独立执行，y 又是唯一最终输出，因此没有已观察到的后续传播；Kernel 内部从哪一步开始偏离仍未知，不进一步查源码或修复。输入一致时应描述“误差指标为 0、余弦相似度为 1”，不能写“全部指标为 0”。

## 共同的交付检查

- 运行摘要能够说明选择 2A 或 2B 的依据，阶段跳过和补采都有明确原因。
- CSV/raw 的采集身份、转换 NPY、golden 文件/key 和比对结果可以对应；观察点数、文件数和最终输出数分别统计。
- 使用 `summarize.py` 时，按实际配对保存 `summary.json`、官方结果和 `mismatch-<序号>.npy`；缺少逐元素判据时不生成超差掩码或 PASS。
- 模型融合、多次调用、直调描述各自完成必要核验；未匹配项保留缺口，不通过推测补全报告。
- 结论来自实际比较，覆盖多少就报告多少；示例中的异常区域、shape 和数值不作为其他工程的判断规则。
