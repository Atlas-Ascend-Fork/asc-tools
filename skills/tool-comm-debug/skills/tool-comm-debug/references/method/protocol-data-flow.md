# 通信数据流与完整输出核查

适用：多 rank 通信正常返回但数据不符，或首轮正常而后续调用错误。先读公开功能契约、输入元数据与输出日志；不根据一条 mismatch 自动判为跨 rank API 参数不一致。源码证据指向用户自研引擎时，结合[引擎协议故障](../symptoms/comm-engine-protocol-fault.md)核查。

按当前证据选择下列相关项，不要求每项重新采证或重复阅读。已有精确数据流证据时，直接定位并修复；无法确认的接口含义再定向检索。

## 最小证据与定位

1. **明确结果来自哪里**：把输入 → 设备输入 → 通信暂存 → 远端访问/归约 → 设备结果 → 落盘输出串起来。记录每段的所有者 rank、轮次、有效元素数、dtype 与缓冲容量。读取侧视角与存储侧视角分别写明；同一标量名不保证语义相同。
2. **核对实际字节区间**：每次搬运/归约展开源与目标的基址、偏移、长度和单位，区分元素数与字节数。检查各块并集是否恰好覆盖要求输出，是否有空隙、重复、超出容量或只覆盖整块；同时核对生产方布局和消费方实际访问区间。对齐或分段规则来自源码与API契约，不猜固定常量。
3. **核对跨 rank 数据归属**：从公开算子语义确定每段结果需要哪些来源与目标，核对写入、读取、保留与归并的对应关系。不要把本端 rank、对端 rank、目标 rank 或逻辑分片编号互换，也不要把某一种合法算法的槽位约定套用所有实现。
4. **核对跨调用生命周期**：从上次完成到本次消费追踪缓冲与通知状态。明确哪些对象跨轮复用、哪次输入写入哪一区域、消费的是哪次写入，以及归约前应有的初始值。首轮正确只是线索；需用实际发布/消费关系证实陈旧数据、累加残留或生命周期错误，不能直接套用修复。
5. **保留执行语义**：修复必须保持公开要求的引擎与设备数据面、全部合法输入和调用轮次。同步或资源参数仅在证据指向时修改；记录改动如何恢复上述不变量，不以“编译成功”代替论证。

AIV搬运长度/尾部证据明确时，按需读[GM/UB对齐核查与官方接口链接](aiv-transfer-alignment.md)；不做全SDK检索或无证据API试错。

## 核内搬运与缓冲复用

源码证据指向 AIV/MTE 流水时，再核查这一层；不要把所有数值错误归为同步问题。如果程序提供通信中间结果，先找它与最终结果中的第一处差异，区分搬运阶段和后续计算阶段。

- 沿同一块实际存储列出“本次写入 → 就绪通知 → 消费 → 归还 → 下次覆盖”。同时记下流水方向、事件 ID、缓冲槽和当前轮次，不能只数 Set/Wait 是否成对。
- 确认通知对应哪些**已经完成**的操作。SetFlag 约束的是源流水中的前序操作；一个位置靠前的通知不证明后续搬运已经完成，也不阻止源流水继续发出后续工作。具体语义以现场 SDK 和目标型号为准。
- 从下一次覆盖反查所有消费者：消费方的最后一次访问完成后，缓冲才可复用。就绪和归还分别证明两个方向的依赖，不能互相替代。
- 展开内层搬运循环与调用者的外层循环。一次外层调用可能多次使用同一槽；只在函数末尾或外层分块结束时等待，未必覆盖中间复用。也不能把两个不同层级的槽号当成同一对象。
- 核对首次使用、尾块、最后在途任务和下一次调用。WaitFlag 会消费对应的硬件标志，重复使用事件时要能解释它属于哪一轮；不要用一次正常返回推断所有中间依赖成立。核内流水通知也不自动证明跨核、跨 rank 或缓存可见性条件。

接口语义参考[官方 SetFlag/WaitFlag 文档](https://www.hiascend.com/document/detail/zh/CANNCommunityEdition/910/API/ascendcopapi/docs/api/SIMD-API/%E5%9F%BA%E7%A1%80API/%E5%90%8C%E6%AD%A5%E6%8E%A7%E5%88%B6/%E6%A0%B8%E5%86%85%E5%90%8C%E6%AD%A5/SetFlag_WaitFlag_ISASI.md)。该链接为 CANN 9.1 文档，且 ISASI 接口与体系结构相关；迁移时仍需核对现场版本，不能据此宣称所有 SKU 都支持同一实现。

## Hcomm 的提交边界与实际实现

遇到 Hcomm 的 `OnThread` 调用，先确认当前产品、通信引擎和已安装版本的提交规则。CANN 9.1 文档及 Hcomm 9.2.0-beta.2 源码随附文档要求 A2/A3 使用批模式：在同一个主机线程中成对调用 `HcommBatchModeStart/End`，批量操作到 End 才提交。不要把 A5 支持的立即执行模式套给 A2，也不要因一次裸调用跑通就推断接口合同允许它。此规则针对这些 Hcomm 数据面接口，不是要求给任意 ACLNN/AIV 算子外加批模式。迁移其他版本时重新核对对应文档。

如果等待方已提交却等不到发布方，除了检查通知编号，还要确认生产、搬运和等待所在的实际 stream 都进入了本次提交。主机函数返回成功只说明相应调用成功，不等于整条设备依赖链已经提交或完成；把实际调用、提交日志和设备侧等待对应起来，再判断丢任务、缺同步还是上游失败。

修改底层库时，先核对进程实际加载的库及目标 API 的符号来源，再沿现场产品分支找实现。同名类或 API 可以分流到不同后端，源码里存在某个方法不等于当前设备执行它。修复后确认修改的源文件重新编译并链接进运行库；旧对象、另一份已装库或错误的搜索路径都可能使“补丁编译通过”与实际行为脱节。

参考：[官方批模式接口与产品约束](https://www.hiascend.com/document/detail/en/CANNCommunityEdition/910/commlib/commopdev/docs/en/api_ref/comm_opdev/data_plan_api/cpu-cpu_ts-aicpu_ts/others/HcommBatchModeStart.md)。任务标签的缓存语义仍需看当前版本，不由标签名字推断，也不把数值错误自动归因于缓存。

## 通知与实际资源

遇到 Hcomm 通知停滞，先弄清当前通知是否计数、等待是否消费或复位。名称相近的 Event、Notify、软 flag 不一定有相同语义，不能把广播事件或消息队列的经验直接套过来。核对当前 SDK、创建参数、日志或已有最小验证，再判断协议是否成立。

- 按实际的 rank、thread/channel 句柄、通知索引和所属轮次追踪发布与消费。逻辑变量名不同，不保证底层资源不同；有别名时，先合并为实际 stream 或通道，再画等待关系。
- 对二值或消费型通知，连续发布不等于积累了同样数量的可消费消息。即使总 Record/Wait 次数相等，也要检查前一次尚未消费时，是否又复用了同一槽。
- 分开核对数据缓冲容量与同步资源容量。能容纳一批数据，不代表能同时保留这一批的所有就绪状态；缓冲已经写完，也不代表等待方仍能区分每次发布。
- 核对跨 rank 动态子域或团队（如 team split）的槽位协商与设备寻址一致性：当 Host 动态分配槽位索引并在设备侧按该索引偏移寻址同步池或团队元数据时，各成员的本地空闲位图可能因先前非全员子团队（如单 rank 局部团队）的存活占用而不同。仅在各 rank 本地独立选取首个空槽会导致同一新团队在不同 rank 取得不同槽位并在 kernel 同步点永久互等；修复须对全体新成员的可用槽位求交集以协商一致的共同空槽，同时保全各 rank 仍存活的既有团队槽位不被覆盖。
- 修复可以调整发布/消费时机、复用约束、跨成员共同空槽协商或资源划分。重点是证明每次等待都有对应状态、跨 rank 寻址槽位一致且复用不会覆盖仍存活的状态，不要求某一种实现。

接口索引可从[官方 Hcomm 数据面说明](https://www.hiascend.com/doc_center/source/en/CANNCommunityEdition/900/programug/commopdev/hcclopdevapi_07_0001.html)进入。该页只作为接口线索，不能代替当前版本的具体行为保证。

## 零数据量与控制消息

数据量为零时，先分别看搬运条件和协议完成条件。接收方若仍等待该 rank、专家或任务的完成状态，发送方就不能把“没有数据可搬”直接当作“整个通信阶段可以跳过”。如果协议按活跃参与者缩减等待集合，则核对双方使用的集合与当前轮次一致。不要要求每个 rank 都有非零数据，也不要把合法的零值或空分区当成异常。

## 跨调用缓存与数据身份

如果错误只在后续调用出现，先区分缓存的是存储空间、执行计划，还是由输入元数据推导的路由/索引。形状相同或总元素数相同，只能说明容量可能复用，不能证明缓存内容仍适用于这次输入。

从缓存内容的生成过程反查依赖：哪些有序元数据、分片归属或布局参与了计算，命中条件是否覆盖它们，失效后是否实际重建。对照命中前后第一次错误的位置，同时核对设备原始中间结果与后处理结果，避免修好一层后漏掉另一层。保留正确缓存或每次重新计算都可以；选择符合公开功能与性能约束的实现，用合法的连续调用验证，不要求某一种补丁形状。

## 自验与交验

自验前从本例明确runner/入口配置定位输入和产物，遵守[产物定位边界](../fix/common-constraints.md#产物定位边界)；不得向父目录或其他会话扩大扫描。

- 覆盖全部 rank、调用轮次和应产出元素，检查文件完整长度与数值；记录哪组输入实际运行过。若提供独立比较入口，优先执行并保留退出码及错位摘要。
- 修复后正常返回时，仍需检查完整输出。若提供了完整数学契约和输入，但没有可用比较入口，应在允许的分析范围内独立计算 CPU 参考并比较设备输出；不因缺少现成比较脚本就跳过数值检查。不能创建额外文件时，可使用不落盘的只读计算。参考计算与被测实现分开，不用设备结果构造参考，不把参考写回设备产物或嵌入修复代码。契约或权限不足时，说明未验证的范围，不凭正常退出宣称数值通过。
- 遵守用户或项目约定的修改范围与验证限制；不读取私有答案，不改 golden、输入或判定脚本，不用常量、高层 collective 或主机计算替代用户或项目要求的数据面。
- 本次修改影响长度边界或跨调用状态、且当前数据未覆盖时，才追加另一组合法长度/数据或多次调用检查；无权改变输入或无额外材料时，说明只验证了已提供数据。未执行的 rank、轮次、长度或设备运行不能声称通过。最终结论以约定的独立验证结果为准。
