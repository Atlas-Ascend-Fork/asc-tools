# 原生通算融合：先找失败阶段，再追数据

适用：原生 ACLNN/MC2 的矩阵通信融合、MoE 路由合并等多 rank 链路。只检查当前证据涉及的部分；不要求把正常链路重新 profiling 一遍。

## 有一侧报错，另一侧一直等

沿每个 rank 记录三个位置：准备参数与 `GetWorkspaceSize`、提交执行、等待设备完成。把最早明确失败的调用与对端最后完成的动作对应起来。准备阶段报错时，后续通信可能根本没有被提交；对端的超时是后果，单纯延长超时或更换通信算法不能修复先前的参数错误。

返回码帮助缩小范围，详细错误才说明这次失败的对象。优先读取该次调用对应的 `aclGetRecentErrMsg` 或 plog 上下文，避免让后一次调用的错误覆盖现场。

| 返回码 | 应查什么 |
|---|---|
| `161001` / PARAM_NULLPTR | 必需输入、输出或属性是否有有效对象；不能直接解释成算子未注册 |
| `161002` / PARAM_INVALID | 详细日志指出的 dtype、shape、属性和平台支持组合 |
| `561002` / INNER_TILING_ERROR | tiling 内部失败；若日志指出入参约束，再查本地 shape 与全局属性是否相容，否则继续定位内部失败 |
| `561003` / INNER_FIND_KERNEL_ERROR | 实际算子包、目标芯片、kernel 路径与构建产物 |
| `561000` / INNER | 通用内部错误，继续用详细日志收窄，不猜唯一原因 |

这些定义可对照[官方 ACLNN 返回码](https://www.hiascend.com/document/detail/en/CANNCommunityEdition/910/API/aolapi/context/ops-nn/aclnn_return_code_nn.md)。现场版本与操作符的详细约束仍须核实。某个可选输入允许为空，不代表同阶段的输出也能省略；业务没有读取某个输出，也不代表当前接口接受空描述符。

区分“没有提供对象”和“提供了内容中性的对象”。可选 mask、量化尺度或辅助张量的存在，可能选择不同的实现分支。是否等价由安装版本的公开契约和实际错误决定，不能仅根据张量数值猜测。若当前主线文档与安装包矛盾，保留双方版本与错误证据，按已验证的接口约束处理，不盲目调整全局 batch 或通信域参数。

## 程序完成了，最终输出却不对

把公开数学关系写成几段，沿设备输入、原生算子输出、局部计算、下一次通信追踪。每个张量至少辨清三件事：它属于谁、按什么顺序排列、是否已完成归约或归一化。

- **矩阵通信融合**：AllGather 后的行属于来源 rank，本卡权重决定输出列；ReduceScatter 前有哪些来源参与求和，输出行落到哪个 rank。量化尺度分别沿 token、channel 或其他明确轴传播，归约前后的尺度操作不总能交换。残差应按业务数学加入，不能因它在每个 rank 可见而重复求和。
- **MoE**：区分全局 expert ID、本地 expert 序号、权重缓存位置以及 token 的 top-k 槽位。搬运或缓存重排之后，权重与专家身份仍要对应。Dispatch 产生的路由恢复元数据是下游 Combine 的协议输入；不能按猜测重排、重建，或拿计数数组替代。辅助输出只在当前文档允许的范围内解释。
- **统计与归一化**：先查原生输出究竟是原始累加量、已归一化结果还是供下一步使用的中间统计。广播维、重复 lane、全遮挡/空分片等特殊值需要从 API 约束与实际结果核实，不能把某个版本的哨兵常量当作跨版本通用答案。

两条不同设备实现若满足公开数学、精度和执行约束，都可能正确。不要要求修复补丁复刻某一种内部缓存顺序、布局或融合方式。

## 把数据依赖落实到实际执行

多个请求或微批次交错执行时，为通信调用记录通信域、调用序号、算子种类、请求身份和必要参数，再跨 rank 对齐。每个 rank 的局部计算依赖正确，仍可能在同一通信位置提交了不同操作。总调用次数相同也不证明匹配；先找最后一组双方都完成的通信，再比较各自接下来的提交。允许计算交错或采用其他合法顺序，但必须能解释对应通信如何匹配。

为当前错误涉及的缓冲区找到最后写入者和第一次读取者。跨 stream 需要真实完成关系；仅有“代码先调用生产者”、事件变量名、预分配的合法地址都不足以说明新数据已就绪。原生融合调用也有 stream 参数，要纳入同一依赖图。

若问题进入自定义 tiling/kernel，先看实际选中的 tilingKey、block 数和分块参数，再追该分支中的发布与消费。不要修改没有运行到的模板。排查加载来源时，区分“链接了某个库”“实际打开了某个 kernel”“设备执行了该任务”三层证据；原生封装器不必含有自定义 `op_kernel` 目录。

在需要证明引擎的任务里，API 名或环境变量只是线索。复用已有 runtime/profiling 记录，把实际 device、stream、task、算子和时间对应起来。重复导出的 CSV 可能包含同一任务；先按任务身份去重。公开 API 版本名与底层 kernel 名不一致时，核对映射，不仅凭名字判定执行错误。

## 缓存的是布局，还是已经绑定的数据

`aclTensor` 并非只描述 shape。创建时还绑定 dtype、stride、offset、format、storage shape 和设备存储地址；见[官方 aclCreateTensor 接口](https://www.hiascend.com/doc_center/source/en/CANNCommunityEdition/910/API/aolapi/operatorlist_00019.html)。复用参数对象或已绑定的执行输入时，要确认它指向本次实际使用的存储。形状和布局相同，不能证明属于同一个输入或权重。

先辨清缓存对象：存储容量、未绑定的布局模板、绑定过地址的张量，还是从数据值推导的预处理结果。沿其生成过程核对设备/上下文、存储身份、偏移、逻辑布局以及必要的数据版本；只检查真正影响该对象的依赖。单纯更新同一存储中的数据，未必需要换描述符；缓存了预处理值时，则还要核对值的版本。已有正确绑定可保留，也可按接口契约重建或重绑定，不强制禁用所有缓存。

## 验证与结论

使用既有比较入口，核对全部要求 rank、轮次和最终输出。中间值用于定位，只有公开契约要求它作为输出时才计入验收。分别报告接口/构建失败、已完成但数值错误、等待超时和通过；没有输出数组就不能报告“数值不符”。

某个部分修改只修好一组合法输入，并不证明第二条根因不存在。根据原始失败与尚未解释的证据检查剩余路径，避免把“当前没有再报错”写成完整修复。具体落码仍遵守[公共约束](../fix/common-constraints.md)。
