# comm-engine-protocol-fault（通信引擎协议层故障）

## 家族定位

**用户自研通信算子的引擎协议实现错误**：异常位于工程内自研通信算子的数据面/同步面**协议要素**——信箱（数据落点）寻址、单边写目的槽位映射、拼装读源缓冲口径、读长与分段偏移口径、就绪通知的发布义务与事件编号取值表、通知原语类别、数据面任务提交句柄、完成回发时序、跨调用状态收口。根因层级 = 用户算子协议实现（user-op-protocol），**非**通信库内故障、**非** host API 使用层误配、**非**设备侧 stream/event 编排错。判别要点：本家族的**通信数据面/同步面协议原语调用本身不产生 API 层错误码**（无入口拒绝、无 API 错误码返回），错在**协议取值与寻址**——注意与浮出信号区分：kernel 载体的完成等待超时会自报失败行（AI CPU+TS 载体 `completion wait failed` 类 / AIV 载体 kernel 下发后流同步超时 `vector core timeout` 类——均属控制面等待超时自报，非数据面原语错误码），kernel 内部原语被拒/超时也不向 host 透出原语级错误——**不得以"有超时失败行"排除本家族**（是否为本家族看错在协议要素而非契约违反，见排除近似）。

载体特征（两类，判别依据是原语的**机制类别**，不依赖具体原语库符号名——自研封装或公开通信库的同类机制数据面 API 均适用）：
- **host 编排类引擎**：主机端单边写 + 分离式事件通知类数据面原语组合（通信线程/通道获取 → 单边写对端信箱 → 事件通知（发布 Record / 带超时等待 Wait）→ 本域拼装拷贝），算子入口在 op_host 侧源码。
- **kernel 编排类引擎**（设备侧 kernel 承载数据面，按同步面机制再分两载体形态）：host 只做资源创建（通信线程/通道/信箱缓冲）与 kernel 下发，数据面搬运与同步任务全部由设备侧 kernel 完成；缺陷载体在 **kernel 侧数据面编排源码**（算子执行体/任务编排文件），host 侧编排通常完全正确。两载体形态：
  - **AI CPU+TS kernel 载体**（任务调度提交模型）：数据面任务（单边读/写/本域上送/通道通知握手）由 kernel 在设备侧向任务调度系统提交；host 与 kernel 经互相导出的线程通知对做启动/完成控制握手（完成以**回发完成通知原语**表达）。
  - **AIV/Vector Core kernel 载体**（软同步 flag 协议模型）：host 将自研 Ascend C kernel 二进制加载下发至 Vector Core 执行，数据面搬运与同步均在 kernel 内完成——同步面为 **HCCL Buffer 软同步 flag 协议**（缓冲分数据区/flag 区，发布方写自槽、等待方轮询对端槽，块/核内角色映射通信角色）；**完成等待以流同步表达，无回发完成通知原语**，kernel 内等待停滞由下发参数中的 launch 级超时兜底截断。

症状形态与参与 rank 对称性无关（对称/非对称均可能）。

## 典型现象（两配方症状族）

**配方一｜通知链路断（同步面协议要素错）→ 等待停滞/超时症状族**
- 协议要素错位形态：就绪通知的发布步骤缺失或被分支条件化（部分 rank/部分通道组合未履行发布义务）；发布侧与等待侧的事件编号取值表不一致（一侧沿用陈旧口径）；通知原语类别错用；数据面任务提交句柄错用；跨调用状态收口缺失。
- 可观测签名（host 载体）：等待侧所等事件永不到来——**无原语级错误行**（等待原语未按其超时参数报错返回，属已观测引擎行为，**不得以"无超时报错"排除等待停滞**）、driver stderr 空；收场 = 编排层有界超时兜底截断 → 非 0 退出，全程无 device error、无 aic error、无 kernel 参与。
- 可观测签名（kernel 载体）：失败锚点在 **host 对 kernel 完成的等待**，浮出形态随载体模型二分——**AI CPU+TS 载体**（回发通知模型）：等待 kernel 回发完成通知，双层浮出——kernel 内有界等待超时或提前出错且**不向 host 回发完成通知** → host 完成等待超时失败（`completion wait failed` 类 stderr 行）→ 进程非 0 退出。**AIV 载体**（流同步模型）：完成等待以流同步表达，kernel 内软同步等待停滞（所等 flag 永不置位 → kernel 内死自旋）→ **流同步超时失败**（`vector core timeout` 类浮出：流同步返回超时错误码〔507034 类〕+ 任务级超时报告行）→ 进程非 0 退出；失败浮出耗时与下发参数的 launch 级超时兜底值同量级（≈ 兜底时长 + 收尾开销）为该形态特征。两形态均可对称（双侧滞留）或非对称（单侧失败退出、对端正常完成）。
- 停滞形态二分（定位关键）：**非对称停滞**（单 rank 滞留、对端走完全程且数据校验通过——host 载体通知义务违约方恰是"走完"的一方，构成"滞留 rank ≠ 缺陷引入 rank"的跨 rank 因果；kernel 载体缺陷侧即滞留侧或呈假成功分居）；**对称停滞**（全体 rank 滞留——编号/句柄/收口类错位使双侧互不命中或任务全不入队）。
- **假成功变体**（kernel 载体）：通知误发到 host 完成等待所在的**控制通道** → 对端在数据面通道上所等事件永不到来（超时失败），本端完成等待却被误触发提前解除——op 返回异常快"成功"、本端校验通过正常退出。**症状与根因分居两侧**（失败侧在对端、成功侧反而是缺陷侧），需跨 rank 日志关联定位。
- **跨调用状态泄漏变体**（kernel 载体）：同一算子/同一通信标签**第一次调用全部通过、第二次调用停滞超时**——成功路径未做引擎侧状态收口（按标签存续的批量/会话状态跨调用泄漏），"错误反而无害、成功反而埋雷"的隐蔽形态；证据需跨调用关联（前一次校验通过行 × 后一次超时行）。

**配方二｜消息语义坏（数据面协议要素错）→ 静默数据损坏症状族**
- 协议要素错位形态：单边写目的槽位映射错（写入落点按陈旧映射计算）；拼装读源缓冲口径错（"通道对端窗口"查询与"本域通信缓冲"查询是**两个不同缓冲**，拼装误从永不被对端写入的区域取数）；单边读长度/分段偏移口径错；完成回发时序提前。
- 可观测签名：通信正常完成、事件同步全部通过、无任何报错无 hang；显形于**数据级校验**——输出中本 rank 段正确、自远端来源段起整段不符（常为零值/未写入区域读值），退出码非 0。
- 旁证信号：工程内"经查询接口取得而全程未使用"的缓冲指针（死变量）是两种缓冲口径混用的强提示。
- **读长/分段口径形态**（载体中性）：接收侧输出**前段精确、自某元素界起整段保持预置值**（预置零缓冲的后半全零）——单边读长度误用固定类型尺寸口径（与算子实际数据类型不符）或分段偏移按错误视角取值。
- **收发分段倒置形态**：对称交换类算子两 rank 输出**逐字节相同而期望互异**、错值为**合法原值**（对端输入原样，互补分段错位）——发送段/保留段角色随 rank 视角互换，上送分段偏移误用自视角索引；与归约读切片归属错（错值为**和**）按错值类别区分。
- **归约读切片归属错形态**（拉模式协议，host/kernel 载体均可）：拉模式归约类算子（本端全量输入上送本域信箱后，从各对端信箱"拉取本 rank 所属切片"归约累加）的**拉取源切片映射与切片归属映射两侧异表**——从对端信箱拉取的切片索引误按对端视角取（"我要的切片在对端数据中的位置"实由本端所属切片决定，与对端是谁无关）。可观测签名：通信正常完成、无任何报错；**两 rank 输出相同（或非互异）而期望各不同**、错值为**聚合"和"类值**（每 rank 归并进同一错误切片的贡献）——与收发分段倒置（错值为**合法原值**）按错值类别区分。
- **完成回发时序形态**（AI CPU+TS kernel 载体，间歇性）：通信/握手/返回码全正常 + **op 返回耗时异常短** + 输出偶发全零/部分拼装（预置缓冲未被设备侧任务覆盖）——host 回读先于设备侧数据面任务落地（竞态，偶发通过）。与"算子未执行/未部署"表象同形，区分证据 = 执行链路自证通过（预检/加载/下发证据齐全）+ 无设备侧错误行 + 返回耗时异常短三证据联合。

## 调用工具

1. **[plog](../tools/plog.md)**：作为阶段辅助侧证，对当前运行日志窗执行单次窄 grep（`timeout|HCCL_E_|fail|error`）核对是否存在库层或链路层报错信号；当前采样窗口零命中仅说明该窗口未见上述日志特征，仍结合通信域初始化链与源码协议要素逐项核查（本家族主证据在源码协议要素，勿全量读 plog）；如需形态旁证，仅对滞留 rank 的单个 plog 文件取资源获取链后的最后 ~10 行（`tail`）。**现场仅静态材料（无运行日志/plog）时**：以题面与基线摘要（现象描述、失败锚点、参与 rank 对称性、返回耗时异常等）定配方，直接进入源码协议要素核查，不因缺日志而停滞。
2. 源码协议要素核查（本家族主证据源 = 算子工程源码〔host 载体查 op_host 侧、kernel 载体查 kernel 侧数据面编排文件〕 + plog/题面侧证；无需重跑）。

**最小确认集**：README/题面、退出码和已有日志先确定现象，再定向查看通知、任务提交和数据区间。沿实际发布/消费关系核实原因，不能仅凭字符串命中定因。批量通知或资源复用还需读[通知与实际资源核查](../method/protocol-data-flow.md#通知与实际资源)，确认同一槽的未消费状态是否被覆盖。已有证据足够时进入修复，不追加无目标采集。

## 决策逻辑

1. 症状为"静默停滞 + 编排层截断 + 无原语报错"且算子为**自研主机侧通信算子**（源码通信由"主机端单边写 + 分离式事件通知"类原语组合承载，判别看机制类别、不看原语库符号名）→ 进入本家族配方一核查（协议要素核查 ①②）。
2. 症状为"host 完成等待超时失败（`completion wait failed` 类——AI CPU+TS 载体）/ kernel 下发后流同步超时失败（`vector core timeout` 类——AIV 载体）/ op 返回异常快假成功 / 第一次好第二次坏"且算子为**自研 kernel 编排引擎通信算子**（工程含设备侧 kernel 数据面编排源码，题面/源码声明数据面由设备侧 kernel 承载）→ 进入本家族配方一核查（协议要素核查 ①④⑤⑥⑦，kernel 载体位；AIV/软同步载体主要消费 ① 软同步槽位——④–⑦ 为 AI CPU+TS 任务调度提交模型专用要素）。
3. 症状为"正常完成 + 数据级校验失败（远端来源段整段不符/前段精确后段预置值/双侧同值互补错位〔错值为合法原值〕/双侧同值聚合错位〔错值为"和"，拉模式归约读〕/间歇性全零）"且无 API 报错 → 进入本家族配方二核查（协议要素核查 ②③⑧⑨）。
4. 任一协议要素核查命中（发布义务缺口 / 编号两侧异表 / 写读落点异映射 / 缓冲口径混用 / 等待索引异表〔含软同步 flag 槽位两侧异表〕 / 任务句柄类别错用 / 完成回发时序提前 / 状态收口缺失 / 原语类别错用 / 读长分段口径错〔含拉模式归约读切片归属视角错〕）→ 本家族；§4 根因须落到"用户算子引擎协议层"的具体要素与代码位置（kernel 载体缺陷落在 kernel 侧源码，不得误报 host 编排）。

**排除近似类型**：
- 与 [communication-timeout](communication-timeout.md)：communication-timeout 有 watchdog/超时报错等库层超时信号；本家族（host 载体）无任何超时报错（等待原语不报错）且根因在用户算子协议实现。kernel 载体对称超时形态与 communication-timeout 同形——判别：communication-timeout 第一跳排查项（collective 参数不一致/rank 缺席/等待环）全部落空 + 失败锚点在 host 对 kernel 完成的等待（AI CPU+TS 载体 = 完成回发等待；AIV 载体 = kernel 下发后的流同步等待——流同步超时错误码/任务级超时报告属超时兜底浮出，非 kernel 独立错误行，亦非数据面原语错误码）+ 算子为自研 kernel 编排引擎 → 本家族（**有超时失败行不排除本家族**）；参数确有不一致/确有缺席/确有等待环 → 对应家族。
- 与 [stream-event-cycle](stream-event-cycle.md)（停滞配方最近似）：stream-event-cycle 的等待对象是设备侧 stream/event 原语且缺陷在依赖图次序/生命周期；本家族等待对象是**用户算子内的引擎通知协议要素**（事件编号/发布义务/原语类别/句柄/收口）——形态学同构（never-satisfied wait）但层级不同。判别：源码中等待-发布对位于自研算子的协议原语组合内（host 或 kernel 侧）→ 本家族；位于 runtime stream/event 编排 → stream-event-cycle。
- 与 [single-rank-block](single-rank-block.md)：本家族无 rank 缺席——各 rank 均到达调用点、算子正常提交（非对称形态下"走完/假成功"的 rank 完整参与且本端校验通过，不是缺席方；假成功侧反而是缺陷侧）。
- 与 [comm-operator-anomaly](comm-operator-anomaly.md)（损坏配方最近似）：comm-operator-anomaly 是调用即违反 API 契约（入口拒绝/错误码/崩溃）；本家族原语调用全部成功返回，错在协议取值与寻址——无任何 API 报错是分界签名（原语类别/句柄错用也**不产生错误码**，而是被错误消费）。
- 与 [collective-param-mismatch](collective-param-mismatch.md)：跨 rank 一致性参数（count/dataType/op/root/comm 句柄）两侧完全一致；错在算子**内部**协议实现，无 rank 间参数对比可违。
- 与 [rank-group-mismatch](rank-group-mismatch.md)：通信域/线程/通道/图获取全部成功（资源链完整），无建链/协商失败。

## 定位方法（协议要素核查。载体适用口径：**①②③ 载体通用**——① 含 kernel 两载体位；**④–⑦ 为 AI CPU+TS kernel 载体增补**（任务调度提交模型专用要素）；**⑧⑨ 为配方二通用扩展**——host/kernel 载体均适用〔拉模式/读长/分段/归属口径与跨侧同表不分载体〕）

1. **通知义务覆盖核查**（载体通用，含 kernel 两载体位）：grep 算子源码全部通知发布调用与全部通知等待调用，逐 (rank 维度, 通道) 组合核对——发布是否被 rank 条件分支/循环边界条件化遗漏（义务覆盖缺口）；每对发布↔等待的 (通道, 事件编号) 是否**两侧同表**（同一取值口径；一侧残留陈旧口径即互不命中）。AI CPU+TS kernel 载体位：等待索引与**对端 kernel 的发布索引**配对核对——等待侧误用自身已发布的索引（自证已发事件）是典型形态。AIV/软同步载体位：软同步 flag 的**等待轮询槽位与发布方发布槽位两侧同表**——发布方写自槽，等待方须轮询**发布方槽位**（对端缓冲中发布方所属的槽）；等待侧误用自视角索引（自身 rank 号槽 / 自身已发布槽）使所等 flag 永不被对端置位 → kernel 内死自旋、由 launch 级超时兜底截断，为该载体典型形态。
2. **写-读落点一致性核查**（载体通用）：单边写的**目的槽位映射**与接收方**拼装读源取点映射**必须是同一映射的两侧（本 rank 写入的槽位 = 对端拼装时读取的槽位）；参与规模/拓扑变化引发的映射更新须两侧同步（陈旧映射残留是典型缺陷形态）。
3. **缓冲口径核查**（载体通用）：区分"通道对端窗口缓冲查询"与"本域通信域缓冲查询"两类接口的返回语义——对端单边写入的实际落点在**本域侧**缓冲，拼装读源应取本域侧；误取对端窗口地址即"从永不被写入的区域读数"。工程内取得而未使用的缓冲指针（死变量）是口径混用的旁证。
4. **数据面任务提交句柄类别核查**（AI CPU+TS kernel 载体）：kernel 内数据面任务（读写/上送）须由**本引擎自有线程句柄**向任务调度系统提交；跨引擎导出的线程句柄仅承载**控制通知**（host↔kernel 启动/完成握手）——两类句柄同为线程句柄但用途不同，数据面任务误用控制通知句柄提交**不报错但任务不入队**（通知全对、任务全丢）。核对数据面提交调用与完成通知调用所用的句柄来源是否同源异用。
5. **完成回发时序核查**（AI CPU+TS kernel 载体）：完成回发（通知 host 可回收结果）必须位于**全部数据面任务落地之后**（写/读/拼装全部提交完成）——host 对 kernel 提交的设备侧任务**无流级同步覆盖**，完成通知是 host 侧唯一同步点；完成回发出现在任一数据面任务提交之前即构成 host 回读竞态（间歇性损坏）。核对完成回发调用在 kernel 编排中的相对位置。
6. **跨调用状态收口核查**（AI CPU+TS kernel 载体）：引擎侧按标签存续的批量/会话状态，其开启/收口调用必须**成对且覆盖成功路径**（错误路径收口、成功路径遗漏是隐蔽形态——异常不出在本次调用而浮出于后续同标签调用）。"同一算子第一次好、第二次坏"签名出现时强制核查两条路径的收口差异。
7. **通知原语类别核查**（AI CPU+TS kernel 载体）：**通道通知**（数据面就绪/取走握手，按通道事件编号寻址）与**线程通知**（host↔kernel 控制握手，含完成回发）是**两个独立握手域**——数据面就绪发布误用线程通知原语时，对端在通道上等不到（超时）且本发通知被 host 完成等待**错误消费**（假成功）。双侧症状分居（对端超时 + 本端异常快成功）出现时强制核查发布调用的原语类别与目标通道/线程。
8. **读长与分段口径核查**（载体通用）：单边读长度 = 元素数 × **算子声明数据类型**的尺寸（误用固定类型尺寸口径 → 前段精确后段预置值）；对称交换类算子的分段偏移须按**目标 rank 视角**取（保留段/发送段角色随视角互换，误用自视角索引 → 双侧输出同值互补错位、错值为合法原值）；拉模式归约读的**拉取切片归属视角**核查——从对端信箱拉取的切片索引须按**本 rank 归属视角**取（"我要的切片在对端数据中的位置"由本端所属切片决定，与对端是谁无关），拉取源切片映射与切片归属映射**两侧须同表**（误按对端视角取对端所属切片 → 每 rank 归并错切片贡献，两 rank 输出同值而期望互异、错值为聚合"和"）。
9. **协议要素跨侧同表总核**（载体通用）：上述各要素的取值表/映射/口径在发布侧与等待侧、发送侧与接收侧、本端与对端**必须两侧同表**——本家族缺陷的统一形态是"单侧沿用错误口径"，修复前须定位错误侧并以对端/协议语义侧为基准。

## 报告归档映射（当前接口固定为 8 类）

- 停滞配方（通知链路断，含 kernel 载体各形态与假成功变体）→ 按 **stream-event-cycle**（次序错配型，语义最近：never-satisfied wait）归档 §1；§2 如实记录滞留 rank 与（非对称/假成功形态下）缺陷引入 rank；§3 记录引擎通知等待/host 完成等待级等待点（AI CPU+TS 载体 = 完成回发等待；AIV 载体 = kernel 下发后流同步，kernel 内软同步轮询为实际停滞点）；§4 如实记录"用户算子引擎协议层"根因。
- 损坏配方（消息语义坏，含读长/分段/归属/时序形态）→ 按 **comm-operator-anomaly**（自研算子内部实现缺陷，语义最近）归档 §1；§4 记录协议寻址/口径根因。
- 内部第九类 `comm-engine-protocol-fault` 继续用于知识导航与根因描述；当前解析器仅接收上述八类，不能在 §1 自行新增枚举。将来接口升级须同步修改解析器、题面与 Skill 后再启用新枚举。
