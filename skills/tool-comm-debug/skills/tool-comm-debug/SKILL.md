# 多卡通信排查与修复

按当前现象选入口，不必先确认故障类型：

- **卡住、超时或接口报错**：从[症状分流](references/INDEX.md)开始，结合各 rank 的退出状态和最后完成的动作。
- **正常返回但输出错误**：从[通信数据流与完整输出核查](references/method/protocol-data-flow.md)开始。AIV/MTE 的数据就绪、消费与缓冲复用也适用；具体原因仍由当前执行路径与数据证据确认。

**修复闭环要看结果。** 原来的报错消失后，回到公开输出契约，检查全部 rank、轮次和最终产物。只有退出码为 0，还不能说明数值已经修好。若题面给出了完整数学语义和输入、又没有现成比较器，应在允许的分析范围内，从这些公开信息独立计算参考并比较实际设备输出；不把参考计算写入被测数据路径。没有足够语义或验证权限时，明确留下的验证缺口，不猜参考值，也不宣布数值已通过。

和用户一起把问题查清楚：哪一侧先出现异常，通信停在哪里，或者数据从哪一步开始不对；再用现场证据支持修复，并确认结果。用户不需要先知道故障类别，也不必准备齐全套日志。

先解决当前问题。下面是工作入口，详细知识放在同级 `references/` 中，只读当前证据需要的部分。本技能独立运行；可选外部知识由固定版本 cannbot-knowledge 提供，按[知识访问说明](references/knowledge-access.md)查阅，实际工具仍使用现场 CLI。

## 1. 先接住用户的问题

从用户给出的症状、日志、退出码或源码开始。用户只问原因时，给出证据和排查建议；用户要求修复且允许修改工程时，把修改和验证做完。不要把“请修复”停留在建议上，也不要为单纯诊断擅自修改代码。

- **确认现场**：使用本次明确提供的工程、日志与配置。输入和输出位置以入口脚本、公开配置及 `INPUT_DIR`、`META_FILE`、`OUTPUT_DIR` 为准；展开变量后只访问已授权的精确目录。文件缺失时先核对配置与退出码，不向父目录、其他会话或全盘扩大搜索。全程基于本地已有工程、公开知识与 SDK 材料离线排查，不执行 `curl`、`wget`、`git clone`/`fetch`/`pull` 等外部网络请求或在线依赖拉取。详见[产物定位边界](references/fix/common-constraints.md#产物定位边界)。
- **复用环境证据**：对照[适用范围与限制](references/applicability.md)，核对实际构建和运行加载的 CANN 路径、版本与设备证据。已有可信摘要就复用；仅缺项或矛盾时使用现场 npu-smi、SDK 版本文件和构建配置补查。区分用户可见逻辑 device id、物理 chip id 与部分底层映射权限接口要求的驱动逻辑 device id，不直接混用。版本不同本身不是拒绝理由。
- **信息不够时**：说明当前能确定什么、还缺哪项证据，以及补齐它能排除什么。给出最小待采集清单，不先让用户收集所有工具输出。

默认 `core`：利用现有日志和源码完成通信等待或数据错误的定位、修复与验证。`full` 在此基础上增加多卡链路分析和 Rank/Stream 依赖分析；按请求与证据选择，不因开启技能就启动整套探测。

## 2. 先分清：没跑完，还是跑完却算错了

### 卡住、超时、接口报错，或现象还不清楚

先保留退出码、stderr/stdout 的关键行，以及各 rank 最后完成的动作。对大日志先看行数、关键词计数和命中位置，通常取命中行前后几行即可；超过 200 行的文件不要无过滤整份输出。plog 的常见位置是 `~/ascend/log/run/plog/`、`run/device-<N>/`、`debug/plog/`；以本次配置或已提供快照为准，只读取授权位置。

读[症状分流表](references/INDEX.md)，圈定少量候选；需要判别时再读对应的 `references/symptoms/<type>.md`。超时只说明“有人没等到”，还不能说明谁先出错。对照各 rank 的调用次序、参数、退出状态和等待关系，定位先发生异常的一侧。

涉及批量通知、队列或资源复用时，读[通知与实际资源核查](references/method/protocol-data-flow.md#通知与实际资源)。不要只数发布和等待次数：需要确认每次等待能消费哪一次发布，以及复用前的状态是否已经收回。原生融合链路还要跨 rank 对齐通信调用，而不只检查各自的局部依赖。

工具输出可能推翻初判。遇到类型交叉，按[边界判定](references/boundaries.md)的工具结果回流表与 B1/B2 规则重新核对，不固守第一个标签。最终说清四件事：**异常类型、异常 rank、等待位置、根因**。

### 通信正常返回，但数据不对

退出成功不代表通信正确。已有公开数学契约、多 rank 数据差异和相关源码时，直接读[通信数据流与完整输出核查](references/method/protocol-data-flow.md)，从输入一路追到设备结果和落盘输出，重点看：

- 这段数据属于哪个 rank、哪一轮，生产方与消费方是否对应。
- 搬运的偏移和长度是字节还是元素，要求的输出是否全部覆盖。
- 缓冲区、通知和累加状态在下一轮复用前是否满足使用条件。

归属核清后，把路径、rank/轮次、dtype 和有效长度记成简短索引，后续增量核查未知环节；在授权范围内复用已有的数学参考和检查，避免为每个疑点另写近似脚本。最终仍覆盖全部要求的输出。

这些是核查方向，不是看到症状就能套用的答案。证据已能定位时，读公共修复约束后即可落码，不必补读总索引或所有症状页。出现等待、接口报错、参数或归属歧义时，再回到常规分流。AIV 尾部搬运证据明确时，按需查[GM/UB 对齐核查](references/method/aiv-transfer-alignment.md)。

### 原生 ACLNN / MC2 链路

如果现场用了矩阵通信融合、MoE Dispatch/Combine 等原生算子，按需读[原生融合链路核查](references/method/native-fused-operators.md)。先区分参数/tiling 准备、设备提交和等待完成；再追踪路由、尺度和跨流依赖。某 rank 在准备阶段先失败，其他 rank 的通信超时可能只是后果。

## 3. 用工具回答具体问题

先写清这次调用要确认什么，再选最小工具集。对长头文件或驱动源码优先用 `rg` 或行号区间定向读取目标函数与结构体，避免一次性连续通读数千行源码后在单步思考中空想推演全流程而触发单轮输出长度截断；形成主因假设后尽早最小落码并执行公开构建/运行入口，用真机实测结果驱动下一步排查。现有日志和 plog 足够定位就进入修复；不够时，按症状页指引读取 `references/tools/<tool>.md`，再选择 msprof、msnpureport、hccn_tool、hccl_test 或 msaicerr。重采集需有明确证据缺口，并用 `timeout` 限时。

工具参数以当前环境的 `--help` 与官方文档为准。未知 API 先确认工程实际使用的版本：内置参考已覆盖时直接复用；核对签名、类型或参数单位时，可从工程已有 include 入手，定向读取对应的公开 SDK 声明与注释。同步、缓存可见性和生命周期等行为保证，不能仅凭函数名或头文件推断；按知识访问说明检索固定版本知识卡并核对官方来源，或在任务允许的范围内做最小验证。工具页有扩展指引时再调用对应技能。不做无目标的全 SDK 扫描。连续查询仍未补上关键证据时，先收住这个方向，记下未确认项；换查版本匹配的公开资料，或在授权范围内做一个能区分候选的小验证。只有明确要验证哪个假设，才进一步查内部实现；字符串命中本身不证明该分支实际运行。

同一会话已经确认的环境、读过的参考和未受改动影响的验证结果可以复用。没有新矛盾就不重复查版本、搜文档或运行工具；出现新证据时，再更新结论。

## 4. 把修复做到能验证

落码前完整阅读[修复落码通用约束](references/fix/common-constraints.md)。其中八项工程约束适用于所有修复，不因使用快速路径而省略。常规分流还需按证据读取[修复索引](references/fix/INDEX.md)的相关类型节；数据流证据已经明确时，不重复加载无关类型资料。

确认 API 签名与版本语义后做最小修改，说明改动怎样恢复通信、数据归属或同步关系。保留要求的引擎和真实设备数据面，以及全部 rank、轮次和元素；不能靠删等待、跳过计算或换成主机结果来制造通过。严格遵守契约允许修改的文件列表，临时调试也不触碰范围外文件、golden、判定脚本或受保护输入。若工程单次编译耗时较长（如大型算子或通信库），在确认根因并完成最小落码后，先将根因、证据链与修改方案写入目标报告路径，待编译和设备验证完成后再更新实测验证结果，避免长耗时构建挤占交付时间。

修复后构建并运行约定验证：逐 rank 确认输出位置、文件长度和实际数值，覆盖要求的轮次与元素。公共约束中的数据签名判读、复合根因跨文件核查和输出命名要求仍需执行。编译通过、程序退出或文件存在都不能单独作为修复成功的依据。

展示日志时用了 `tail` 等过滤，仍要保留实际构建/运行命令的退出码。比较前确认输出确由最新修改后的这次成功运行产生；运行失败或产物来源不明，就把验证标为未完成，不让旧文件或管道尾命令的成功掩盖它。

没有可用比较入口时，可按公开数学契约从实际输入独立计算 CPU 参考值，**只用于比较设备输出**。修改涉及长度边界或跨轮状态、当前数据又没覆盖时，在授权范围内补充相应检查；无法补测就明确验证限制。构建失败先根据错误行修改，数值失败再回到数据流核查，不盲试、不重复运行已通过且未受改动影响的项目。

私有答案不属于排查材料。只有用户或任务明确授权用于对照的参考实现，才可读取并比较；不能因目录存在或名称像 `fix/` 就自行查找答案。

## 5. 把结论讲给用户听

先说发现了什么、修了什么、实际验证到了哪里，再给支撑证据。语气像同事交流，用具体的文件、函数和 rank 解释；不整段抄日志，也不把猜测写成结论。

需要交付诊断报告时，写入指定路径。开头用 1–2 行交代实际构建/运行环境及证据来源，正文保留以下七节，兼容现有报告接口：

1. **异常类型**：使用 `communication-timeout`、`collective-param-mismatch`、`rank-group-mismatch`、`single-rank-block`、`stream-event-cycle`、`sync-imbalance`、`comm-operator-anomaly` 或 `composite`。证据不足时说明候选与缺口，不强行定类。
2. **异常 rank**：区分出错侧、等待侧和缺席侧，附已有的 pid/deviceLogicId 证据；未知项明确标记。
3. **等待点 / 卡死点**：定位到算子或函数。没有等待、只有数据错误时写明这一点，并指出错误输出或数据流位置。
4. **根因**：解释哪条通信、资源槽位或接口契约关系被破坏及如何产生现象；若现场同时涉及调用方前置操作与底层库属性查询或回退分支，把首错直接因果与关联库分支的实际回退范围分别说明；当契约声明多个可修改文件（如公开头文件、内部实现头与核函数封装）而最小修复仅改动其中子集时，一并说明其余声明文件在接口转发、模板实例化或 ABI 兼容链中的职责及无需改动的原因。
5. **证据链**：文件与行号、关键日志或工具结果，每条结论至少有一条证据。
6. **修复建议**：写清实际修改或建议修改的位置、依据与验证结果，引用用到的修复模式或数据流方法；区分已通过、失败和未执行项。
7. **自评**：有明确授权的参考实现时，说明完全一致、部分一致或不一致及原因；未提供时写“未作参考实现对照”，不为填写此节寻找答案。

引擎协议故障是内部知识中的第九类，报告仍使用上面八类接口：通知停滞填 `stream-event-cycle`，通信完成后的数据损坏填 `comm-operator-anomaly`，并在根因中写明“用户引擎协议层”和具体机制。
