# 能力范围与限制

本页说明 `npu-check` 已验证的运行配置、检查边界和结论边界。超出已验证配置时，应将对应能力标记为
不支持或未知，不能把运行结果解释为有效检查结论。

## 已验证运行配置

- 目标设备是 Ascend 950（dav-3510）。
- 使用与目标 NPU 和驱动匹配、且包含 `npu-check` 的 CANN 包。
- 目标程序是可执行文件，脱离 `npu-check` 后也能成功执行核函数。
- 应用通过 `<<<>>>` NPU 核函数调用语法或 aclnn 调用一个算子，且一次运行只下发一次。
- 应用以单进程、单线程方式运行。
- NPU 核函数下发后调用 `aclrtSynchronizeStream` 或 `aclrtSynchronizeStreamWithTimeout`，以触发检测数据导出和处理。
- PyTorch 场景暂不支持。

## 检查边界

- `memcheck` 检查已支持指令对设备全局内存（GM）的访问，以及 L1、L0A、L0B、L0C 的容量越界。
  当前包含部分标量直接访问（scalar）；不能据此外推到所有 scalar 指令、全部片上访问或其他芯片架构。
- `synccheck` 检查核内 `SET_FLAG -> WAIT_FLAG`、`GET_BUF -> RLS_BUF` 配对及重复设置问题，并检查受支持的跨核同步模式。
- `initcheck` 检查受支持的持久化寄存器依赖及 GM、L1、L0A、L0B、L0C 的初始化状态；不是地址越界检查。
- `racecheck` 检查同一次下发内缺少必要同步的冲突访问，不检查不同下发之间的竞争，也不能代替 memcheck 或 initcheck。
- `npu-check` 不检查数值精度、性能、CPU 侧（Host）逻辑或构建配置。

### GM 越界判定基准

`memcheck` 根据受支持分配接口和 `aclrtFree` 的成功返回结果记录当前有效的 NPU 内存分配范围：

1. 分配成功且返回有效的 NPU 内存地址时，工具记录起始地址和分配大小。`aclrtMalloc`、`aclrtMallocAlign32` 的
   检查边界使用申请字节数向上按 32 字节对齐后的大小；`aclrtMallocWithCfg` 按请求字节数记录，不套用该对齐规则。
   这些记录规则不改变应用实际传入的分配参数。
2. `aclrtFree` 成功且能够找到对应分配记录时，工具将该范围标记为已释放，用于识别释放后访问。分配或释放失败时，
   不更新记录。
3. 对本次实际执行的受支持指令，工具比较访问范围与同一 NPU 设备上的有效分配范围。访问范围必须完整落入一个
   当前有效的分配范围，否则可能形成越界、释放后访问或未知地址诊断。

需要进行地址计算时，文档使用 `[start, end)` 表示“包含起始地址 `start`，但不包含结束地址 `end`”。例如，
申请大小向上对齐后的有效范围可表示为 `[base, base + alignedBytes)`，其中 `base` 是起始地址，`alignedBytes` 是
对齐后的字节数。

该判定依据是 NPU 内存分配范围，不是张量（Tensor）的逻辑输入形状或有效数据边界。如果 CPU 侧代码为 NPU 申请了
额外预留空间（padding）、内存池或复用缓冲区，访问即使超出逻辑数据范围，只要仍在同一有效分配范围内，就不一定会
被报告为 GM 越界。报告中的 `size N bytes` 是本次完整访问长度，不是实际越过分配边界的字节数；真实越界量需要
用访问结束地址与分配结束地址计算。

不要将上述分配记录机制外推到未明确支持的其他分配接口。

### 片上容量判定基准

Ascend 950（dav-3510）上，memcheck 对已支持指令产生的 L1/L0 访问按以下空间容量检查：

| 空间 | 容量 | 有效字节偏移范围 |
| --- | --- | --- |
| L1 | 512 KiB（524288 字节） | `[0, 524288)` |
| L0A | 64 KiB（65536 字节） | `[0, 65536)` |
| L0B | 64 KiB（65536 字节） | `[0, 65536)` |
| L0C | 256 KiB（262144 字节） | `[0, 262144)` |

每个已还原的访问区间都必须完整落入对应空间的容量范围。这与 GM 的动态分配记录无关，不需要为片上空间寻找
`aclrtMalloc` 分配或 `aclrtFree` 释放记录，也不应把报告中的片上地址解释为 GM 地址。

例如，L0A 从偏移 `65520`（`0xfff0`）开始读取 32 字节，访问结束偏移为 `65552`（`0x10010`），超过容量
16 字节。报告中的 `size 32 bytes` 是访问总长度，不是越界量。

容量检查不追踪用户在空间内部划分的每个 buffer 的起止位置。访问即使越过某个逻辑 buffer，只要仍在该空间容量内，
也不能据此保证一定报告越界。这里不承诺 UB 或其他未列出空间的 memcheck 边界检查；不支持的指令、模式或无法精确
还原的访问不能按完整覆盖解读。平台范围仍限于 Ascend 950（dav-3510）。

## 同步检查判定基准

- `synccheck` 检查 `SET_FLAG/WAIT_FLAG`、`GET_BUF/RLS_BUF` 的实际执行记录。
- 检测数据在 `aclrtSynchronizeStream` 或 `aclrtSynchronizeStreamWithTimeout` 调用时导出并处理；被测应用未调用任一
  接口时，不具备本次检查所需的导出触发条件。
- 工具根据指令参数（如源/目的流水标识 `src/dst pipe`、事件编号 `event ID` 或缓冲区编号 `buffer ID`）和实际
  执行次数判断是否配对。
- 报告可区分前置操作重复执行、缺少对应前置操作和前置操作未被消费。synccheck 只检查本次运行实际执行到的同步操作。未进入的分支、未执行的循环或提前返回后未运行的代码，不属于本次检查结果。
- 跨核检查覆盖当前已支持的 `FFTS_CROSS_CORE_SYNC/WAIT_FLAG_DEV` 等同步操作及模式；需要结合报告中的模式、
  flag、参与核与拓扑信息解释。未知模式或不支持的拓扑不能当作完整检查通过。
- 诊断只表示本次执行发生同步操作配对问题，不提供预期同步设计或算子代码修改方案。

## 初始化与竞争检查边界

- `initcheck` 的寄存器检查基于已支持搬运、Fixpipe 等指令明确的持久化寄存器依赖；内存检查区分 GM、L1、L0A、
  L0B、L0C 的初始化状态。没有已知且按同步关系可见的写入，可能报告未初始化读取。未初始化不等于越界，
  已写入也不等于数值正确；访问范围、指令或同步覆盖不完整时应保留不完整结论。
- `racecheck` 检查写后读（RAW）、读后写（WAR）、写后写（WAW）及原子写语义竞争。支持 ADD/MIN/MAX 原子写，
  相同原子模式的写访问之间不视为竞争；不同原子模式或原子写与普通读写重叠且缺少必要同步时参与竞争检查。
  不支持或无法识别的原子配置使分析不完整。单次下发内可报告多个竞争，同一内存区间仅报告首次确认的竞争，
  不能以报告条数代表所有动态冲突次数。

## 结论边界

检查结论只覆盖本次命令、输入、实际执行路径、启用的检查类型和工具实际生成的报告。“本次未发现明确问题”不能
证明：

- 未执行的输入形状、任务块或条件分支没有问题；
- 未启用的检查类型没有问题；
- 本次未执行或工具未报告的其他接口（API）、操作及访问没有问题；
- 数值精度、性能、CPU 侧逻辑或构建配置正确。

官方资料未明确说明支持的检查对象，统一标记为“覆盖范围未知”。
